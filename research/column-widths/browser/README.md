# Браузерная валидация `pretext` (H4)

Стенд тикета [#479](https://github.com/mavkasgit/ktm2000/issues/479): один и
тот же текст меряется дважды — моделью (`pretext.lineCount`) и реальным
Chromium в `table-fixed`-ячейке. Проверяется гипотеза H4 из
[`docs/specs/preview-column-widths.md`](../../../docs/specs/preview-column-widths.md):
расхождение меньше 1% строк.

## Запуск

```bash
npm install --prefix research/column-widths   # vite, @playwright/test, pretext
npm --prefix research/column-widths run browser:test
```

`browser:test` прогоняет оба стенда: точность H4 (`validation.spec.mjs`) и
рантайм-замер (#483, `runtime.spec.mjs`).

Playwright сам поднимает Vite на свободном порту, `retries: 0`, `workers: 1`,
только chromium. Браузеры берутся из общего кэша `%LOCALAPPDATA%\ms-playwright`;
`npx playwright install` нужен, только если chromium 1254 (Playwright 1.65.0)
там отсутствует.

Сырой JSON пишется в `research/column-widths/results/browser.json` (каталог
`results/` не коммитится). Markdown-фрагмент ниже — доказательство для
итогового отчёта #485.

## Что рендерится

- `table-layout: fixed` + `<colgroup>`; ширина колонки = ширина контента +
  `CELL_PADDING_PX` (12 px).
- `font-size: 11px`, `line-height: 20px` (`LINE_HEIGHT_PX`), шрифты
  `11px "Inter"` и `11px "JetBrains Mono"` из `fonts/` (WOFF2, OFL-1.1).
  `document.fonts.load` + `document.fonts.ready` до первого `prepare()`.
- `overflow-wrap: normal`, `word-break: normal`, без `line-clamp`: потолок
  строк — свойство потребителя, а не текста, и скрыл бы строки от измерения.
- Профили генератора: все семь. Текстовые колонки модели (`wrap: true`) —
  `source_name` и `errors`; ширины контента 60/90/120/150/180/220/280 px.
  Ширины ниже `minPx` (90) — диагностика, в H4 не входят.
- Mono-колонки (`source_code`, `sku`) — отдельная диагностика: в продукте они
  обрезаются в одну строку, но проверяют перенос по дефису.
- Seed 1, 100 строк на профиль. Фактическое число строк — по
  `Range.getClientRects()` (у каждой визуальной строки свой `top`); высота —
  по высоте контента ячейки / `LINE_HEIGHT_PX`.

## Результат H4

Текстовые колонки, ширины 90–280 px (продуктовый диапазон `minPx..maxShare`):

| Профиль | Непустых ячеек | Расхождений строк | Доля |
|---|---:|---:|---:|
| `realistic` | 612 | 0 | 0.00% |
| `long-tail` | 876 | 4 | 0.46% |
| `outlier` | 636 | 0 | 0.00% |
| `all-short` | 654 | 0 | 0.00% |
| `mono` | 618 | 0 | 0.00% |
| `mixed` | 642 | 0 | 0.00% |
| `empty` | 618 | 5 | 0.81% |
| **Итого** | **4656** | **9** | **0.19%** |

Высота расходится ровно там же и ровно на столько же: каждое расхождение —
одна лишняя строка (20 px). Отдельной ошибки высоты нет.

**Вердикт H4: порог <1% достигнут** — 0.19% по строкам и 0.19% по высоте.

### Классификация расхождений

| Срез | Ячеек | Расхождений | Доля |
|---|---:|---:|---:|
| `width >= maxWordWidth` | 4647 | 0 | 0.00% |
| `width < maxWordWidth` | 9 | 9 | 100% |
| Диагностика на 60 px (вне `minPx`) | 776 | 232 | 29.90% |
| Mono-диагностика (все ширины) | 6730 | 0 | 0.00% |

Все 9 продуктовых расхождений — одна и та же строка `errors` на ширине 90 px:

> `Единица измерения 'упак' не поддерживается`

Слово «поддерживается» в Inter 400 11px занимает **90.84 px**, а ширина
контента — 90 px. CSS с `overflow-wrap: normal` оставляет слово в одной
переполненной строке (4 строки), `pretext` рвёт его по графемам
(`overflow-wrap: break-word`, как в README пакета) и показывает 5 строк.
На 60 px причина та же: 232 расхождения из 776 ячеек — это подмножество
257 ячеек, где самое длинное слово шире строки (25 совпали: слишком широкое
слово не добавило строку). Как только слово помещается, расхождение
**нулевое** (4647 продуктовых и 519 узких ячеек, включая дефисные `ALS-…` и
`ZU2.0-5.5`).

Других причин нет: шрифт загружен (проверяется до `prepare()`), DPR = 1,
`letter-spacing` = normal, `word-break` = normal; mono-колонки на дефисах
совпали с браузером во всех 6730 ячейках. Модель не «плывёт» — расходится
только политика переноса слишком широкого слова.

### Что это значит для модели

1. `pretext` точен, пока `usableWidth >= maxWordWidth` для каждой строки.
   Это условие и нужно сделать инвариантом оптимизатора: минимальная ширина
   колонки — не константа `minPx`, а `max(minPx, max(maxWordWidth))` по листу
   (+ `CELL_PADDING_PX`). Тогда H4 выполняется с запасом.
2. У `errors` статический `minPx = 90` на 0.84 px уже самого широкого слова
   синтетики. Достаточно 92 px — или честный `maxWordWidth` из листа.
3. Если хочется разрешить слова шире колонки, CSS обязан быть
   `overflow-wrap: break-word` / `anywhere`, иначе `pretext` завышает строки.
   Менять модель под `overflow-wrap: normal` не нужно: она права для
   `break-word`, а продукт просто не даёт таких ширин.
4. Текущий продуктовый CSS ещё расходится с проверенным контрактом:
   `source_name` обрезается (`truncate`, одна строка), у `errors` —
   `leading-snug` и `font-medium`. Стенд проверяет контракт исследования
   (`wrap`, `line-height: 20px`, вес 400). Если #483 оставит текущие классы,
   высота `source_name` модели не подчиняется, а вес 500 у `errors` может
   увеличить `maxWordWidth`. Это отдельный риск интеграции.
5. Не проверялись: зум/DPR ≠ 1 и системный fallback-шрифт. Стенд фиксирует
   DPR = 1 и именованные WOFF2; для продукта это условие нужно сохранить
   (не подменять семейство и не мерить до `document.fonts.ready`).

## Рантайм-замер (#483): гейт §15 не пройден

Отдельная страница `runtime.html` (`runtime.spec.mjs`) меряет не точность, а
**стоимость** расчёта ширин рантайм-вариантом — ровно тот путь, который
предлагалось поставить в продукт: `prepareSheet` всех ячеек → `search` с
`pillsMaxTruncatedShare` = текущей продуктовой доле на этой ширине. Условия —
из протокола #483: 500 строк × 11 колонок, seed 1, профили `realistic` и
`long-tail`, ширины 1180/1400/1500/1600/1920, `λ = 0`, продуктовая политика
ячеек (`source_name` — `truncate`, `errors` — перенос), CPU throttling 4×
через CDP, DPR = 1, 9 повторов.

Две детали протокола, без которых число врёт:

- **`pretext.clearCache()` перед каждым повтором.** `pretext` кэширует ширины
  сегментов (canvas → (сегмент, шрифт)). Без сброса повторы меряют попадание
  в кэш: медиана падает до ~138 мс вместо ~190–220 мс, хотя продукт платит
  полную цену один раз.
- **Диагностика — отдельным проходом.** Разбивка `prepare` по классам колонок
  и `canvas.measureText` аллоцируют тысячи строк; в общем цикле их GC попадал
  в соседнюю конфигурацию.

### Результат (CPU 4×)

| Фаза | Медиана | p95 | max |
|---|---:|---:|---:|
| `prepare` (5000 ячеек) | 195.2 мс | 261.31 мс | 520.7 мс |
| `search` (включая `buildCostModel`) | 26.05 мс | 43.54 мс | 57.4 мс |
| **Итого** | **219.6 мс** | **296.86 мс** | **573.4 мс** |

Холодный прогон (первый, без прогрева JIT — то, что продукт платит на первом
листе): **573.4 мс**. По конфигурациям медиана «итого» — 166–218 мс на
`realistic` и 219–281 мс на `long-tail`; все ширины далеки от 100 мс.

**Вердикт §15: не пройден** — 219.6 мс медианы и 573.4 мс холодного прогона
против порога 100 мс. `frontend/` по условию тикета не трогался.

Для сверки: тот же замер без throttling (`KTM_RUNTIME_THROTTLE=1`) — медиана
31.55 мс, p95 46.3 мс, холодный 79 мс, то есть порог проходится, но это не
условия гейта: на слабом CPU рантайм стоит в ~4–7 раз дороже.

### Куда уходит время (диагностика, CPU 4×)

| Часть | Медиана по конфигурациям |
|---|---:|
| `prepare` однострочных колонок (9 колонок × 500 ячеек, `pretext`) | 121.4–195.3 мс |
| То же через один `canvas.measureText` на ячейку | 71.6–118.7 мс |
| `prepare` переносимой колонки (`errors`, 500 ячеек) | 4.0–26.2 мс |
| `buildCostModel` | 9.7–34.7 мс |

`prepare` — это ~89% времени, и почти всё — однострочные колонки, которым
`pretext` не нужен: им требуется только натуральная ширина. Поэтому варианты
для #485:

1. **Оставить текущий фикс** по §15.3: ни рантайм (этот замер), ни оффлайн-вектор
   (#487: +20% высоты) порог не проходят.
2. **Сузить подготовку до переносимых колонок.** При `λ = 0` натуральная
   ширина однострочной колонки влияет только на статистику обрезки, но не на
   `cost`, то есть не на выбор ширин: её можно не мерить `pretext` вовсе.
   Оценка по частям: `prepare` переносимых + `search` дают **21–63 мс** на 4×.
   Это уже другой протокол гейта: он требует повторного замера полного
   варианта и проверки H4 на фактическом CSS (в т.ч. вес 500 у «Ошибок»),
   поэтому решение — за #485, а не за этим замером.

Воспроизвести: `npm --prefix research/column-widths run browser:test` (оба
стенда) или `npx playwright test --config browser/playwright.config.mjs
runtime.spec.mjs` из `research/column-widths`. Сырой JSON — `results/runtime.json`;
без throttling — `results/runtime-throttle-1x.json`. Спека не падает на
медленном результате (это решение #485), но падает на сломанном замере:
шрифт не загружен, DPR ≠ 1, нарушен `minPx`.

## Воспроизводимость

Одинаковые seed (1), ширины, шрифты и версия Chromium дают одинаковые
счётчики; повторный прогон меняет только `meta.startedAt`.
