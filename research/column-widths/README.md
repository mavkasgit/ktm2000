# Research: ширины колонок таблиц

Исследовательский стенд для спеки
[`docs/specs/preview-column-widths.md`](../../docs/specs/preview-column-widths.md)
(эпик [#475](https://github.com/mavkasgit/ktm2000/issues/475)).

Здесь нет продуктового кода: только синтетика, измерители, оптимизаторы и бенч.
Результат исследования — решение, какой алгоритм и какие константы брать в
`ImportRemaindersDialog`.

## Профили и калибровка

`lib/generator.mjs` строит лист по seed: один и тот же seed даёт одинаковые
данные, разные профили — разные стресс-условия. Измеренные перцентили длин
лежат в `CALIBRATION`, тесты сверяются с ними, а не с точной
последовательностью PRNG.

| Профиль | Что моделирует | Границы |
|---|---|---|
| `realistic` | обычный ОСВ | наименования p50/p90/p99 ≈ 12/23/45 (измерено 12/25,5/46,8), артикулы 7/8/12, ошибки p50/p90/p99 ≈ 33/53/73 |
| `long-tail` | тяжёлый хвост наименований, p50/p90/p99 ≈ 3× реалистичных | стресс, а не калибровка |
| `outlier` | ровно один выброс на текстовую колонку и одна строка с 6 пилюлями | `OUTLIER_TEXT_MIN_LENGTH = 100`, `OUTLIER_PILL_COUNT = 6` |
| `all-short` | короткие наименования и ошибки | всё ≤ `ALL_SHORT_MAX_LENGTH = 25` |
| `mono` | длинные артикулы без пробелов | 12–16 символов, без whitespace |
| `mixed` | латиница и кириллица в одном листе | наименования около реалистичных |
| `empty` | пустые значения и пустые пилюли | ~30 % пустых строк, ~20 % пустых `operations` |

Источник калибровки — выборка без персональных данных:
`docs/catalog/ktm-profile-register.csv` (216 наименований и артикулов
прод-каталога, снимок 2026-11-26) и тексты ошибок предпросмотра из
`backend/app/stock/import_service.py` / `import_1c_osv.py` (14 сообщений).
Перцентили ошибок считаются только по непустым ячейкам: пустая ячейка
встречается чаще ошибки и о длине текста ничего не говорит.

5000 строк на 12 колонках генерируются примерно за 15–20 мс; тест держит
потолок 1 с и 128 МБ на лист.

## Как добавить профиль

1. Добавить имя в `PROFILES` (`lib/generator.mjs`) — тест на число профилей и
   цикл детерминизма подхватят его автоматически.
2. Задать правило в `makeValue` / `makeError` / `makePills`: профиль должен
   отличаться от `realistic` измеримым признаком, а не только seed'ом.
3. Если признак — граница (длина, число пилюль), вынести её в экспортируемую
   константу рядом с `ALL_SHORT_MAX_LENGTH` и проверять в тесте той же
   константой, без дублирования литерала.
4. Добавить в `test/generator.test.mjs` проверку признака и отличия от
   соседних профилей; обновить таблицу выше.
5. `npm test --prefix research/column-widths` — и при желании
   `node research/column-widths/bench.mjs --quick`.

## Запуск

```bash
npm ci --prefix research/column-widths  # @chenglou/pretext, vite, @playwright/test
node research/column-widths/bench.mjs                 # полный прогон, ~80 с (до ~110 под нагрузкой)
node research/column-widths/bench.mjs --quick         # сжатая матрица, ~2 с
node research/column-widths/bench.mjs --measurer=pretext
node research/column-widths/bench.mjs --seeds=3
node research/column-widths/bench.mjs --only=product  # matrix|oracle|product|sweep|stability|robust|offline|all
node research/column-widths/bench.mjs --only=stability,robust  # только #482
node research/column-widths/bench.mjs --only=offline   # только оффлайн-доли #487
node research/column-widths/bench.mjs --lambda=40     # λ свипа; основной всегда 0
npm test --prefix research/column-widths
npm --prefix research/column-widths run browser:test  # H4: pretext против DOM
```

| Флаг | Действие |
|---|---|
| `--quick` | 2–3 профиля, 100/1000 строк, 2 ширины, 6/12 колонок, 1 seed; все секции за ~1–2 с |
| `--measurer=pretext` | движок текста вместо `greedy` (в Node через `OffscreenCanvas`) |
| `--seeds=N` | число seed'ов (полный прогон — 2, `--quick` — 1) |
| `--only=…` | `matrix`, `oracle`, `product`, `sweep`, `stability`, `robust`, `offline` или `all`; можно через запятую (`sensitivity` — старое имя `sweep`) |
| `--lambda=N` | λ свипа обрезки, px (по умолчанию 20); основной прогон всегда `λ = 0` |

Результаты пишутся в `results/bench.json` и `results/report.md`; каталог
`results/` не коммитится — итоговый отчёт исследования живёт в `docs/research/`.

## Бенч-харнесс (#481)

`bench.mjs` — воспроизводимое доказательство, а не «на глаз». **Основной
сценарий — полный текст: `clamp = ∞`, `λ = 0`.** Обрезка — не условие задачи,
а отдельная политика; её цена измеряется свипом. Полный прогон состоит из
шести секций (`--only`):

| Секция | Форма полного прогона | Что доказывает |
|---|---|---|
| `matrix` | 7 профилей × {100,1000,5000} × {1180,1500,1920} × {6,12,20} × seed {1,2} = **378** | сравнение оптимизаторов на широкой сетке при полном тексте |
| `product` | те же профили/строки/ширины × **11 колонок** × seed {1,2} = **126** | продуктовый срез `ImportRemaindersDialog` + сравнение с текущей политикой |
| `oracle` | 60 строк × 7 профилей × 3 ширины × {6,11,12} × seed {1,2} = **126** | точный эталон, gap для H1 при `clamp = ∞` |
| `sweep` | 7 профилей × 3 ширины × clamp {∞,6,4,3,2} × seed 1 = **105** | Парето «высота против потерянного текста» при `λ = 20` |
| `stability` | 7 профилей × W' ∈ {1180,1400,1600,1920} при W0 = 1500 = **28** | матрица сожалений: доли с W0 против оптимума на W' (#482) |
| `robust` | 7 профилей × те же 4 ширины = **28 сценариев** | один робастный вектор долей и его gap к оптимуму (#482, #487) |
| `offline` | 7 профилей × W ∈ {1180,1400,1500,1600,1920} × seed {1,2} = **70** | зашитый вектор #482 и 2–3 бакета против текущих долей; порог §15 (#487) |

Матрица и продуктовый срез идут отдельными прогонами: 11 колонок — продуктовая
конфигурация, а не ещё одно значение стресс-матрицы 6/12/20. Оптимизатор
подбирает ширины по ≤500 строкам, метрики считаются по всему листу. 20 колонок
остаются стрессом матрицы, но не входят в оракул: 12 гибких колонок превышают
бюджет полного перебора, эталон пришлось бы прореживать — и gap к нему перестал
бы быть честным.

**Колонки и `clamp`.** `lib/columns.mjs` объявляет политику (`clamp: 2/3` для
текущего продукта), а бенч клонирует набор: `mainColumns()` ставит `clamp: null`
у всех переносимых колонок, `clampColumns(count, k)` — потолок свипа,
`currentProductColumns()` — текущий продукт (`truncate` у «Наименования», полный
перенос у «Ошибок»). `MAX_LINES = 64` в `lib/curves.mjs` — техническая защита
перебора; в основном прогоне на синтетике не достигается.

**Метрики** каждой конфигурации: суммарная/средняя/p95/max высота строки, доли
строк с ≥2/≥3/≥4 строками, распределение высот (40/60/80/≥100 px), доля
обрезанных ячеек, время, число побед. Для продуктового среза — `cost` с `λ=0`
(то есть высота) и нормализация на 1000 строк, а также три политики: текущий
продукт, baseline-доли с полным текстом и `search` с полным текстом.

**Гипотезы.** H1 выводится из оракула в основном сценарии; H2 (500/5000 по
высоте) и H3 (доли при W 1180–1920) — отдельные проверки на полном листе; H4 —
только из `results/browser.json` (`browser:test`, #479). Если браузерного JSON
нет, H4 печатается как «см. browser:test» и не подменяется согласием
`pretext` ↔ `greedy` (оно остаётся отдельной диагностикой модели).

**Детерминизм.** Одинаковый seed даёт одинаковые ширины, высоты, `cost` и доли;
время — единственное, что меняется. Это фиксирует `test/bench.test.mjs`
(`runConfig` дважды, `aggregate` без таймингов, режим без clamp и свип).
Ручная проверка: два `--quick`-прогона с одинаковыми флагами дают одинаковый
`bench.json` после удаления `ms` и `meta.runtimeMs`.

**JSON.** `results/bench.json` содержит `meta` (основной сценарий и λ свипа),
`matrix.configs`, `product.configs` + `product.policies`, `oracle.cases`,
`sweep.cases`, `stability` (матрица сожалений), `robust` (вектор, доли по
каждой ширине, gap по сценариям), `offline` (зашитый вектор, бакеты, все
конфигурации W × профиль × seed, проверки границ, `decision` по §15),
`decision` (порог #482), `virtualization`, `sampleStability`,
`widthStability`, `h4` и `hypotheses`. В каждой конфигурации
лежат ширины всех колонок по каждому оптимизатору, поэтому любой вывод отчёта
можно перепроверить без повторного прогона. `results/report.md` — черновик
отчёта для `docs/research/` (#485): матрица, распределение высот, продуктовый
срез и политики, Парето свипа, сожаления и робастный вектор, оффлайн-доли,
виртуализация, H1–H4, ограничения.

## Измерители

У всех трёх реализаций один интерфейс, поэтому оптимизатор не знает, каким
движком считается строка:

```js
const prepared = measurer.prepare(text, font); // font: "sans" | "mono"
measurer.naturalWidth(prepared);               // ширина в одну строку
measurer.maxWordWidth(prepared);               // самый широкий неразрывный кусок
measurer.lineCount(prepared, usableWidth);     // число строк при ширине
```

| Измеритель | `role` | Модель |
|---|---|---|
| `greedy` | `primary`, дефолт бенча | табличные метрики 11px + жадный перенос по пробелам (`overflow-wrap: normal`) |
| `ceil` | `baseline` | линейное `ceil(naturalWidth / usable)`, только точка отсчёта в отчёте |
| `pretext` | `primary` | `@chenglou/pretext`: `prepareWithSegments` + `measureLineStats` + `measureNaturalWidth`; перенос по правилам браузера, включая дефис |

`ceil` не попадает в финальное решение: `--measurer` по умолчанию `greedy`, а
`role: "baseline"` помечает его явно (тест `ceil помечен baseline и не
является дефолтом`).

**Шрифты.** Строка canvas-шрифта строится только через `cssFont()`:
`11px "Inter"` (`sans`) и `11px "JetBrains Mono"` (`mono`). Это те же семейства
и размер, что в CSS предпросмотра (`text-[11px]`); менять размер нужно в
`FONT_PX`, иначе модель и DOM разойдутся.

**Node без DOM.** pretext на этапе `prepare()` требует Canvas 2D:
`new OffscreenCanvas(1, 1).getContext("2d")`, `context.font`, `context.measureText`.
`lib/offscreen-canvas.mjs` ставит в `globalThis` минимальный полифилл с этим
контрактом:

- `getContext("2d")` возвращает один и тот же контекст на канвас;
- `context.font` — строковое свойство, читается обратно (pretext так проверяет,
  что контекст принял шрифт);
- `context.measureText(text).width` — ширина из таблицы 11px (`text.mjs`);
- `context.letterSpacing` намеренно отсутствует — pretext видит, что контекст
  не умеет letter-spacing, и не идёт по ветке letter-spaced shaping.

**Согласие с greedy.** На тексте без дефисов и при ширине не уже самого
длинного слова `pretext` и `greedy` дают одинаковое число строк (тест
`pretext и greedy согласны на синтетике без переносов по дефису`). Где модели
расходятся, это записано отдельно:

- pretext переносит после дефиса/soft hyphen (как браузер), greedy — нет:
  `maxWordWidth` у pretext считается по сегментам и на `AL-6060` меньше, а
  строк при узкой колонке — меньше (тест `граница модели: pretext переносит по
  дефису, greedy — нет`);
- при ширине уже самого длинного слова pretext делает аварийный перенос внутри
  слова (`overflow-wrap: break-word`), greedy оставляет слово в одной
  переполненной строке.

## Оптимизаторы ширин

Все оптимизаторы получают один бюджет `W` (контент минус 68 px служебных) и
одну модель колонок. **Фиксированные колонки** (числа, контролы, mono) стоят
на продуктовых долях у всех алгоритмов — включая `auto`, иначе он получал бы
лишние пиксели, отнимая ширину у контролов, и сравнение `cost` было бы нечестным.

### Кэш кривых (`lib/curves.mjs`)

Число строк ячейки — ступенчатая функция ширины. Для каждой ячейки один раз
находятся пороги `b1..b_clamp` (минимальная полезная ширина, при которой строк
не больше `k`) бинарным поиском по `lineCount`; дальше любая ширина считается
без измерителя:

```
lines(u) = min(clamp, 1 + #{k : b_k > u})     trunc(u) = u < b_clamp
```

Сетка кандидатов колонки — объединение порогов всех строк плюс `min`,
обрезанное `maxShare` и бюджетом соседей. Кандидат, у которого вектор
`(lines, trunc)` совпадает с более узким, доминируется (та же стоимость,
больше пикселей) и выбрасывается. После дедупликации перебор по сетке
эквивалентен перебору по всем порогам — на этом стоит оракул.

`costOf(indices)` повторяет `evaluate` бит-в-бит на подвыборке (это проверяет
тест) и стоит O(строки × гибкие колонки) чтений массива: шаг поиска не
пересчитывает текст. Для перебора кандидатов одной колонки максимум по
остальным считается один раз (`costOfColumnCandidates`), поэтому полный
перебор порогов колонки стоит O(строки) на кандидата, а не
O(строки × колонки).

Время на 5000 строк (полный лист, измеритель `greedy`, 11px): `search` —
8–18 мс на 11 колонках и до ~60 мс на стресс-конфигурации с 20 колонками
(12 гибких). Мягкий потолок теста — 150 мс, цель тикета — 50 мс на 5000×11.

### Алгоритмы

| Алгоритм | Идея | Что кэшируется | Константы |
|---|---|---|---|
| `baseline` | текущие продуктовые доли | — | доли `baselineShare` (сумма 95) |
| `auto` | min/max-content только гибких колонок, линейный рост до бюджета | `maxWordWidth`, p99 | `maxShare` |
| `p90` | пропорционально p90 натуральной ширины | p50/p90/p99 | `maxShare`, `maxWordWidth` |
| `narrowing` | Marriott et al.: от широкой раскладки сужаем колонку с минимальным приростом `cost` на пиксель, шаг — следующий порог; остаток тратит жадный рост | сетка порогов + `(lines, trunc)` | `maxCandidates=40` |
| `breakpoints` | рост от минимумов: берём **все** кандидаты выше текущего, а не только следующий порог (иначе колонка застревает на ступени), по лучшему `gain/px` | то же | `maxCandidates=40` |
| `search` | то же + локальный обмен бюджета: колонку сужаем до порога `j`, запрещаем ей вернуться (`ceilings`) и снова растим — освобождённые пиксели уходят другим | то же | `maxCandidates=40`, `rounds=4`, `downgrades=все нижние пороги` |
| `oracle` | полный перебор сетки порогов гибких колонок с нижней границей по `cost` и бюджетом | все пороги без прореживания | строк ≤60, ≤2M комбинаций, иначе сетка прореживается (`thinned`) |

Общие константы поиска (`lib/curves.mjs`): `DEFAULT_MAX_CANDIDATES = 40`,
`DEFAULT_SAMPLE_ROWS = 500`. Подвыборка детерминированная: в неё гарантированно
попадают самые длинные строки (по одной на гибкую колонку), остальное —
равномерная сетка по листу. Перекашивать долю подвыборки в хвост нельзя:
`cost` чувствителен к доле обрезанных ячеек, и на `long-tail` хвост в 60%
строк давал +7% cost против полного листа. Метрики в бенче всегда считаются
на **полном** листе: поиск видит ≤500 строк, `cost` — все. Влияние самой
подвыборки (200/500/1000 из 5000, 11 колонок) в основном сценарии: |Δвысоты|
≤0.26% на `long-tail`, 0.12% на `realistic`, 0.07% на `outlier` (H2
подтверждена; подробности и порог переноса — раздел #482 ниже).

### Инварианты

1. Сумма ширин = бюджет; если минимумы не влезают — честное переполнение
   (сумма равна сумме минимумов), а не тихое нарушение.
2. `min_i ≤ w_i ≤ maxShare_i · W` для гибких колонок.
3. Минимум текстовой колонки — `max(minPx, maxWordWidth + CELL_PADDING)`
   по всему листу (#479/H4): уже самого широкого слова `pretext` рвёт слово,
   а CSS предпросмотра с `overflow-wrap: normal` — нет, и модель завысила бы
   строки. Для синтетики это поднимает `errors` с 90 до 99 px
   (`«поддерживается»` = 86.9 px в табличных метриках, 90.84 px в браузере),
   `source_name` остаётся на 90. Статический `minPx` не меняется: честный
   минимум зависит от листа, а не от объявления колонки.
4. `baseline` воспроизводит продуктовые доли (тест) и не участвует в
   H1-сравнении как кандидат.

### Результат бенча (#481, основной сценарий)

за ~80 с** (бюджет 5 минут): матрица 378, продуктовый срез 126, оракул 126,
свип 105, `stability` 28, `robust` 28, `offline` 70.

колонок; `clamp = ∞`, `λ = 0`:

|---|---:|---:|---:|
| `auto` | 5.22% | 24.44% | 40/126 |

выходит за 5% только в худшей конфигурации (1.61%), `narrowing` — 5.58%.
Продуктовый срез 11 колонок: `search` — **0.905** `cost`/baseline, средняя

7.5 мс, стресс 20 колонок — до ~68 мс.

**Политики на продуктовом срезе (полный текст против текущего фикса):**

| Политика | Средняя высота строки | Потеря текста | Обрезка пилюль | Рост к текущему фиксу |
|---|---:|---:|---:|---:|
| Текущий продукт (`truncate` наименования, ошибки перенос) | 46.81 | 4.83% | 3.35% | 0% |
| Baseline-доли, полный текст | 48.68 | 0% | 2.48% | **+3.09%** |
| `search`, полный текст | 42.80 | 0% | 6.70% | **−7.06%** |

Текущий фикс не «экономит» высоту: его доли (15/21) перекошены, и оптимальные
ширины при полном тексте дают **меньше** высоты, чем он. Порог §15 (+25%) не
достигается ни в одном варианте; это значит, что отказ от обрезки не обязан
стоить дороже — вопрос в ширинах, а не в `clamp`.

«Потеря текста» — только текстовые колонки (наименование, ошибки): у текущего
продукта это 4.83% обрезанных наименований, у полного текста — ноль. «Обрезка
пилюль» — отдельная политика `nowrap` для «Операций» и mono: подпись остаётся
в `title`, это не скрытый текст. Смешивать эти числа нельзя, поэтому бенч
считает их раздельно.

### Устойчивость к ширине: сожаление переноса и робастный вектор (#482)

Порог записан в тикете до прогона и здесь не меняется: перенос долей с
`W0 = 1500` на `W'` должен стоить ≤3% (средняя и худшая по профилям); робастный
вектор принимается при среднем gap ≤2% и худшем ≤4% и только если он не хуже
переноса с `W0`. Числа ниже — полный прогон; `--quick` урезает профили и ширины
и годится только как дымовой тест, его вердикт решением не является.

**Матрица сожалений.** `search` подбирает доли на `W0`, затем применяет их к
`W'` как проценты (`share × contentWidth(W')`) — это реальное поведение
`table-fixed`. Потеря — против раскладки `search` на самой `W'`; 7 профилей,
1000 строк, seed 1:

| W' | Средняя потеря, % | Худшая потеря, % | Худший профиль | Наруш. `minPx`/`maxShare` |
|---:|---:|---:|---|---:|
| 1180 | −0.02 | 0.58 | `empty` | 13 |
| 1400 | 0.87 | 2.79 | `empty` | 1 |
| 1600 | 0.84 | **4.47** | `empty` | 0 |
| 1920 | 0.56 | 3.36 | `long-tail` | 0 |

Средняя по сетке — 0.56%, худшая — **4.47%** > 3%: порог переноса **не
пройден**. На 1180 проценты ещё и опускаются ниже `minPx` («Операции» 70.7 px,
«Качество» 82.3 px при минимуме 90) — реальная таблица либо ужмёт контрол, либо
получит горизонтальный скролл; это отдельный аргумент против варианта «(а)».

**Робастный вектор.** Один набор долей гибких колонок на все профили и ширины;
поиск — `lib/robust.mjs` (координатный спуск по кэшу порогов, `costAtWidths`),
старт — среднее оптимальных долей, цель — худший gap. Доли от бюджета гибких:

| Колонка | Доля гибкого бюджета | Доля контента при `W0 = 1500` |
|---|---:|---:|
| `source_name` | 38.00% | 18.79% |
| `operations` | 16.58% | 8.19% |
| `errors` | 45.42% | 22.46% |

| W' | Средний gap, % | Худший gap, % | Худший профиль | Средняя потеря (а), % |
|---:|---:|---:|---|---:|
| 1180 | 0.66 | 3.90 | `empty` | −0.02 |
| 1400 | 1.71 | **6.80** | `empty` | 0.87 |
| 1600 | 1.30 | 4.47 | `empty` | 0.84 |
| 1920 | 1.45 | 5.00 | `empty` | 0.56 |

Средний gap — 1.28% (≤2%), худший — **6.80%** > 4%: порог робастного вектора
**не пройден**, и он хуже переноса с `W0` на каждой ширине. Причина честная:
`empty` на 1400–1600 хочет отдать «Операциям» меньше 16.6% бюджета, но на 1180
та же доля уже упирается в `minPx = 90`, а один вектор обязан уважать минимум
на всех ширинах.

**Решение: (в) пересчитывать на ресайзе.** Вариант «(а)» даёт 4.47% > 3%,
вариант «(б)» — 6.80% > 4% и хуже «(а)». Пересчёт остаётся, и #483 обязан
уложить его до первого показа таблицы (спека §15: расчёт ≤100 мс при CPU 4×,
применение — пока идёт запрос и скелетон). Вход для #487 — `robustShares`,
`buildRobustScenario`, `contentSharesFromFlexShares` и `costAtWidths`; вектор
пересобирается по любой сетке профилей/ширин и детерминирован (тест).

**H2 по размерам подвыборки.** Основной сценарий, 11 колонок, 5000 строк,
профили отдельно; худшая Δ высоты по модулю:

| Профиль | N = 200 | N = 500 | N = 1000 |
|---|---:|---:|---:|
| `realistic` | −0.11% | −0.12% | −0.08% |
| `long-tail` | −0.21% | −0.26% | −0.21% |
| `outlier` | −0.06% | −0.07% | −0.07% |

Отрицательная Δ — подвыборка не видит хвост и не раздувает колонки под редкие
длинные строки; по модулю всё ≤0.26%, порог 2% пройден с запасом. H2 остаётся
**подтверждённой**; H3 (Δ долей ≤5 п.п.) по-прежнему **не подтверждена**
(8.79 п.п., `narrowing/long-tail`), но её формулировка заменена порогом
«потеря при переносе ≤3%» — и по нему вариант «(а)» не проходит.

## Оффлайн-доли: запасной исход (#487)

Порог §15: оффлайн-доли зашиваются константой, если рантайм не проходит 100 мс,
но вектор даёт **≥4% суммарной высоты** или **≥1 п.п. обрезки** против текущих
продуктовых долей (15/21) при полном тексте. Это сравнение не с оптимумом на
каждой ширине, а с уже сделанным фиксом; потеря текста и обрезка пилюль
считаются раздельно и не складываются.

Вектор #482 зафиксирован в `lib/offline-shares.mjs` (`OFFLINE_FLEX_SHARES`) и не
пересчитывается от прогона к прогону: 38.00 / 16.58 / 45.42% гибкого бюджета.

38.10 / 16.60 / 45.30% — расхождение ≤0.12 п.п., то есть константа не

### Вход для #483: что зашивать, если рантайм не пройдёт 100 мс

Константы — в `lib/offline-shares.mjs`:

```js
export const OFFLINE_FLEX_SHARES = {
  source_name: 0.38,   // 38.00% гибкого бюджета
  operations:  0.1658, // 16.58%
  errors:      0.4542, // 45.42%
};
```

- Фиксированные колонки остаются на продуктовых долях; бюджет гибких —
  `contentWidth − Σ(round(baselineWidth фиксированных))`.
- Ширина: `w_i = share_i × flexBudget`; в `<colgroup>` — `share_i × flexBudget /
  contentWidth`. При ресайзе доли не меняются, масштабируется только бюджет.
- При `contentWidth` 1432 px (W = 1500) это 18.79 / 8.20 / 22.46% ширины
  контента; полная таблица — `offline.pinned` в `results/bench.json`.
- Бакеты не зашивать: критерий переключения не пройден.
- Если #485 отвергает рост обрезки пилюль, оффлайн-вектор не спасает: чтобы
  удержать пилюли на текущем уровне, «Операциям» нужно ≥40% гибкого бюджета, а
  высота тогда выигрывает лишь 3.58% — оба порога одновременно не достигаются.
  Тогда остаётся текущий фикс либо рантайм-пересчёт с ограничением на пилюли.

## Границы модели

- В Node текст измеряется табличными метриками, а не canvas: сравнивать
  раскладки между собой можно, абсолютные пиксели — только после валидации
  в браузере (отдельный тикет). В браузере тот же `pretext`-адаптер меряет
  настоящим canvas, полифилл не нужен.
- **`letter-spacing`** не моделируется: таблица 11px его не знает, полифилл не
  выставляет `context.letterSpacing`, `greedy`/`ceil` его игнорируют. Если в CSS
  предпросмотра появится `letter-spacing`, его нужно передать в
  `prepare(..., { letterSpacing })` и пересчитать модель — иначе число строк
  занижено.
- **`line-height`** в модель не входит: измеритель возвращает число строк,
  высоту строки задаёт `LINE_HEIGHT_PX = 20` в `columns.mjs`. В продукте
  «Ошибки» — `font-medium leading-snug` (15.125 px при 11 px) и вес 500, поэтому
  модель завышает их вклад (до 8.67 px на строку, где ошибки задают высоту).
  Предсказанную высоту для виртуализации нужно пересчитать в фактический CSS —
  #483. `line-clamp` — потолок строк у потребителя (`clamp` в `columns.mjs`).
  `MAX_LINES = 64` в `lib/curves.mjs` — техническая защита, а не продуктовая
  политика: на синтетике она не достигается.
- **`overflow-wrap`** у моделей разный: `greedy` — `normal` (длинное слово не
  рвётся), `pretext` — `break-word` (рвётся). Для колонки с
  `overflow-wrap: normal` в CSS `maxWordWidth` — нижняя граница ширины, ниже
  которой `pretext` начнёт делить слово и покажет больше строк, чем браузер.
- **Именованный шрифт.** Модель знает только `sans`/`mono`; canvas-строка
  (`11px "Inter"` / `11px "JetBrains Mono"`) важна для браузера, где pretext
  меряет реальный шрифт. Подмена семейства в CSS без правки `FONT_FAMILY`
  делает браузерные числа невалидными.
- **Загрузка веб-шрифта.** В браузере `prepare()` до `document.fonts.ready`
  (или без `font-display`) меряет fallback-шрифт: строки будут другими, хотя
  код не менялся. Синтетика в Node от этого не зависит, поэтому расхождение
  проявляется только на DOM-валидации.
- `Операции` смоделированы как неразрывные пилюли: ширина покупает отсутствие
  обрезки, а не число строк.
- `oracle` перебирает пороги только гибких колонок и только на малых
  инстансах; он эталон для `cost`, а не для продакшена.
