# Хуки git в ktm2000

Дата: 2026-11-03 (#353). Инструмент — `lefthook` (devDependency, Go-бинарник из npm,
работает на Windows без WSL). Конфиг — `lefthook.yml` в корне.

## Главное правило: хук — удобство, а не гейт

Проверка, которая существует только в хуке, не считается существующей: `core.hooksPath`
не наследуется ни клоном, ни worktree, ни переустановкой `node_modules`, а
`--no-verify` стоит одну клавиатуру. Поэтому каждая команда в `lefthook.yml` — это
уже существующий шаг `npm run gate` или шаг CI, только по staged-файлам:

| Хук | Команда | То же самое живёт здесь |
|-----|---------|------------------------|
| `pre-commit` | `node scripts/guard-tree.mjs` | второй дом — `npm run doctor` (строка «своё дерево») |
| `pre-commit` | `ruff check --no-fix {staged_files}` | шаг `ruff` гейта, `ruff.yml` в CI |
| `pre-commit` | `eslint {staged_files}` | шаг `frontend-lint` гейта, `frontend-tests.yml` |
| `pre-commit` | `npm run check:docs` | шаг `docs-links` гейта, `docs.yml` |
| `pre-push` | `npm run gate:fast` | `npm run gate` целиком, все CI-workflow |

Единственное исключение в таблице — `guard-tree` (#354). У него нет гейт-эквивалента,
потому что вопрос «не чужое ли дерево трогает этот коммит» ставится только в момент
коммита: вне него нечего сверять. Чтобы исключение не стало дырой, та же проверка
доступна командой `npm run guard:tree` и строкой в `npm run doctor` — то есть её
можно выполнить, не полагаясь на хук.

`npm run gate` вызывается независимо от того, установлены хуки или нет: он ничего не
знает про lefthook и не становится короче без хуков. Это проверяется текстом —
`grep -n lefthook scripts/gate.mjs` пуст.

## Установка и проверка

```bash
npm run hooks:install   # lefthook install: пишет shim'ы в каталог хуков
npm run hooks:check     # что объявлено, что реально установлено, --json
```

`hooks:check` смотрит на файлы, а не на `core.hooksPath`: значение по умолчанию
(`.git/hooks`) выглядит «заданным», хотя в каталоге лежат одни `*.sample` и до
коммита не запускается ничего. `npm run doctor` печатает это как информационную
строку `хуки до коммита: пусто` — отсутствие хуков не является NO-GO.

## Что хук не делает намеренно

- **Не правит файлы.** `stage_fixed` выключен, `--fix` в конфиге нет. Хук, который
  переписывает staged-файлы, создаёт коммит, которого никто не писал, и в чужом
  рабочем дереве это выглядит как порча. Правки — только руками автора или
  отдельной командой `npm run gate -- --fix` (её нет: см. предыдущий абзац).
- **Не запускает дорогое.** Backend-тесты, e2e, типы всего проекта — это `pre-push`
  и CI, не `pre-commit`. Замер на этой машине: staged-`.py` — 0.1 с (2 с вместе с
  пуском lefthook), 12 staged-файлов `frontend/src/**` — 5.3 с.
- **Не проверяет message commit'а.** Conventional commits остаются соглашением
  (стандарт 4 в `AGENTS.md`); автоматизация была бы отдельным тикетом.

## Как пропустить и когда это запрещено

Пропуск: `git commit --no-verify` или `LEFTHOOK=0 git commit …` (второе точнее:
`--no-verify` глушит все хуки разом, `LEFTHOOK=0` — только lefthook).

Разрешено, когда падение хука объясняется самой работой, а не её качеством:

- интерактивная часть бисекции/эксперимента, где «красное» и есть предмет;
- восстановление истории (`cherry-pick` чужого коммита, где ругается `check:docs`
  на чужие строки);
- инцидент на проде, когда цена ожидания — время простоя.

Запрещено, когда пропуск прячет найденную проблему: после красного хука коммит либо
чинится, либо остаётся незакоммиченным. Отдельный случай — **агент не имеет права
пропускать хук, чтобы «обойти» конфликт с чужой правкой**: правило «чужие правки
не трогаем» из `AGENTS.md` сильнее хука, и красный хук на чужом staged-файле — это
сигнал остановиться и спросить, а не сигнал жать `--no-verify`.

Каждый пропуск должен быть объясним: если он попал в историю (коммит без проверки),
в описании PR или в комментарии тикета обязана быть одна строка — что и почему.
