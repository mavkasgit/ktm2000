# Спека: импорт остатков из 1С (ОСВ)

Источник решений: гриллинг 2026-11-25, файл
`excel/Шаблон импорта остатков.xlsx` (листы `Импорт остатков`, `Склад сырой`,
`Дробь`; каталог `excel/` в `.gitignore`, в репозиторий файл не попадает).

Термины: [`GLOSSARY.md`](../GLOSSARY.md) — «Остатки из 1С», «Код номенклатуры 1С».
Решение: ADR-0077 (тикет документации).

## 1. Проблема

Импорт остатков умеет только ручной шаблон
`Артикул | Кол-во | Статус качества | Операции | Участок | Коммент. | Длина`
(`backend/app/stock/import_service.py::parse_remainders_excel`). Бухгалтерия
присылает остатки выгрузкой 1С — оборотно-сальдовой ведомостью (ОСВ): строки
вида `Код | Наименование ТМЦ | Ед. изм. | … | Конечное сальдо / Количество`.
Кода артикула в этой выгрузке нет; артикул иногда стоит в скобках внутри
наименования (`(ЮП-2616)`), иногда отсутствует. Количество — в метрах, а склад
KTM ведёт учёт в штуках.

Нужен режим «Остатки из 1С»: разобрать ОСВ, привязать строки к артикулам по
коду номенклатуры 1С, показать наименование из БД и пересчитать метры в штуки.

## 2. Факты по данным заказчика

| Факт | Значение |
|---|---|
| «Склад сырой» | 1096 строк с кодом; 517 с ненулевым остатком; 579 с пустым количеством |
| «Дробь» | 113 строк с кодом; 106 с остатком, все единицы — `м` |
| «Склад сырой»: единицы | `м` 234, `шт` 554, `шт.` 147, `м2` 38, `кг` 49, `рул` 18, прочее |
| Артикул в наименовании | «Дробь» — 95 из 106; «Склад сырой» — 81 из 517 |
| Группы эквивалентов | Уже есть в `Product.aliases`: `033↔ЮП-2630`, `035↔АТ-7121`, `150↔ЮП-3168`, `371↔ЮП-2256`, `3328↔ЮП-2083` и т.д. |
| Длины | У артикула две длины: **сырьевая** (`raw_length_mm`, участвует в расчётах и может быть в наименовании: `2,75`) и **нормальная** (`length_mm`, учёт и операции: `2,7`). `length_mm`: 2700 — 140 строк, 2500 — 28, 3050 — 18, 2750 — 5. Пограничные 2750/3050 — дефект справочника (в учёте 2,75 быть не может), разбирается в приёмке. |
| Без длин | 4 артикула из 216 |
| `Product.code` | У всех 216 артикулов пуст; поле «Уникальный код» (ADR-0012) не трогаем |

Не вся номенклатура 1С есть в справочнике KTM: упаковка, химия, расходники,
инструмент и т.п. — это не артикулы MES. Такие строки показываются ошибкой и
не импортируются; автоматически артикулы не создаются.

## 3. Решения (гриллинг)

1. **Режим определяется автоматически** по заголовкам листа: есть `Код`,
   `Наименование` (или `Наименование ТМЦ`) и группа `Конечное сальдо`.
   Переключателя «обычный/1С» нет.
2. **Все листы**: вкладки по листам (как в импорте плана), тип каждого листа
   определяется при загрузке; кнопка «Импортировать все листы ОСВ» применяет
   все распознанные ОСВ-листы одним действием, история — **батч на лист**.
   `clear_existing` в этом режиме запрещён.
3. **Участок** определяется по складу из шапки листа:
   `Склад сырой`/`Склад сырья` → `RAW_STOCK`,
   `Подготовительный участок`/`Склад подготовки` → `PREP_STOCK`,
   `Склад полуфабриката` → `WIP_STOCK`,
   `Склад готовой продукции` → `FINISHED_STOCK`.
   При неоднозначности или отсутствии — ручной выбор, как сейчас.
4. **Коды номенклатуры 1С** хранятся отдельной таблицей `product_1c_codes`:
   код уникален, у артикула их несколько (`20933`, `22069`, `10926`).
   `Product.code` не трогаем. Заполняются программно при импорте; ручной
   привязки в окне импорта нет — это функция каталога (отдельная задача).
5. **Один артикул на группу алиасов**: любой матч приводится к канону группы
   (`AliasGroups.group_key`, минимальный `product_id`). Если кандидаты в
   наименовании из разных групп — ошибка «неоднозначно».
6. **Длины**: длина из наименования ищется среди `length_mm`/`raw_length_mm`
   артикула и приводится к **нормальной** `length_mm`; если точного совпадения
   нет — ближайшая меньшая `length_mm`. Нет длины в наименовании — `is_primary`
   или единственная; иначе ошибка. Расхождение > 100 мм — предупреждение.
7. **Штуки**: `floor(метры / нормальная_длина)`. `0` штук — ошибка; пустое
   количество — строка пропускается; отрицательное — ошибка.
8. **Единицы**: только `м`/`м.п.`/`п.м.` (метры → штуки) и `шт`/`шт.` (как
   есть). Прочие единицы у найденного артикула — ошибка.
9. **Без артикула** — строка с ошибкой, не скрывается и не создаёт артикул.
10. **Предпросмотр**: колонки `Код 1С | Артикул | Наименование из БД |
    Кол-во, шт | Метры | Длина | …`; код/наименование/метры — показ, без
    серверных фильтров.
11. **История**: код номенклатуры и метры хранятся в строке импорта
    (`stock_import_rows.source_code`, `source_quantity_m`) и видны в детализации
    батча. Складской учёт остаётся в штуках; метры — аудит источника, не
    второй остаток.
12. **Комментарий проводки** — только пометка `Импорт остатков из 1С`, без
    чисел: числа не дублируются, чтобы не было второго источника правды.
13. **Ручной шаблон Excel не меняется.** ADR-0077 и термины — в этой же
    задаче (тикет документации).
14. **Версии до/после обязательны** для любого обновления прод-данных и
    каталога: перед изменением снимается снимок и экспорт, после — второй
    снимок и отчёт об изменениях. Заказчик сравнивает «до/после» и решает,
    всё ли верно; без пары артефактов изменение не считается принятым
    (§15).
15. **Выполненные операции — префикс маршрута из наименования** (#468).
    Колонки «Операции» в ОСВ нет, маркеры закодированы в наименовании:
    цвет словом (`– 02(золото)`) и/или суффиксом `-NN` сразу после артикула
    строки (SKU или его алиаса), пресс — `окно`/`гребенка`, полуфабрикат —
    `ПФ`/`П/ф`. Маршрут собирается тем же профилем `packaging_map_rp`, что у
    плана, но **не сохраняется**: в остаток пишется только префикс операций
    до `ANODIZING` (цвет или ПФ) либо `PRESSING` (только пресс). В префикс
    `ANODIZING` входят все значимые операции этапа, включая упаковку
    (`PACK_SPUNBOND` для П/ф, `PACK_STRETCH` для ГП); префикс «только пресс»
    заканчивается на `PRESSING`. Строка без маркеров получает пустой
    список — «прошёл маршрут, операций не было». Неоднозначность (равная
    длина у разных цветов, слово ≠ суффикс, два пресса, ПФ без цвета,
    маршрут не собрался) — `invalid` с видимой причиной; не угадываем.
    ПФ-строки лежат на «Складе готовой продукции»:
    склады сырья и ГП считаются едиными (решение заказчика 26.11.2026).

## 4. Схема данных

### 4.1. `product_1c_codes`

| Колонка | Тип | Ограничения |
|---|---|---|
| `id` | `BIGINT IDENTITY` | PK |
| `product_id` | `BIGINT` | FK `products.id` `ON DELETE CASCADE`, `NOT NULL`, индекс |
| `code` | `VARCHAR(64)` | `NOT NULL`, `UNIQUE` |
| `source` | `VARCHAR(32)` | `NOT NULL`, default `'1c_osv'` |
| `created_by` | `BIGINT` | FK `users.id`, `NULL` |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL`, `now()` |

Смысл: код номенклатуры 1С — атрибут артикула. Один код принадлежит ровно
одному артикулу; у артикула кодов сколько угодно.

### 4.2. `stock_import_rows` (две колонки)

| Колонка | Тип | Смысл |
|---|---|---|
| `source_code` | `VARCHAR(64) NULL` | код номенклатуры 1С из строки ОСВ |
| `source_quantity_m` | `NUMERIC(18,4) NULL` | метры из «Конечное сальдо / Количество» |

`quantity` остаётся штуками (`NUMERIC(18,4)`). Метры — только для ОСВ; у
ручного шаблона `NULL`.

### 4.3. Модели

- `Product1CCode` — `backend/app/models/product.py` (рядом с `Product`) или
  отдельный `backend/app/models/product_1c_code.py`; реэкспорт в
  `app/models/__init__.py`.
- `StockImportRow` — `backend/app/stock/import_models.py`, новые поля.
- Миграция Alembic: `npm run db:makemigrate -- "product 1c codes + source fields"`.

## 5. Контракты API

### 5.1. `POST /api/stock/import/remainders/sheets`

Multipart `file`. Определяет листы и их тип без полного разбора строк.

```json
{
  "sheets": [
    {
      "index": 1,
      "name": "Склад сырой",
      "kind": "1c_osv",
      "detected_section_id": 1,
      "detected_section_name": "Склад сырья"
    },
    {
      "index": 0,
      "name": "Импорт остатков",
      "kind": "manual_template",
      "detected_section_id": null,
      "detected_section_name": null
    }
  ]
}
```

`kind`: `1c_osv | manual_template | unknown`.

### 5.2. `POST /api/stock/import/remainders/preview`

Существующие параметры. Автоопределение ОСВ по `sheet_index`.

Дополнения ответа:

```json
{
  "source_kind": "1c_osv",
  "detected_section_id": 1,
  "detected_section_name": "Склад сырья",
  "items": [
    {
      "source_code": "20933",
      "source_name": "Кант универсальный 26мм 2,70м (ЮП-2616) алюминий…",
      "source_unit": "м",
      "source_quantity_m": 6391.0,
      "quantity": 2367,
      "product_name": "Кант универсальный 26мм",
      "dimensions_label": "2,7 м"
    }
  ]
}
```

`source_code` участвует в общем поиске (`search`), но не в колоночных фильтрах.

`items` / `items_total` — страница предпросмотра. Диалог импорта запрашивает
лист целиком (`limit` до `PREVIEW_ITEMS_MAX_LIMIT` = 5000, без клиентской
пагинации): оператор должен видеть все строки сразу. Строки сверх потолка
достижимы поиском и фильтрами — они применяются до нарезки страницы. Строки,
разобранные реестром исключений, приходят со `status: "skipped"` и подписью
`skip_reason_label` — «есть в исключениях»; у строки с неподдерживаемой
единицей подпись «нет совпадения», но если её код или имя есть в реестре,
печатается «есть в исключениях»: решение каталога объясняет строку, хотя
единица всё равно не даёт её импортировать. В таблице это одна строка с
префиксом «Пропущено: » (на него опирается e2e и счётчик в шапке). `skip_note`
остаётся уточнением для API и в таблице не печатается: он повторял подпись.
`summary.skipped` — их счётчик.

Ответ несёт `source_token` — контентный адрес загруженного источника
(`sha256`). Повторные запросы предпросмотра передают `source_token` вместо
`file`/`clipboard_text`: смена фильтра, сортировки, чипа категории и листа не
отправляет байты и не перечитывает xlsx. Сервер разбирает лист один раз на
ключ `(токен, sheet_index, row_selection, template_id)`; ключ живёт TTL и
ограничен по памяти (LRU). Неизвестный или протухший токен — `410`, клиент
прозрачно отправляет файл ещё раз. Новый файл даёт другой `sha256`, то есть
новый ключ — инвалидация не нужна.

### 5.3. `POST /api/stock/import/remainders`

Без изменения сигнатуры: клиент передаёт `location_id` = участок листа
(из `detected_section_*` или выбранный вручную), `sheet_index` = лист.
Для ОСВ участок также проставлен в `item.target_section_id`.

Ответ дополняется `batch_id` (уже есть) и счётчиками; для режима «все листы»
клиент вызывает эндпоинт по каждому листу последовательно — **батч на лист**,
как в импорте плана.

### 5.4. История

`GET /api/stock/import/remainders/batches/{id}` — строки дополняются
`source_code` и `source_quantity_m`.

## 6. Разбор листа ОСВ

### 6.1. Определение

- Строка заголовков: ячейки `Код` и `Наименование` (нормализация: lowercase,
  схлопывание пробелов/NBSP).
- Следующая строка — подзаголовки групп (`Количество`, `Стоимость, руб.`).
- Колонка остатка: группа `Конечное сальдо`, подзаголовок `Количество`
  (в файле — та же колонка). Также поддерживать `Остаток на конец`.
- Колонки: `Код`, `Наименование ТМЦ`, `Ед. изм.`, `Конечное сальдо / Количество`.
- Строки с нечисловым/пустым `Код` (итоги, группы) пропускаются.
- Пустое количество — строка пропускается (не ошибка).
- Отрицательное количество — ошибка строки.

### 6.2. Склад → участок

Сканируются первые 25 строк листа (до заголовка) на название склада:

| Признак в ячейке | Код участка |
|---|---|
| `склад сыр`, `склад сырья`, `завод ктм склад сырой` | `RAW_STOCK` |
| `подготовительный участок`, `склад подготовки` | `PREP_STOCK` |
| `склад полуфабриката` | `WIP_STOCK` |
| `склад готовой продукции`, `склад гп` | `FINISHED_STOCK` |

Сначала точное совпадение с `Section.name` (активные складские участки), затем
таблица синонимов. Два разных участка-кандидата → автоопределения нет.

### 6.3. Единицы

Нормализация: lowercase, убрать пробелы и точки.

| Значение | Обработка |
|---|---|
| `м`, `м.п.`, `п.м.`, `мп` | метры → штуки |
| `шт`, `шт.` | штуки как есть |
| прочее (`кг`, `м2`, `л`, `рул`, `упак`, `пар`, `компл`, …) | `skipped/not_mes`, единица — в `skip_note` (решение 26.11.2026) |

## 7. Сопоставление с артикулом

Порядок (первое сработавшее побеждает):

1. **Код номенклатуры 1С** → `product_1c_codes.code`.
2. **Артикул в наименовании**:
   - группы в скобках `(...)`, разбитые по `,` и `/`;
   - токены вида `ЮП-2616`, `ALS-917`, `АТ-7121`, `КП5096`;
   - `#033-00` → `033`, `#150-00` → `150`;
   - каждый кандидат прогоняется через существующий `match_sku_cell`.
   - **Скобки главнее кода поставщика:** если в скобках нашёлся артикул,
     `#NNN-00` вне скобок в разборе не участвует — `#318-00(ЮП-3123)` даёт
     `ЮП-3123`, а не `318`. Иначе строка становилась ложно неоднозначной
     (#467).
   - **Алиас — такое же написание:** алиас, которого нет отдельным SKU,
     узнаётся в наименовании наравне с SKU.
   - **Дефис между буквой и цифрой — оформление:** `ALS1291` и `ALS-1291`
     — один артикул (`sku_loose`).
   - **Исполнение артикула:** если токен не нашёлся, берётся единственный
     артикул с базой `токен-<цифры>` (`ЮП-2464` → `ЮП-2464-1`, 1С пишет
     `ЮП-2464-01`); два артикула на базу — неоднозначность. `-00` — код
     поставщика, а не исполнение.
3. **Точное наименование** (нормализованное равенство `Product.name`) —
   только если артикула в наименовании нет; предупреждение
   «сопоставлено по наименованию».

Правила:

- Все кандидаты одной группы эквивалентов → канон группы
  (`AliasGroups.group_key`).
- Кандидаты из разных групп → ошибка «неоднозначно: …».
- Код уже привязан к артикулу A, а наименование указывает на группу B →
  ошибка «код N привязан к A, в наименовании B»; молча не перепривязывать.
- Код не привязан, артикул найден → после успешного импорта создаётся
  `product_1c_codes(code, product_id)`.
- Ни код, ни артикул, ни точное наименование → ошибка
  «код N не привязан к артикулу, в наименовании артикул не найден».

## 8. Длины и штуки

### 8.1. Длина из наименования

Поддерживаемые формы:

- `2,70м`, `2,7 м`, `2.7m` — число + `м`/`m`;
- `3м` — целое + `м`;
- `L=3,61 м`;
- одиночное `2,7`/`3,0` в конце/середине названия без `м` (сырьё:
  `Кв. труба 10*10 3,0 алюминий`);
- `0,18мм` — не длина (мм), игнорируется;
- размеры `10*10`, `60*32,4` — не длина.

### 8.2. Нормальная длина

Для найденного артикула загружаются все `product_lengths`
(`length_mm`, `raw_length_mm`, `is_primary`).

- Точное совпадение с `length_mm` → эта длина.
- Точное совпадение с `raw_length_mm` → соответствующая `length_mm`.
- Иначе — ошибка «длина 3,0 не совпадает с длинами артикула (2,7)».
  «Ближайшая снизу» не подбирается: 3,0 м и 2,7 м — разные длины, и подмена
  одной другой кредитует склад не тем, что пришло из 1С.
- Длины в наименовании нет:
  - ровно одна `length_mm` → она;
  - несколько, есть `is_primary` → primary;
  - несколько, primary нет → ошибка «в наименовании не указана длина,
    у артикула несколько длин».
  - когда длина взята из карточки, строка получает предупреждение
    «длина взята из карточки: 2,7 м (в наименовании не указана)» — оно
    называет длину, по которой считались штуки (#490).
- Пограничные данные: у 5 артикулов `length_mm=2750` без `raw_length_mm`,
  у 18 — `3050`. Если наименование даёт 2,7/3,0, точного совпадения нет →
  ошибка строки, а не молчаливая подмена. Это дефект справочника
  (2750→2700, 3050→3000), исправление — в приёмке/каталоге.

### 8.3. Штуки

```text
pieces = floor(source_quantity_m / (length_mm / 1000))
```

- `pieces == 0` → ошибка «остаток меньше одной штуки».
- `dimensions = {"length_mm": length_mm}` (нормальная длина).
- `quantity = pieces`; `source_quantity_m` — исходные метры.

Примеры:

| Наименование | Метры | Нормальная длина | Штуки |
|---|---:|---:|---:|
| `Плинтус 100 мм 2,61м` (в БД 2500, raw нет) | 5084,1 | ошибка «2,61 не совпадает с 2,5» | — |
| `Профиль … (ЮП-3098) 2,75м` (в БД 2700, raw 2750) | 5084,1 | 2,7 | 1883 |
| `Уголок 10*10 3,0` (в БД 3000) | 1455 | 3,0 | 485 |
| `Круглая труба 16 мм 2,75` (в БД 2700/2750/3000) | 3453,1 | 2,7 | 1278 |

Если физическая длина отличается от нормальной (как `2,61` у плинтуса),
её объявляют в карточке как `raw_length_mm`; тогда она отображается на свою
нормальную без предупреждений. Угадывать «ближайшую» импорт не должен.

## 9. Мультилистовый режим

- При загрузке файла вызывается `POST /remainders/sheets`; вкладки показывают
  имя листа и тип: `ОСВ 1С` / `шаблон` / `неизвестно`.
- По умолчанию выбран первый лист типа `1c_osv`; если таких нет — первый.
- Предпросмотр — существующий, по выбранной вкладке (кэш по листу, как в
  `ImportWizard` импорта плана). Файл отправляется один раз: первый ответ
  возвращает `source_token`, и смена вкладки/фильтра/сортировки идёт только
  параметрами — сервер разбирает лист один раз (спека §5.2).
- Кнопка «Импортировать все листы ОСВ (N)»:
  1. догрузить предпросмотры всех ОСВ-листов;
  2. последовательно применить каждый лист (свой `location_id` = участок
     листа, свои `sheet_index`, `quality_state_overrides`);
  3. при ошибке листа остановиться и показать, какие листы уже применены;
  4. итог — сводка по листам: лист, участок, импортировано, пропущено,
     ошибки; каждый лист — отдельный батч истории.
- `clear_existing` в режиме «все листы» disabled с объяснением: очистка
  одного склада не должна гасить остатки другого.

## 10. UI

### 10.1. Диалог импорта остатков

- Загрузка: подсказка про ОСВ и ручной шаблон; вкладки листов с типом.
- Предпросмотр: колонки
  `# | Код 1С | Артикул | Наименование | Кол-во, шт | Метры | Длина | Операции | Качество | Участок | Ошибки`.
  `Код 1С`, `Наименование`, `Метры` — без шапки фильтра/сортировки; поиск
  (`search`) ищет и по коду, и по `product_name`.
- Метры печатаются `fmtQtyPrecise` (дробное), штуки — `fmtQty`.
- «Наименование» — из каталога (`product_name`). Если артикул не найден
  (пропущенная строка), серым печатается наименование 1С из файла
  (`source_name`), иначе `—`.
- Участок ОСВ показывается бейджем (как участок из файла); при отсутствии
  автоопределения — `SectionSelect`, как сейчас.
- Таблица показывает весь лист: пагинации в диалоге нет. Пропущенные строки
  реестра исключений по умолчанию **скрыты** — их сотни, и оператор листал их,
  чтобы дойти до рабочих строк. Категория переключается цветными чипами как в
  импорте плана (`FiltersPanel`, `kind: "toggle"`): «Ошибки» (red,
  `summary.invalid`) показывает только `invalid`, «Пропущенные» (amber,
  `summary.skipped`) — только `skipped`; чипы взаимоисключающие, повторный клик
  по активному и «Сбросить» возвращают дефолт (`valid` + `invalid`). Чип виден,
  если счётчик > 0 или категория активна. Фильтрация категории — клиентская:
  лист уже загружен целиком, переключение чипа не шлёт запрос. Бейдж
  «Пропущено: N» в шапке остаётся. В колонке «Ошибки» пропуск — одна строка
  «Пропущено: есть в исключениях» (у неподдерживаемой единицы — «Пропущено: нет
  совпадения»). Выбор статуса `Select` («Все строки / Только ошибки / Только
  пропущенные») удалён.
- Строки рисуются виртуализированным `tbody`
  (`VirtualizedTableBody`, 40 px из `TABLE_ROW_COMPACT`, ADR-0030) с липкой
  шапкой; на время разворота сырых строк (`Развернуть`) таблица рисуется
  обычным `tbody`, потому что детализация выше компактной строки. Качество и
  участок интерактивны только у `valid`; у `skipped`/`invalid` — статичный
  бейдж: импорт их всё равно не применит.
- Кнопка «Импортировать все листы ОСВ (N)» — в предпросмотре, рядом с
  существующими кнопками; при `clear_existing`/ручном листе не показывается.

## 11. Ошибки и предупреждения

| Код/текст | Тип | Когда |
|---|---|---|
| `Отрицательный остаток` | ошибка | количество < 0 |
| `Единица измерения 'кг' не поддерживается` | пропуск `not_mes` | единица не м/шт у найденного артикула; в таблице — «Пропущено: нет совпадения» (или «есть в исключениях», если строка в реестре), подробность в `skip_note` |
| `Код 16944 не привязан к артикулу, в наименовании артикул не найден` | ошибка | нет матча |
| `Код 16944 привязан к ЮП-2616, в наименовании АТ-7121` | ошибка | конфликт кода и группы |
| `Артикул неоднозначен: ALS-1103, ЮП-3773` | ошибка | кандидаты из разных групп |
| `В наименовании не указана длина, у артикула несколько длин` | ошибка | нет длины и нет primary |
| `Длина 2,0 меньше минимальной длины артикула (2,5)` | ошибка | нет нормальной длины ≤ |
| `Остаток меньше одной штуки` | ошибка | floor = 0 |
| `Длина 2,61 приведена к 2,5` | предупреждение | расхождение > 100 мм |
| `Сопоставлено по наименованию` | предупреждение | матч по точному имени |

## 12. Не входит в задачу

- Ручная привязка кодов 1С к артикулам в окне импорта (это каталог).
- Автоматическое создание артикулов из номенклатуры 1С.
- Импорт сразу нескольких файлов.
- Запись в `Product.code`.
- Изменение ручного шаблона Excel.
- Пересчёт/хранение метров в `StockBalance`/`StockTransaction`.
- Правка справочника алиасов (данные) — отдельная задача/приёмка.

## 15. Версии до/после (обязательное правило)

Правило распространяется на **любое** обновление прод-данных и каталога:
импорт остатков, миграцию/бэкфилл, правку каталога, силы/сиды. Без пары
«до/после» изменение не считается принятым.

### 15.1. Артефакты

| Что | До | После |
|---|---|---|
| БД (prod) | ручной бэкап `POST /api/backups` (тип `manual`, не ротируется) | второй ручной бэкап |
| БД (dev/e2e) | `npm run db:snapshot -- dump pre-<label>` | `post-<label>` |
| Каталог | `GET /catalog-import/export-excel` → `final_catalog_before_<label>.xlsx` | `..._after_<label>.xlsx` |
| Массовый импорт | preview-ответ сохранён (`preview_before_<label>.json`) | батч истории + `preview_after` |
| Изменения | — | отчёт: строки `create/update/skip`, поля «было → стало», счётчики |

`<label>` — `#<тикет>-<slug>` (например, `#461-aliases-1c`). Артефакты
складываются в `data/backups/changesets/<label>/` (dev; вне git) и
`<STORAGE_ROOT>/backups/changesets/<label>/` (prod) + `meta.json`:
тикет, автор, время, команды, отпечаток БД/файла, ссылка на батч.

### 15.2. Порядок

1. Снять «до» (БД + экспорт затронутых данных + preview).
2. Применить изменение (миграция/импорт/`apply-excel`).
3. Снять «после» (БД + экспорт + отчёт об изменениях).
4. Приложить пути к тикету; заказчик сравнивает и говорит «ок» или
   «откатываем».
5. Откат: prod — восстановление ручного бэкапа «до»; dev — `db:snapshot
   restore`; импорт остатков — откат батча (LIFO), если он последний;
   каталог — повторное применение файла «до»/точечная правка.

`db:snapshot` против prod **запрещён** (скрипт сам отказывается): там только
ручной бэкап приложения. Бэкап «после» не заменяет «до» — нужны оба, иначе
нечего сравнивать.
