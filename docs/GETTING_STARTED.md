# Getting Started — KTM-2000

Пошаговая установка с нуля. Архитектура → [project-overview.md](project-overview.md).

## Шаг 1. Зависимости Node

```bash
npm run setup
```

## Шаг 2. Виртуальное окружение Python

```bash
cd backend
python -m venv .venv

# Windows PowerShell:
.venv\Scripts\Activate.ps1
# Linux/macOS:
source .venv/bin/activate

pip install --upgrade pip
pip install -r requirements.txt
```

## Шаг 3. Переменные окружения

```bash
cp .env.example .env.dev
```

Порты dev: Postgres `5440`, frontend `5172`, backend `8012`.  
Порты test: Postgres `5441`, frontend `8100`, backend (в контейнере) `8000`.

> Файл `.env` в корне — для MCP-утилит (SSH/SFTP), отдельно от `.env.dev`.

## Шаг 4. Запуск

```bash
npm run dev
```

Автоматически: Postgres в Docker → ожидание готовности → `alembic upgrade head` → backend `:8012` + frontend `:5172`.

- Frontend: [http://localhost:5172](http://localhost:5172)
- Swagger: [http://localhost:8012/docs](http://localhost:8012/docs)

## Шаг 5. Демо-данные (опционально)

```bash
npm run db:seed
```

### Рабочая демо-доска «Участков»

`db:seed` наполняет только справочники. Чтобы на страницах «План» и «Участки»
было что покликать, есть отдельный сид: **два набора планов** на шести
производственных участках.

**Первый план — упаковочный.** Собран из реального `Упаковочный план.xlsx`:
55 позиций реального файла (по одной строке на артикул — в пределах
производственного плана артикул не повторяется; строки зафиксированы в коде как
`PACKING_PLAN_ROWS`, сам xlsx остаётся локальным), плюс 30 строк участков
подготовки с повторяющимися артикулами (`PREP_PLAN_ROWS`), 6 строк пар
анодирования (`ANOD_PAIR_ROWS` — один артикул двумя видами выпуска), 4 строки
парных артикулов (`PAIR_ARTICLE_ROWS`), 12 незакрытых строк
(`PENDING_PLAN_ROWS`) и 2 непарных строки (`UNPAIRED_PAIR_ROWS`).

**Распил — одна позиция, а не две.** Среди незакрытых есть пара строк ЮП-2627:
вход один (100 шт по 2,7 м), выходы разные (0,9 м и 1,8 м). По ADR-0003 группа
строк с объединённой ячейкой входа импортируется **одной** позицией с
несколькими выходами, поэтому в лист вторая строка идёт без входного
количества (в фикстуре — признак `input_continuation`), и баланс материала
сходится точно: 100 × 2,7 = 0,9 × 100 + 1,8 × 100. На пиле у такой позиции одно
задание на вход, дальше по маршруту оно раздваивается по длинам.

**Второй план — подготовительный.** Импортируется по своему шаблону «План
подготовительного участка» (`PREP_STAGE_PLAN_ROWS`, 6 строк): у него другие
колонки (одна длина и одно количество вместо входа и раскроя) и другой
профиль маршрута, поэтому его маршрут заканчивается складом подготовки, а не
отгрузкой.

Оба плана идут доменным путём: импорт → approve → релиз → дневные планы, плюс
прогон маршрута, чтобы задания имели реальные статусы.

```bash
npm run db:seed                       # обязательно первым: справочники, профили и правила
npm run db:seed:packing-demo           # снести оперативку и собрать демо заново
npm run db:seed:packing-demo -- --keep # пересобрать демо поверх текущих данных
```

Демо **не создаёт правил** — оно их использует. Шаблон «План подготовительного
участка», профиль `prep_stage_plan` и его 8 правил живут в сид-файлах
(`app/seeds/import_templates.py`, `route_rule_profiles.py`, `selection_rules.py`) и
заливаются скриптом `npm run db:seed`. Если профиля или шаблона в базе нет, демо
останавливается с ошибкой «Профили маршрута не засеяны» / «Шаблон импорта не
засеян», а не строит маршруты по шаблону-заглушке. `db:seed` идемпотентен, его
можно просто прогнать повторно.

**Что получается на шести участках.** Демо наполняет все производственные доски
завода. Базовые 55 позиций реального «Упаковочного плана» делятся по кругу между
пилой, упаковкой и анодированием. Блок `PREP_PLAN_ROWS` (30 строк, по 10 на
участок) ведёт строки подготовки в сверловку, пресс и дробеструй: у пресса в
блоке обе операции («окно» и «гребёнка»), внутри каждого блока есть
повторяющиеся артикулы — на доске видно несколько заданий одного артикула.
Сколько заданий на участке — решает маршрут позиции, а не круг: спанбонд («П/ф»)
не заходит на пилу и упаковку, а анодирование и дробеструй проходят все
выпущенные позиции обоих планов. Строки второго (подготовительного) плана
останавливаются на участках подготовки: их маршрут заканчивается складом
подготовки, а не отгрузкой.

| Участок | Заданий | В дневных планах |
|---|---|---|
| Дробеструй | 101 | 12 |
| Анодирование | 97 | 12 |
| Пила | 44 | 12 |
| Упаковка | 44 | 12 |
| Сверловка | 24 | 11 |
| Пресс | 23 | 11 |

Дневных планов — 70: по 12 на пиле, упаковке, анодировании и дробеструе, по 11 на
сверловке и прессе (`min(12, незакрытые задания участка)`). Даты за девять дней, у
некоторых дней два плана, поэтому в UI номера «№1» и «№2». Старые планы содержат
отработавшие задания и показывают ненулевой процент, свежие — нулевой. В планы
попадают только незакрытые задания: дневной план не принимает терминальные.

**Не всё в работе.** Из 113 позиций двух планов 101 выпущена и ушла в маршрут
(18 закрыты полностью, 33 выполнены на 60 %, 50 выданы и ждут оператора), а 12
оставлены в незакрытых состояниях: 9 неутверждённых (`draft` — ждут
планировщика) и 3 утверждённые без релиза (ждут запуска). У незакрытых позиций
нет ни задания, ни строки внутреннего плана, поэтому в дневные планы они не
попадают — но маршрут импорт назначает сразу.

Под каждую такую позицию сид кладёт остаток на **складе готовой продукции** тем
же доменным путём, что и форма «Импорт остатков»: позиция с нулевым остатком —
мёртвая строка плана, её нечего взять в работу. Остаток ложится на свой артикул
и свой габарит позиции (баланс ключуется `product + section + dimensions`,
ADR-0001), поэтому после утверждения и релиза такую позицию действительно
можно взять в работу.

Именно неутверждённые позиции видны на экране «План»: он отдаёт
`GET /production-plans/all-positions`, а тот показывает только статусы
`draft`/`invalid`/`valid` — рабочий список планировщика. Выпущенные и
утверждённые позиции оттуда скрыты, поэтому демо из одних выпущенных строк
показывал бы пустую страницу при полной базе.

**Парные артикулы.** Четыре строки `PAIR_ARTICLE_ROWS` — это две реальные пары
(`ЮП-2604`/`ЮП-2616` с нормой 30 и `ЮП-2695`/`ЮП-2878` с нормой 24 на подвес), и ещё две строки той же пары `ЮП-2604`/`ЮП-2616` лежат среди неутверждённых: вторая партия, видная на экране «План» с той же парной нормой.
Пара импортируется **двумя** самостоятельными позициями, а не одной склейкой
`A+B`: утверждаются и идут по маршруту раздельно, но норма «количество на
подвес» у обеих одна и парная, поэтому печатный лист участка сводит их в один
подвес («24×ЮП-2695 + 24×ЮП-2878»), а подвесы считает **один раз на пару**
(`ceil(max(план по строкам) / N)`), а не суммой по артикулам — сумма дала бы
подвес, которого физически нет. Количества обеих сторон пары **равны** (#67:
пара — единая загрузка `N×A + N×B`): 210/210 у первой пары и 240/240 у второй —
подвес заполняется парой целиком, и разные количества означали бы, что одна
сторона в свои подвесы не влезает.

Норму пары берёт только позиция, **пришедшая в паре**: импорт считает пару парой,
если в том же листе есть строка второго компонента на ту же нормальную длину
**соседним номером строки** (так эта пара и записана в файле заказчика: 2616 с
наименованием и 2604 под ней). Пара — факт плана, а не свойство артикула:
одинокая строка артикула пары (базовая `ЮП-2616` на 300 шт в базовом блоке — её
партнёра в демо нет) считается обычной позицией по своей норме (62), и на печати
она стоит своей строкой, а не внутри группы пары. Решение импорта лежит в
payload позиции (`product_pair.resolved`) — его читают и план, и доска, и печать.
Пара заводится сидом в `product_pairs` до импорта — иначе строки импортировались
бы как обычные одиночные артикулы.

**Непарный вариант пары.** Две строки `UNPAIRED_PAIR_ROWS` — те же два артикула
(`ЮП-2604`/`ЮП-2616`) самостоятельными строками со **своими** наименованиями
(«Кант универсальный 29мм» и «Кант универсальный 26мм»), а не одним общим, как
у пары. Так они и записаны в реальном файле: в «Плане март 26 03» строки 10 и 11
— одна пара, где вторая строка приходит с пустой ячейкой наименования, а строки
119–125 — тот же `ЮП-2616`, но уже сам по себе и со своим именем.

Считаются они **своей** нормой подвеса, а не парной, и длина тут ни при чём: обе
строки стоят на той же 2,7 м, что и пара. Непарность выражает ручной override
позиции (`source_payload.quantity_per_hanger` — то же поле, что пишет экран
«План» в поле «Кол-во на подвес»): резолвер ставит его выше пары, поэтому строка
считает сама по себе (60 у `ЮП-2604`, 62 у `ЮП-2616` — авто-расчёт артикула на
этой длине), а парные строки — парной нормой 30. На печати участка это видно
сразу: пара идёт одной группой с одной нормой и одним счётом подвесов
(`30×ЮП-2604 + 30×ЮП-2616`, 7 подвесов), а непарные строки стоят отдельными
строками со своими нормами и своими счётами (4 и 4).

Строки выпущены — задание непарной строки тоже непарное. Количества не совпадают
ни с одной другой строкой этих артикулов: импортный fingerprint наименования не
содержит, и совпадение по SKU, габариту, упаковке и количеству превратило бы
новую строку в дубликат.

Длины строк берутся из каталога (`product_lengths`) как **готовые** длины артикула
(`raw_length_mm IS NULL`): 0,9 / 1,35 / 1,8 / 2,5 / 2,7 / 3,0 м. Заготовка прутка
(2,75, 1,83, 3,05, 2,55) в демо-строки не попадает. На анодировании есть три пары
заданий одного артикула и цвета, отличающиеся видом выпуска (`ГП` → `PACK_STRETCH`
«Стрейч», `П/ф` → `PACK_SPUNBOND` «Спанбонд»): в плане такая пара печатается одной
строкой с разбивкой упаковки — «Спанбонд 348 · Стрейч 200».

Маршруты у позиций свои: имя в колонке «Маршрут» и на карточке содержит вид
выпуска, операции пресса, цвет анодирования и вид упаковки — «ГП - Окно - Чёрный -
Стрейч». Поэтому на доске анодирования в «Операции» стоит цвет позиции, а
упаковка — своей колонкой.

Прогон сносит всю оперативку и собирает заново, поэтому повторный запуск
возвращает демо к исходному виду независимо от того, что в нём нащёлкали.
Каталог артикулов при этом только дополняется (недостающие создаются, длины
дописываются, погашенные реактивируются) — правки каталога не откатываются.

### Снапшот dev-БД

```bash
npm run db:snapshot -- dump demo-packing                     # снять слепок
npm run db:snapshot -- restore demo-packing-20260926-214516  # вернуть слепок
```

Дамп кладётся в `data/backups/snapshots/` (вне git) и снимается `pg_dump` внутри
dev-контейнера. `restore` пересобирает базу целиком, поэтому после него нужен
повторный вход в приложение.

### Защита от прода

И сид, и снапшот отказывают при `ENV=prod`/`production` (в файле `.env.dev`, в
`.env.prod` через `ENV_FILE` или в переменных окружения процесса) — до любой
записи в базу. Прод-конфигурация дополнительно не поднимается вне контейнера
из-за `STORAGE_ROOT`, но это вторая линия, а не защита.
