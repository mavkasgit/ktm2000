# Getting Started — KTM-2000

Пошаговая установка с нуля. Архитектура → [project-overview.md](project-overview.md).

## Шаг 1. Зависимости Node

```bash
npm run setup
```

## Шаг 2. Виртуальное окружение Python

```bash
cd backend
python -m venv .venv

# Windows PowerShell:
.venv\Scripts\Activate.ps1
# Linux/macOS:
source .venv/bin/activate

pip install --upgrade pip
pip install -r requirements.txt
```

## Шаг 3. Переменные окружения

```bash
cp .env.example .env.dev
```

Порты dev: Postgres `5440`, frontend `5172`, backend `8012`.  
Порты test: Postgres `5441`, frontend `8100`, backend (в контейнере) `8000`.

> Файл `.env` в корне — для MCP-утилит (SSH/SFTP), отдельно от `.env.dev`.

## Шаг 4. Запуск

```bash
npm run dev
```

Автоматически: Postgres в Docker → ожидание готовности → `alembic upgrade head` → backend `:8012` + frontend `:5172`.

- Frontend: [http://localhost:5172](http://localhost:5172)
- Swagger: [http://localhost:8012/docs](http://localhost:8012/docs)

## Шаг 5. Демо-данные (опционально)

```bash
npm run db:seed
```

### Рабочая демо-доска «Участков»

`db:seed` наполняет только справочники. Чтобы на странице «Участки» было что
покликать, есть отдельный сид на основе реального упаковочного плана: 55 позиций
реального `Упаковочный план.xlsx` (по одной строке на артикул — в пределах
производственного плана артикул не повторяется; строки зафиксированы в коде как
`PACKING_PLAN_ROWS`, сам xlsx остаётся локальным) плюс 30 строк участков
подготовки с повторяющимися артикулами (`PREP_PLAN_ROWS`) и 6 строк пар
анодирования (`ANOD_PAIR_ROWS` — один артикул двумя видами выпуска), доменный
путь импорт → approve → релиз → дневные планы, плюс прогон маршрута, чтобы
задания имели реальные статусы.

```bash
npm run db:seed:packing-demo           # снести оперативку и собрать демо заново
npm run db:seed:packing-demo -- --keep # пересобрать демо поверх текущих данных
```

**Что получается на шести участках.** Демо наполняет все производственные доски
завода. Базовые 55 позиций реального «Упаковочного плана» делятся по кругу между
пилой, упаковкой и анодированием — эта история не меняется. Второй блок,
`PREP_PLAN_ROWS` (30 строк, по 10 на участок), ведёт строки подготовки в
сверловку, пресс и дробеструй: у пресса в блоке обе операции («окно» и
«гребёнка»), внутри каждого блока есть повторяющиеся артикулы — на доске видно
несколько заданий одного артикула. Сколько заданий на участке — решает маршрут
позиции, а не круг: спанбонд («П/ф») не заходит на пилу и упаковку (поэтому там
39), а анодирование и дробеструй проходят все позиции.

| Участок | Заданий | Ожидают | В работе / частично | Закрыто |
|---|---|---|---|---|
| Дробеструй | 91 | 20 | 10 | 61 |
| Анодирование | 91 | 30 | 37 | 24 |
| Пила | 42 | 18 | 12 | 12 |
| Упаковка | 42 | 30 | 12 | — |
| Пресс | 21 | — | 10 | 11 |
| Сверловка | 20 | — | 10 | 10 |

Дневных планов — 68: по 12 на пиле, упаковке, анодировании и дробеструе, по 10 на
сверловке и прессе (`min(12, незакрытые задания участка)`). Даты за девять дней, у
некоторых дней два плана, поэтому в UI номера «№1» и «№2». Старые планы содержат
отработавшие задания и показывают ненулевой процент, свежие — нулевой. В планы
попадают только незакрытые задания: дневной план не принимает терминальные.

Длины строк берутся из каталога (`product_lengths`) как **готовые** длины артикула
(`raw_length_mm IS NULL`): 0,9 / 1,35 / 1,8 / 2,5 / 2,7 / 3,0 м. Заготовка прутка
(2,75, 1,83, 3,05, 2,55) в демо-строки не попадает. На анодировании есть три пары
заданий одного артикула и цвета, отличающиеся видом выпуска (`ГП` → `PACK_STRETCH`
«Стрейч», `П/ф` → `PACK_SPUNBOND` «Спанбонд»): в плане такая пара печатается одной
строкой с разбивкой упаковки — «Спанбонд 348 · Стрейч 200».

Маршруты у позиций свои: имя в колонке «Маршрут» и на карточке содержит вид
выпуска, операции пресса, цвет анодирования и вид упаковки — «ГП - Окно - Чёрный -
Стрейч». Поэтому на доске анодирования в «Операции» стоит цвет позиции, а
упаковка — своей колонкой.

Прогон сносит всю оперативку и собирает заново, поэтому повторный запуск
возвращает демо к исходному виду независимо от того, что в нём нащёлкали.
Каталог артикулов при этом только дополняется (недостающие создаются, длины
дописываются, погашенные реактивируются) — правки каталога не откатываются.

### Снапшот dev-БД

```bash
npm run db:snapshot -- dump demo-packing                     # снять слепок
npm run db:snapshot -- restore demo-packing-20260926-214516  # вернуть слепок
```

Дамп кладётся в `data/backups/snapshots/` (вне git) и снимается `pg_dump` внутри
dev-контейнера. `restore` пересобирает базу целиком, поэтому после него нужен
повторный вход в приложение.

### Защита от прода

И сид, и снапшот отказывают при `ENV=prod`/`production` (в файле `.env.dev`, в
`.env.prod` через `ENV_FILE` или в переменных окружения процесса) — до любой
записи в базу. Прод-конфигурация дополнительно не поднимается вне контейнера
из-за `STORAGE_ROOT`, но это вторая линия, а не защита.

## Troubleshooting

```bash
npm run devkill       # Остановить серверы на 8012 и 5172
npm run devrestart    # Перезапустить dev-окружение
npm run db:down       # Остановить Postgres
npm run db:up         # Поднять Postgres заново
```
