# Синк каталога KTM → «Экранчик» и dev-стенд

Прод-каталог KTM — источник правды. Скрипт
[`scripts/sync-ekranchik.py`](../scripts/sync-ekranchik.py) доводит до него двух
адресатов: каталог «Экранчика» (`ekranchik-modern/static/ekranchik.db`, SQLite)
и dev-стенд (БД + storage). «Изменилось в проде — поменяли и в dev»: dev по
определению копия прода.

Это **данные**, а не файлы кода: файловый синк-гейт между KTM и HRMS —
отдельный, [`scripts/verify-sync.mjs`](../scripts/verify-sync.mjs).

## Что синхронизируется

### «Экранчик»

Переносится весь каталог: профиль есть — обновляется, профиля нет — создаётся.

| Что | Правило |
|---|---|
| `length` у существующего | должна совпадать с любой нормальной **или** сырьевой длиной KTM (±1 мм). Если не совпала — ставится основная длина KTM (primary → единственная → минимальная) |
| `quantity_per_hanger` у существующего | норма KTM для этой длины (по `hanger_mode`: manual → `manual`, auto → `auto`) |
| новый профиль | создаётся для **активного** артикула KTM, у которого есть длины: `name` — код артикула, `length` — основная длина, `quantity_per_hanger` — норма этой длины |
| `photo_thumb` / `photo_full` | заполняются, только если поле пустое: файл из storage прода копируется в `static/images/<имя>-thumb.jpg` и `static/images/<имя>.jpg` |

Не трогаются: имя существующего профиля (в Экранчике это код, по которому
ищут операторы), заметки (в них связи «Аналог-…»), занятые фото и уже
существующие файлы в `static/images`. Артикулы без длин и неактивные новые
профили не получают — они печатаются в «Пропущено» с причиной. Карточки,
которых нет в KTM, печатаются как расхождение `product` (профиль остаётся
на месте: удаление — не дело синка).

### dev-стенд

Переносится **вся БД** и `products` + `imports` из storage прода: dev — не
третье хранилище правок каталога, а копия прода. Поэтому `--apply` не выбирает
поля, а пересобирает dev-базу из прод-дампа (`pg_dump` прода → `pg_restore` dev,
одна транзакция) и досыпает файлы.

- `products` — фото артикулов: без них карточки и таблицы отдают 404 на
  `/static/products/...`.
- `imports` — исходники Excel: без них история импортов в dev не открывается.
- `backups` прода **не копируются** — у dev своя ротация
  (`STORAGE_ROOT/backups`), чужие дампы в ней путают сроки хранения.

`--check` сравнивает dev с продом по каталогу: отпечаток каждого артикула
(карточка, режим подвеса и нормы из `attributes`, алиасы, длины, фото,
активность), пары A+B по кодам и наличие файлов фото в dev-storage. Планы,
передачи и прочая оперативка в сверке не участвуют — dev для того и нужен,
чтобы на нём работать; при `--apply` они всё равно заменяются прод-данными.

Перед восстановлением скрипт снимает снапшот dev-БД
(`data/backups/snapshots/pre-sync-<дата>.sql`). Вернуть прежнее состояние:

```bash
npm run db:snapshot -- restore pre-sync-20261104-105622
```

Правки каталога, сделанные **в dev**, при синке затираются: источник правды —
прод. Если каталог нужно изменить, его меняют в проде (или в dev, а потом
переносят в прод), но не держат расхождение.

## Запуск

```bash
npm run verify:ekranchik        # проверка: Экранчик + dev, exit 1 при расхождениях
npm run sync:ekranchik          # обновить оба адресата (Экранчик — с бэкапом, dev — со снапшотом)
```

`--check` для Экранчика показывает три вещи: правки полей существующих
профилей, фото, которые можно подставить, и список профилей на создание
(«Будет создано профилей»). `--apply` создаёт их и копирует фото; бэкап
SQLite — `ekranchik.db.bak-<дата-время>` рядом с базой.

Напрямую:

```bash
python scripts/sync-ekranchik.py --check
python scripts/sync-ekranchik.py --apply
python scripts/sync-ekranchik.py --check --json
python scripts/sync-ekranchik.py --apply --scope dev       # только dev-стенд
python scripts/sync-ekranchik.py --apply --scope ekranchik # только SQLite Экранчика
python scripts/sync-ekranchik.py --check --db ../ekranchik-modern/static/ekranchik.db
```

`--scope` (`all` по умолчанию | `ekranchik` | `dev`) задаёт адресата и для
`--check`, и для `--apply`. `--if-enabled` включает проверку только при
`KTM_EKRANCHIK_SYNCGATE=1|true|yes|on` (для автоматики; сейчас ни в `predev`,
ни в `gate` не подключено).

## Окружение

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `EKRANCHIK_DB` | `../ekranchik-modern/static/ekranchik.db` | SQLite Экранчика |
| `KTM_PG_CONTAINER` | `ktm2000-postgres-prod` | прод-контейнер (источник) |
| `KTM_PG_USER` | `ktm2000_user` | пользователь прода |
| `KTM_PG_DB` | `ktm2000_prod` | база прода |
| `KTM_PROD_STORAGE` | `data/storage-prod` | storage прода (фото, импорты) |

Dev-адресат читается из `.env.dev`: `POSTGRES_CONTAINER_NAME`,
`POSTGRES_USER`, `POSTGRES_DB`, `STORAGE_ROOT` (путь относительно `backend/`,
например `../data/storage-dev` — у dev свой корень, ADR-0026).

KTM читается через `docker exec … psql`; запись в SQLite Экранчика — в одной
транзакции после `sqlite3.backup()` (`ekranchik.db.bak-<дата-время>`). Фото
кладутся в `static/images` рядом с `ekranchik.db` (`--db` задаёт и то и другое);
существующие файлы не перезаписываются. Запись в
dev-БД — только при `ENV` из `.env.dev` не `prod`/`production` и только если
dev-контейнер не совпал с прод-контейнером; иначе `--scope dev` отказывает до
любой записи.

## Почему правило длины такое

В KTM длина разделена на нормальную (`product_lengths.length_mm`) и сырьевую
(`raw_length_mm`), а в Экранчике поле одно. Поэтому «совпало» — это совпадение
с любой из них; так мы не переписываем 2,75 → 2,70 у десятков профилей, где
2,75 — это сырьевая длина. Если же в Экранчике длина, которой у артикула KTM
нет вообще (например, старая 3050), она приводится к основной длине KTM.

Норма (`quantity_per_hanger`) всегда берётся из KTM для выбранной длины —
поэтому в Экранчике появляется то же значение, что показывает карточка KTM.

## Почему dev переливается целиком

Точечно копировать «только каталог» в dev нельзя: каталог связан с оперативкой
(строки плана, нормы на подвес, импорты), и половина ссылок после такого
копирования указывала бы в никуда. Прод-дамп целиком — единственный способ
получить консистентную копию, и он же объясняет, почему перед `--apply` dev-БД
снимается снапшотом.
