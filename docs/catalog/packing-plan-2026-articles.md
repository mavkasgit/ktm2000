# Артикулы упаковочной карты-плана РП, 2026

Источник: `01_09_2026_01_Упаковочная_карта_план_РП_xlsx.xls` (только чтение).
Сверка: прод-БД `ktm2000_prod` (только `select`). Первый разбор — 2026-11-05, повторная сверка с БД — 2026-11-06.

Трассировка по строкам — [packing-plan-2026-rows.csv](packing-plan-2026-rows.csv), агрегат по артикулам — [packing-plan-2026-articles.csv](packing-plan-2026-articles.csv).

## Методика

1. **Чтение.** `.xls` через `xlrd` 2.0.2 (pandas в окружении нет). Листы плана: «План <месяц> 26 <ММ>» (11 листов, январь–ноябрь 2026). Лист «памятка по упаковке» исключён.
2. **Заголовок.** Не фиксируется по номеру: на каждом листе ищется первая строка, где есть ячейки «Артикул» и «Наименование». Фактически это строка 5 на десяти листах и строка 4 на листе «План февраль 26 02». Колонки определяются по тексту заголовка, поэтому сдвиги (июнь: 40 колонок с разбивкой по цветам, «Завеска», «резка в размер»; май/март/апрель: «Комментарии» перед датами) не ломают разбор.
3. **Объединённые ячейки.** Учтены `merged_cells` (xlrd `formatting_info=True`): пустая ячейка внутри merge наследует значение верхней левой. Какие поля унаследованы, видно в `extra_json.merged_fields` строкового CSV. Без этого 67 строк остались бы без длины (обрезанные позиции 2,7 → 1,8/0,9 шли второй строкой пары).
4. **Примечание.** Колонка «Примечание» пуста **на всех 11 листах** (проверено по каждой строке). Поэтому в поле `note` попадает «Комментарии», если «Примечание» пусто; источник указан в `extra_json.note_source`.
5. **Артикул.** `article_raw` — как в файле (если у одного нормализованного артикула несколько написаний, они перечислены через ` | `). `article_norm` — верхний регистр, без пробелов, типографские тире приведены к `-`; префиксы (`ЮП`, `АТ`, `ALS`, `КП`, `МС`) не склеиваются. Для сопоставления дополнительно используется ключ без дефисов/точек (`ALS1359` = `ALS-1359`). Ведущие нули сравниваются только для чисто числовых артикулов и только если такой SKU один (`033` ↔ `33`).
6. **Составные артикулы.** Встречаются записи через дробь: `ЮП-3658/1875`, `ЮП-3485/АТ-4893`, `ЮП-3485/4893`, `ЮП-3773/1103`. Матчинг идёт по частям: если все найденные части ведут к одному SKU — `match_type=composite`; если части ведут к разным SKU (дубли в БД) — `composite-multi`, SKU берётся по первой части, а неоднозначность записана в `notes`.
7. **Порядок матчинга:** точный SKU → точный алиас БД → алиас из `docs/catalog/ktm-profile-register.relations.csv` (`relation=alias_of`) → нормализованный SKU (без дефисов), только если ключ однозначен → нормализованный алиас → числовое совпадение с ведущими нулями. Первый сработавший уровень и есть `match_type`.
8. **Операции.** Значения «Пробивка/сверловка» нормализованы: `сверловка/сверло` → «сверло», `пробивка` → «пробивка», `окно`, `гребенка`, `клей`, `рассеиватель`, `без рассеивателя`, `2х сторонний скотч` → «скотч 2-сторонний». Значения через запятую/дробь/плюс разбираются на отдельные операции. Сырое значение — в `extra_json.operation_raw` строкового CSV.
9. **Длины.** Сравнение план (м) ↔ БД (`length_mm / 1000`), допуск 2 мм. `length_missing_in_db` — длины из «Длина, м», которых нет в БД; `length_after_missing_in_db` — длины из «Длина после упак, м» (для распила это ожидаемо: 0,9/1,35/1,8 м в каталоге как хлыст не хранятся).
10. **Распил (`is_cut`).** Ставится, если «Длина после упак, м» отличается от «Длина, м» больше чем на 1 мм, ИЛИ колонка «резка в размер» (июнь) отличается от «Длина, м», ИЛИ в наименовании/комментарии есть слова «распил/резка/отрез/пиление». Пары «было → стало» с частотой — в `cut_pairs`.
11. **Количество.** `total_qty` — сумма «кол-во штук готовой продукции»; если пусто — «кол-во шт. в 2,7»; если пусто — «Кол-во». Для обрезанных строк это штуки готовой продукции (например 110 хлыстов 2,7 м → 330 шт по 0,9 м), поэтому сумма по артикулу — сумма готовых штук по строкам плана, а не закупка сырья.
12. **Расхождение названий.** Названия сравниваются по «ядру»: отбрасываются цвет/анод/матовость, «алюминиевый», длины и слова-обёртки, раскрываются сокращения (`т-обр` → `т-образный`, `внеш.` → `внешний`). Совпадением считается вхождение набора слов одного названия в другое либо пересечение токенов ≥ 0,6. Если в БД вместо названия стоит сам артикул — отдельное значение `нет названия в БД`. Это эвристика, поэтому в разделе «Расхождения названий» приведены обе формулировки.

## Ограничения и неоднозначности

- «Примечание» в файле не заполнено ни в одной строке; использованы «Комментарии» (источник виден в `extra_json.note_source`).
- 56 строк не имеют «Длина, м» даже после подстановки merge; во всех 56 из них заполнена «Длина после упак, м» — это в основном вторые строки пар (2,7 → 1,8/0,9), где длина в файле не проставлена. Исходную длину для них не подставляли, поэтому пары «было → стало» по таким строкам не построены (распил на них виден только по «Длина после упак, м»). Полный список — в `packing-plan-2026-rows.csv` (пустая `length_m`).
- Внутри файла есть противоречия «название ↔ колонка длины»: например `ЮП-3472` (июнь) — в названии 2,5 м, в «Длина, м» 2,7; `ЮП-3658` (сентябрь, стр. 55) — в названии 2,5 м, в «Длина, м» 2,5, а в «Длина после упак, м» 3,0 (похоже на перепутанные колонки). Значения колонок не переписывались.
- `ЮП-2616` в плане называется и «Кант универсальный 47мм», и «Кант универсальный 26мм», в БД — «Кант универсальный 26мм». Это внутреннее расхождение плана, а не только БД.
- `ЮП-2627` в плане один раз назван «Угол 24*10» (в БД это `ЮП-3019`/`3418`). Строка оставлена за `ЮП-2627`, как в файле.
- Дубли SKU в БД (`ЮП-2413`/`ПП47`/`ПП37`, `ЮП-3168`/`150`, `ЮП-2630`/`033`, `ЮП-2910`/`325`/`ЮП-3473`) разрешаются в пользу точного совпадения артикула, поэтому план `ЮП-2910` не «схлопывается» с `ЮП-3473`, хотя у них общий алиас.
- Составной `ЮП-3773/1103`: `ЮП-3773` есть в БД (на 2026-11-06 — с названием «Плинтус алюминиевый 40 мм» и длиной 2,5 м), вторая часть `1103` точного совпадения не имеет (`ALS-1103` — другой префикс). Матчинг — по `ЮП-3773`.
- Строк, где артикул выглядит как итог/мусор, не найдено; пропущено 0 строк (проверка по regex и по «Итого/Всего»).
