# Спека: эквивалентные артикулы — общий пул сырья

Решения: [ADR-0073](adr/0073-gruppa-ekvivalentov-obshchiy-pul-syrya.md).
Термины: [`GLOSSARY.md`](../GLOSSARY.md) — «Эквивалентные артикулы»,
«Пара (`product_pairs`, A+B)».
Тикеты: [#393](https://github.com/mavkasgit/ktm2000/issues/393) (эпик),
задачи [#394](https://github.com/mavkasgit/ktm2000/issues/394),
[#395](https://github.com/mavkasgit/ktm2000/issues/395),
[#396](https://github.com/mavkasgit/ktm2000/issues/396),

## Проблема

`Product.aliases` объявляет артикулы взаимозаменяемыми, но учёт и выдача
идут строго по `product_id`:

- индикатор `free_stock_by_product_ids` суммирует остаток одного SKU;
- `build_issue_plan` фильтрует `StockBalance.product_id == product_id`;
- `resolve_source_issues` отвергает материал «другого артикула»;
- завершение задания списывает вход по `task.product_id`.

В результате склад, где физически одна куча (A и B — один и тот же
профиль), показывает две кучи: позиция на A не видит остаток B, а две
позиции на A и B конкурируют за один и тот же материал, каждая видя только
свою половину.

## Решение кратко

Группа эквивалентов — **один пул сырья** для индикатора наличия и выдачи.
В БД остатки остаются по каждому SKU (миграции нет): группа живёт в
операторском слое — остатки, индикатор, окно выдачи. При выдаче материал
списывается с фактического SKU, а на участок приходуется **артикулом
задания**; дальше маршрут, завершение, брак, передачи и выпуск не меняются.

## 1. Термины и границы

- **Группа эквивалентов** — транзитивное замыкание `Product.aliases` по
  существующим продуктам. Не путать с парой `product_pairs`: пара — два
  разных артикула на одном подвесе, к эквивалентности отношения не имеет.
  Пары из эквивалентов не существует; структура и выдача пары не меняются.
- **Пул** — GOOD-остатки группы на складах-хранилищах (`raw`/`wip`/
  `finished`, `STOCK_TYPES`).
- **Артикул задания** — `product_id` задания/позиции (для пары — первый
  компонент, как сейчас).
- **Фактический SKU** — `StockBalance.product_id` строки, с которой
  списывается материал. Может не совпадать с артикулом задания.

## 2. Группа

Группа строится **на чтение** и не хранится.

- Узлы — все продукты, у которых есть `sku`, включая `is_active=false`.
  Alias-SKU без строки продукта игнорируется: остатка у него быть не может.
- Рёбра — `Product.aliases` в обе стороны. Сопоставление alias-текста с
  `Product.sku` — через `normalize_sku` (регистр, пробелы, тире).
- Транзитивность: `A~B`, `B~C` ⇒ `A, B, C` — одна группа.
- `group_key = min(product_id)` группы; `skus` — SKU группы по возрастанию
  `id`. Канонического артикула нет: ни один SKU не «владеет» пулом.
- Модуль-владелец — `app/services/product_alias_groups.py`:
  `load_alias_groups(db, product_ids, cache=...) -> AliasGroups`.
  Импорт, выдача и индикатор не строят замыкание сами.
- Кэш — на HTTP-запрос (по образцу `PairResolutionCache`): один SELECT
  `Product.id, Product.sku, Product.aliases` по всему справочнику, дальше
  union-find в памяти. Повторные вызовы одного запроса не дают SQL.

## 3. Наличие

Обозначения: `g` — группа, `Q` — количество позиции (для пары — количество
на каждый компонент).

- `free_g` = сумма `StockBalance.balance_qty` по `product_id ∈ g`,
  `quality_state = GOOD`, `Section.type ∈ STOCK_TYPES`, `balance_qty > 0`.
- `demand_g` = сумма `quantity` открытых позиций (`released`, есть
  незакрытая задача), чьи эффективные продукты входят в `g`. Парная позиция
  даёт `Q` на каждый компонент, как в `committed_demand_by_product_ids`.
- `own_g(position)` = сумма по эффективным продуктам позиции в `g`:
  `Q` на каждый компонент. Для одиночной позиции это `Q`.
- `available_g = max(0, free_g − max(0, demand_g − own_g))`.
- Для позиции:
  - `free = min_g free_g`;
  - `available = min_g available_g`;
  - `deficit = max_g max(0, own_g − available_g)`;
  - групп нет (не резолвится продукт) → все три поля `None`.

Одна группа (обычный случай) сводится к `free_g`, `available_g` и
`deficit = max(0, own_g − available_g)`. Для пары с компонентами в разных
группах работает `min`/`max`: каждой группе нужно `Q`, связывает минимум.

Поля ответа API не меняются: `free_stock_quantity`,
`available_remainder_quantity`, `deficit_quantity`. Добавляется
`free_stock_breakdown: [{product_id, sku, quantity}]` — расшифровка группы
для строки плана; считается из тех же строк, без отдельного SELECT.

Брак и терминал остаются вне пула (как сейчас). Цеховые секции не входят:
материал, выданный открытой задаче, — баланс участка, а не свободное сырьё.

## 4. Что подходит

Ровно те же четыре фильтра, что у выдачи (#282):

1. размеры — строгое равенство (`dimensions_equal`);
2. `completed_operations` — принимается маршрутом позиции (`_match_target`);
3. качество — `GOOD` (брак не источник);
4. склад — `raw`/`wip`/`finished`.

Ничего из атрибутов продукта не сравнивается: ни `profile_type`, ни
покрытие/цвет/сплав, ни реестр длин, ни `is_active`. Эквивалентность —
объявленная человеком взаимозаменяемость; дополнительные проверки
воскресили бы различие, которое алиас и должен стереть.

## 5. Порядок выдачи

- Ключ сортировки:
  `(is_task_product desc, target_sequence desc, ops_count desc, location_id, balance_id)`.
- `is_task_product` — строка принадлежит артикулу задания (для пары —
  первому компоненту). Это первый ключ: артикул задания вычерпывается
  раньше эквивалентов, даже если эквивалент лежит ближе по маршруту.
- Остальные ключи — прежний системный порядок (#282).
- Ручной выбор (`selected_balance_ids`, `remainder_allocation`) принимает
  любой остаток группы. Отказ «материал — другого артикула» заменяется на
  «материал не из группы эквивалентов».
- `excluded_balance_ids` остаётся на уровне строки остатка; UI, снимая
  галочку группы, исключает все её строки.

## 6. Выдача и канонизация

**Замок.** `execute_issue` блокирует `FOR UPDATE` все строки баланса
**группы** на складских секциях, `order_by(id)`, `populate_existing` — как
сейчас, но с `product_id.in_(group_ids)`. Иначе две параллельные выдачи на
A и B вычерпают одну кучу дважды.

**Проводки.** Для каждого взятого кандидата:

- `source_product_id = candidate.product_id`;
- `target_product_id = product_id` (артикул задания);
- `TRANSFER_SEND.product_id = source_product_id`,
  `from_location_id = balance.location_id`;
- `TRANSFER_RECEIVE.product_id = target_product_id`, `task_id = target`;
- `Transfer.product_id = target_product_id` (склад — группа, артикул
  появляется у задания);
- комментарий передачи: `«… источник: <source sku> (эквивалент)»`, если
  `source != target`;
- создаваемое задание — с `product_id = target_product_id`.

Когда `source != target`, локации проводок делят роли: `TRANSFER_SEND`
списывает только склад (`from_location_id`, без `to_location_id`), а
`TRANSFER_RECEIVE` приходит на участок задания (`to_location_id =
task.section_id`). Иначе send положил бы на участок SKU источника, и
физический остаток участка разошёлся бы с артикулом задания. Для группы из
одного продукта форма прежняя: send «склад → участок», receive — учёт
задания без локаций.

**Дальше без изменений.** Завершение, брак, передачи и выпуск работают с
артикулом задания: на участке материал уже под ним. Это и есть канонизация
на границе выдачи; в ledger остаётся фактический SKU источника, поэтому
S1 и аудит честные.

**Отмена.** `cancel_transfer` зеркалит обе проводки: source возвращается
на склад, target снимается с участка. S1/S6/C1/D1 остаются зелёными.

**Явный выбор остатка.** В `resolve_source_issues` проверка «чужой
артикул» становится проверкой членства в группе; в `release_batch`
`TRANSFER_SEND.product_id = issue.balance.product_id`, а
`TRANSFER_RECEIVE.product_id = effective_product_id`; комментарий называет
источник. Ветка без `Transfer` (выдача при выпуске) сохраняет свой
контракт S1/S6.

**Недостача.** Стратегии `fail`/`partial`/`negative_remainder` не меняются;
текст отказа называет склады группы, а не «этого артикула».

## 7. Операторский слой

- **Индикатор** — число по группе; тултип/раскрытие — `free_stock_breakdown`
  по SKU.
- **Окно выдачи** — строка кандидата = группа (склад + размер + операции)
  с суммами `available`/`take`/`remaining_after`; раскрытие — строки по
  фактическим SKU с их `balance_id`/`take`. Порядок и количества остаются
  серверными (#282): клиент только агрегирует по `group_key`, не
  переставляет и не досчитывает.
- **Экран остатков** — строка = группа (склад + качество + размер +
  операции) с суммой; раскрытие — SKU. Пагинация, сортировка и `total` — по
  группам на сервере: иначе группа разъедется по страницам и сумма
  «одной кучи» будет ложной.
- **Журнал** — передача показывает артикул задания и комментарий с
  источником; журнал движений — фактический SKU (аудит/детализация).
  Группировать журнал не нужно.
- **Подпись группы** — SKU по возрастанию `id` (например, «A, B
  (эквиваленты)»). Канонического артикула нет. Артикул задания в строке
  группы помечается.

## 8. API

| Что | Изменение |
|---|---|
| `GET /api/stock/balance` | группировка по `(alias_group_key, location, quality, dims, ops)`; пагинация/сортировка/`total` по группам; в строке — `alias_group_key`, `alias_group_skus`, `items[]` (SKU-строки с `balance_id`, `product_id`, `sku`, `quantity`) |
| `GET /api/stock/balance/by-product/{id}` | без изменений (детализация SKU) |
| `POST /api/production-planning/rows/{id}/issue-preview` | кандидат получает `group_key`, `product_id`, `sku`; `available`/`take`/`remaining_after` — по строке; клиент агрегирует по `group_key` |
| Планировочные строки (индикатор) | `free_stock_breakdown` |
| Схема БД | **без миграций** |

`issue-preview` сохраняет серверный порядок массива `candidates`: это
контракт #282. Группировка на клиенте не меняет порядок и не пересчитывает
количества — только складывает уже посчитанные значения.

## 9. Крайние случаи

- Группа из одного продукта — поведение прежнее (регрессий быть не должно).
- Alias на несуществующий SKU — игнорируется; на неактивный — входит.
- Цепочка `A~B~C` — одна группа; `A` и `C` напрямую не связаны.
- Alias-список изменили между запросами — группа пересчиталась; уже
  выданный материал остался под своим SKU, история не переписывается.
- Безразмерный остаток (`dimensions = null`) матчится только с `null`.
- `completed_operations = null` — не источник, как сейчас.
- Брак на складе группы — подсказка «браком», но не источник.
- Пара с компонентами в одной группе — `own_g = 2Q`; в разных — по `Q` на
  группу, связывает минимум.
- Две параллельные выдачи на разные SKU одной группы — групповой замок
  сериализует; вторая видит уже списанное.
- Отмена выдачи: source возвращается на склад, target снимается с участка.
- Идемпотентный replay не перерезолвит группу — возвращает прежний итог.
- Ручной выбор остатка из группы с чужим размером/операциями — прежние
  отказы с русским текстом, но проверка артикула — по группе.

## 10. Вне рамок

- Канонический артикул и перекладывание остатков под него.
- Группа как ключ `StockBalance`/ledger (миграция ядра учёта).
- Разделение пары на две задачи/две строки по компонентам.
- Резервирование склада по группам сверх текущего агрегатного спроса.
- Изменение импорта остатков и справочника: алиасы уже там, склад пишет
  SKU как есть.
- Покупки, заказы поставщикам, отчётность за пределами перечисленных
  экранов.

## 11. Тесты

**Backend**

- `product_alias_groups`: прямое ребро, двусторонность, транзитивность,
  неактивные, alias на несуществующий SKU, кэш одного запроса.
- `position_remainders`: пул, `own_g` vs чужие позиции, пара в одной группе
  (`2Q`), пара в разных группах (`min`/`max`), «нет данных» ≠ ноль.
- `source_selection`: остаток эквивалента становится кандидатом; порядок
  «артикул задания → эквиваленты»; ручной выбор эквивалента; чужой артикул
  отклоняется; подсказки по группе.
- `issue_service`: send source / receive target; `Transfer.product_id =
  target`; комментарий с источником; S1/S6/C1/D1 после выдачи и отмены;
  повторная выдача видит списанное; групповой замок (гонка на A и B).
- `plan_generation`: явный выбор эквивалента; send source / receive target;
  отказ на чужом артикуле.

**Frontend**

- Окно выдачи: агрегация по `group_key`, раскрытие до SKU, снятие галочки
  группы, сохранение серверного порядка.
- Индикатор: сумма группы и `free_stock_breakdown`.
- Экран остатков: группа одной строкой, раскрытие, пагинация по группам.

**E2E**

- Позиция на A видит остаток B и выдаёт его; на участке материал под A;
  отмена возвращает B.
- Две позиции на A и B видят одну кучу и не могут обе выдать больше, чем
  есть.
- Экран остатков: A и B — одна строка, раскрывается.

## 12. Этапы

1. Backend: группа + индикатор (тикет 1).
2. Backend: выдача из пула, обе ветки (тикет 2, зависит от 1).
3. Frontend: окно выдачи и индикатор (тикет 3, зависит от 2).
4. Остатки: группировка на сервере + экран (тикет 4, зависит от 1).
5. E2E и инварианты (тикет 5, зависит от 2–4).
