# Deployment — KTM-2000

## Обзор

KTM-2000 разработан для локального и серверного развертывания с использованием Docker Compose для управления контейнерами. В режиме Production все компоненты системы (Frontend, Backend, PostgreSQL) упаковываются в Docker-контейнеры.

## Сетевые режимы работы (Порты)

Проект поддерживает два параллельных режима доступа:

1. **Режим единой общей сети (порт 80 / 443)**:
   - Контейнеры подключаются к внешней сети `shared_gateway`.
   - Запросы направляются через центральный обратный прокси на порту 80/443 (используя имена хостов контейнеров, такие как `ktm2000-nginx-prod`).

2. **Автономный режим (прямой доступ)**:
   - Доступ к KTM-2000 осуществляется напрямую через порт хоста **8082** (проброшен в `docker-compose.prod.yml` на порт Nginx).
   - В системе также параллельно работает `ekranchik` (на порту **8083**).

## Структура конфигурационных файлов окружения (.env)

Проект использует разные файлы окружения для разделения баз данных и портов:
- `.env.dev` — Конфигурация для локальной разработки.
- `.env.test` — Настройки тестового окружения (запуск pytest / Playwright).
- `.env.prod` — Production-настройки для развертывания на сервере или в цеху.
- `.env` — Файл в корне проекта, хранящий текущие настройки хоста и доступы к MCP-серверам (SSH/SFTP).

### Ключевые переменные в `.env` файлах:

| Переменная | Пример значения | Описание |
|------------|-----------------|-----------|
| `EXTERNAL_PORT` | `8082` | Внешний порт, на котором доступно приложение |
| `BASE_URL` | `http://localhost:8082` | Базовый URL приложения |
| `POSTGRES_USER` | `ktm2000_user` | Имя пользователя базы данных PostgreSQL |
| `POSTGRES_PASSWORD` | `secure_password` | Пароль базы данных PostgreSQL |
| `POSTGRES_DB` | `ktm2000_prod` | Название базы данных PostgreSQL |
| `POSTGRES_PORT` | `5432` | Внешний порт PostgreSQL (для подключения извне) |
| `DATABASE_URL` | `postgresql+asyncpg://...` | Строка подключения ORM к PostgreSQL |
| `SECRET_KEY` | `very-long-secret-key` | Ключ шифрования сессий и токенов |
| `ENV` | `prod` / `dev` / `test` | Тип запущенного окружения |
| `ALLOW_PRODUCTION_RESET` | `false` / `true` | Полный сброс производства (`POST /production-plans/reset-all`) разрешён. Только role `admin`; при `false` ручка отвечает 404 |

**Сброс производства — только на dev/e2e.** `POST /api/production-plans/reset-all`
стирает всё производство (`TRUNCATE ... CASCADE`: планы, позиции, задания,
передачи, проводки, справочники и шаблоны импорта). Это инструмент стенда, а не
боевая ручка: в прод-окружении `ALLOW_PRODUCTION_RESET=false`, и ручка отвечает
404 — не подтверждая даже своего существования. Включать её допустимо лишь в
`.env.dev` и `.env.e2e` (issue #234).

## Production развертывание (Docker Compose)

Для запуска production-сборки на сервере:

### Шаг 1. Настройка окружения
Убедитесь, что файл `.env.prod` в корне проекта заполнен корректными секретами, паролями баз данных и внешними портами.

### Шаг 2. Сборка и запуск контейнеров
Запустите команду сборки и поднятия контейнеров из корня проекта:
```bash
npm run prod:up
```
Эта команда автоматически соберет Docker-образы для фронтенда и бэкенда, создаст том (volume) для хранения данных Postgres и запустит все сервисы в фоновом режиме (`-d`).

### Шаг 3. Просмотр логов
Для отслеживания логов запущенного production-окружения используйте:
```bash
npm run prod:logs
```

### Шаг 4. Остановка production-окружения
Для остановки и удаления контейнеров выполните:
```bash
npm run prod:down
```

## Проверка дрейфа канона (ADR-0046)

Сверка «канон ⊆ БД»: скрипт падает с ненулевым кодом, если строка
кода-канона отсутствует в БД (участок, операция участка, правило отбора
маршрута). Лишнее в БД — административная правка, дефектом не считается.
Скрипт **только читает**: повторный прогон грязную базу не приводит в
порядок, чинить её надо сидом.

### Запуск против боевой базы

Порт Postgres в проде не проброшен на хост
(`infra/compose/docker-compose.prod.yml`), поэтому запуск — внутри
контейнера backend, где DSN задаёт compose и env-файла нет:

```bash
docker exec ktm2000-backend-prod python scripts/check_canon_drift.py
```

Скрипт печатает имя проверяемой базы (`Проверяем БД: host/имя`) — «OK» без
адреса обманчив. DSN он берёт из env-файла, а не из переменных окружения
оболочки: `apply_env_file()` перекрывает `DATABASE_URL`
(`app/core/env_file.py`), так что устаревшая переменная в шелле увести
проверку на другую базу не может. Если `$ENV_FILE` указывает на
несуществующий файл, запуск падает с кодом `2`, а не печатает «OK» по
базе из окружения. На хосте с доступным портом:

```bash
cd backend && ENV_FILE=../.env.prod python scripts/check_canon_drift.py
```

### Восстановление после срабатывания

1. Пройти `POST /api/routes-seed` — префикс именно `/routes-seed`
   (`app/api/routes/routes_seed.py`), а не `/api/seed`.
2. Либо точечно вставить недостающие строки, названные в отчёте.
3. Прогнать скрипт повторно: код выхода `0` означает, что дрейфа нет.

Падение сразу после внедрения — ожидаемо и правильно: оно означает «сид на
заводе не прогнан», а не «система сломалась».

## Уборка маршрутов-сирот (#228)

**Импорт плана создаёт маршрут под каждое новое состава, и старые маршруты
не исчезают.** `db:seed` ищет только свои `code`/имена, демо-сид и миграции
маршруты не трогают, а `is_active` у лишнего маршрута остаётся `true` —
значит, он продолжает участвовать в подборе
(`app/services/route_selection.py`). За сезон работы таких маршрутов
накапливается столько, сколько было составов, поэтому уборка — регулярная
процедура, а не разовая акция.

**Критерий сироты** (зафиксирован в `app/services/route_deletion.py`):
у маршрута нет ни позиций плана, ни строк плана участков, ни заданий на его
этапах, ни позиций выпуска. Этапы, операции и правила привязки данными не
считаются — они уходят каскадом. Маршрут с любой из перечисленных строк
уборка не трогает: это рабочий или исторический маршрут.

Уборка — командой, не руками. По умолчанию скрипт только печатает список
(dry-run); удаляет лишь с `--execute`:

```bash
# посмотреть, кого убрать (ничего не удаляется)
docker exec ktm2000-backend-prod python scripts/cleanup_orphan_routes.py

# убрать
docker exec ktm2000-backend-prod python scripts/cleanup_orphan_routes.py --execute
```

> Каталог `scripts/` исключён из прод-образа (`backend/.dockerignore`), поэтому
> приведённая выше форма на текущем образе не работает: скриптов в контейнере
> нет. Утилиты запускаются там, где лежит код (`cd backend && …`), против
> выбранной базы.

На хосте с проброшенным портом Postgres DSN берётся из env-файла, а не из
окружения оболочки (ADR-0046), и проверяемая база печатается всегда:

```bash
cd backend && ENV_FILE=../.env.prod python scripts/cleanup_orphan_routes.py
```

Точечная правка одного маршрута — `DELETE /api/routes/{id}?force=true`:
ручка сносит позиции плана, строки плана участков, задания, позиции выпуска,
операции и этапы в порядке внешних ключей. Без `force` она отвечает `409` со
списком того, что будет удалено, и ничего не трогает.


## Починка операций маршрутов после рассинхрона правил отбора

Если `route_selection_rules` в базе разошлись со справочником
`section_operations` (правило адресует группу `PRESS`/`ANOD`, а участок
объявляет `PRESSING`/`ANODIZING`), сборка маршрута падала на дефолт группы:
этап анодирования получал «Серебро» для любого цвета, этап пресса — «Гребенка»
вместо «Окна», а слоты `press_op`/`color` в имени маршрута пустели. Лечится
двумя шагами, в этом порядке:

```bash
# 1. Вернуть справочники и правила к сиду (идемпотентно)
#    на хосте/в dev-окружении:  npm run db:seed
#    в прод-контейнере каталога scripts/ нет — тот же run_full_seed вызывается так:
docker exec -i ktm2000-backend-prod python - <<'PY'
import asyncio
from app.core.database import async_session
from app.seeds.run_seed import run_full_seed

async def main() -> None:
    async with async_session() as db:
        print(await run_full_seed(db))
        await db.commit()

asyncio.run(main())
PY
```

Починка записанных маршрутов — скрипт `backend/scripts/repair_route_operations.py`
(запускается там, где лежит код: `cd backend && python scripts/repair_route_operations.py`;
сначала dry-run, запись — с `--apply`).

Маршрут правится **на месте**: идентификатор не меняется, поэтому позиции
плана, строки участков, задания и выпуски продолжают ссылаться на него;
меняются операции и признаки этапов, имя, код и сигнатура. Вход для
пересборки — `plan_positions.source_payload` позиции, ссылающейся на маршрут.
После записи скрипт сверяет сигнатуру, посчитанную по записанным этапам, с
сигнатурой пересборки: не совпала — правки этого маршрута откатываются.

Маршруты, у которых состав этапов не собирается ни одной из их позиций (в базе
есть `DRILLING`/`PRESSING`, которых пересборка не даёт), скрипт не трогает и
печатает причину: это не порча операций, а разъехавшееся назначение позиций.


## Ремонт оси «пройденные операции» (ADR-0061, #272)

**Признак `completed_operations` у уже записанных проводок остался грубым.**
До [ADR-0061](adr/0061-priznak-projdennyh-operacij-po-operaciyam-etapa.md) он
выводился из справочника УЧАСТКА — объединение операций всех
секций пройденных этапов, — поэтому на одном остатке лежали резы, которых
материал не проходил, и цвета анодирования, которых он не имел. Списание ищет
ТОЧНУЮ группу остатка (ADR-0055), поэтому на полном участке оно находит грубую
строку и падает. Источник признака теперь — операции ЭТАПА
(`route_operations`), но задним числом оси не пересчитываются: этим занят
[`backend/scripts/repair_completed_operations_axis.py`](../backend/scripts/repair_completed_operations_axis.py).

Предусловия:

- миграции накатаны, база доступна по DSN из env-файла;
- справочник `section_operations` актуален (`npm run db:seed`): скрипт сверяет
  пересчитанные признаки со справочником и при коде вне его **отменяет запись,
  код выхода 2** — такая строка остатка отличалась бы от соседней в данных, но
  была бы неотличима в UI (ADR-0055 п.5);
- запуск из `backend/` с `ENV_FILE`. Без env-файла скрипт печатает причину в
  stderr и уходит с тем же кодом 2, не доходя до импорта приложения: иначе
  pydantic отдал бы приоритет окружению оболочки (ADR-0046).

```bash
cd backend

# dry-run — ничего не записывает; режим напечатан в начале вывода
ENV_FILE=../.env.dev python scripts/repair_completed_operations_axis.py

# запись — только после просмотренного dry-run
ENV_FILE=../.env.dev python scripts/repair_completed_operations_axis.py --apply
```

Что обязан показать dry-run перед `--apply`:

- `Проверяем БД: …` — какую именно базу тронет следующий запуск;
- `Проводок с признаком: N`, `Изменится: M; без изменений: K`;
- `Пропущено (импорт/ручное/вне плана): …` — строки импорта остатков
  (`source_ref` с префиксом `import_remainders:`) и ручные правки не трогаются
  принципиально: их признак пришёл из Excel или выбран оператором, и
  переписать его «по маршруту» — значит соврать;
- `НЕ РАЗОБРАНО: …` и `НЕОДНОЗНАЧНО: …` — проводки, чей этап не определить по
  записанному грубому значению. Они не пишутся никогда: молчаливая правка
  «наугад» запрещена (ADR-0021). Непустой список — повод разбираться в данных,
  а не повторять `--apply`.

С `--apply` пересобираются **все** строки баланса
(`StockProjectionManager.rebuild_all_balances`), не только затронутые: ось
входит в подпись строки остатка, и частичная пересборка оставила бы
несогласованными соседние строки. Итог вывода — `Записано проводок: M;
пересобрано строк баланса: N`. Скрипт идемпотентен: второй dry-run на
починенной базе даёт `Изменится: 0`.

Проверка после ремонта. Инвариант ledger ↔ балансы ↔ `WorkTask.cached_*`
живёт в `backend/tests/test_integrity_invariants.py` — семь запросов, те же
вызываются из остальных тестов через `assert_no_invariants_violations`. Это
pytest-срез на своей run-БД (`npm run test:pytest -- -k integrity`), а не
команда для боевой базы. На проде контроль прикладной: списание реального
остатка проходит без «нет подходящей строки остатка».

Флаги (полный текст — `python scripts/repair_completed_operations_axis.py --help`):
`-h, --help`; `--apply` — «записать пересчитанные оси и пересобрать балансы
(по умолчанию только показать)». Других переключателей нет: скоуп ремонта
определяется данными, а не флагами.

**Как откатиться.** Позначного undo нет: скрипт перезаписывает
`completed_operations` и пересобирает проекцию, прежнее грубое значение нигде
не сохраняется. Откат — восстановление базы из бэкапа, снятого **до**
`--apply`: на prod это ручной бэкап раздела «Бэкапы» (`<STORAGE_ROOT>/backups`,
manual-тип ротацией не удаляется), на dev — слепок `npm run db:snapshot --
dump <label>` перед запуском и `restore` после. Слепки, заметим, только для
dev: `db_snapshot.py` сам отказывается работать против prod-окружения, потому
что `restore` пересобирает базу целиком. Поэтому порядок действий фиксирован:
dry-run → бэкап/слепок → `--apply` → сверка.

Решение о запуске на боевой базе принимает владелец: правятся исторические
проводки, балансы пересобираются целиком.

## Ключи ручных норм подвеса (ADR-0047, #218)

Миграция `066_hanger_norm_key_normalization` приводит ключи ручных норм
подвеса в `products.attributes->'quantity_per_hanger'` к нормальной длине
артикула. Правило «на статью»: ключ, совпадающий с нормальной длиной
артикула, не меняется; ключ, равный его сырьевой длине, переписывается на
нормальную; ключ, не совпавший ни с чем, сохраняется.

Каждая изменённая строка и каждый неразрешённый ключ попадают в отчёт —
таблицу `hanger_norm_key_migration`:

```sql
-- что переписано (старый ключ → новый)
SELECT sku, old_key, new_key FROM hanger_norm_key_migration
WHERE status = 'rewritten' ORDER BY sku;

-- что требует решения оператора
SELECT sku, old_key, reason FROM hanger_norm_key_migration
WHERE status = 'unresolved' ORDER BY sku;
```

Неразрешённые ключи — бизнес-решение: удалить значение либо ввести в реестр
длину, совпадающую с ключом. Автоматически подставлять длину нельзя.

Блокирует правку карточки только запись с **непустым `manual`** (ADR-0047
п. 3): у артикула в авто-режиме словарь не читается, поэтому строка отчёта с
`manual = null` — это информация о ключе, а не о несохранимом ручном вводе.

Порядок выкатки обязателен: **защита из #217 должна оказаться в базе раньше,
чем прогнана эта миграция.** Иначе между выкаткой кода и прогоном миграции
правка карточки успеет пересобрать словарь и стереть значения, ради которых
миграция и делается.

Миграция идемпотентна (повторный прогон ничего не меняет) и обратима:
`alembic downgrade 065_route_stage_transit_normalization` возвращает ключи по
отчёту и убирает таблицу.

## Хранение файлов и бэкапы

Расклад файлового хранилища — ADR-0026: корень один (`STORAGE_ROOT`), подкаталоги
`products/`, `imports/`, `backups/` выводятся из него в `config.py` и отдельно не
настраиваются. В контейнере корень задаёт compose (`STORAGE_ROOT=/app/storage`), на
хост смонтирован `data/storage-prod` → `/app/storage`; при запуске backend на хосте
путь резолвится от каталога `backend/` (например `../data/storage-dev`).
Контейнерный путь `/app/...` вне контейнера — ошибка старта, а не молчаливый
каталог `C:\app\...`.

Данные Postgres лежат в bind-mount, заданном в compose-файлах:
`data/postgres-prod` (prod) и `data/postgres-dev` (dev).

Бэкапы БД создаются разделом бэкапов в настройках приложения и авто-планировщиком,
пишутся в `<STORAGE_ROOT>/backups` — то есть персистятся тем же bind-монтированием,
что и файлы (`data/storage-prod/backups`). На prod авто-бэкап включён:
`config.json` → `{"auto_enabled": true, "time_of_day": "00:00"}`. Время — локальное
время контейнера, а это UTC (`TZ` намеренно не переопределяем: смена TZ сдвинула бы
`datetime.now()` во всём коде), поэтому 00:00 = 03:00 МСК. Ротация — GFS в
`rotate_backups()`: daily хранится 7, weekly — 4, monthly и manual автоматически не
удаляются; тип бэкапа определяется датой (`determine_backup_type`). Локальная
копия не защищает от отказа диска: офсайт-копирование — отдельная задача.
Скрипт `scripts/backup.sh` — серверный (Linux), архивирует дамп БД и
`data/storage-prod` в `/home/ubuntu/backups/archive` с ротацией 14 дней.
