## 1. Где вообще живёт исполнитель (факты, с места)

Исполнителя нет ни в `Transfer`, ни в `Action` как связи — он живёт **только на
проводке ledger** и в паре мест в UI.

| Слой | Что сегодня | Файл:строка |
|---|---|---|
| Проводка ledger | `executor_user_id` (FK на users, **nullable**) + `executor_user_name` (снимок имени, nullable) | `backend/app/stock/models.py:242,244` |
| Проводка ledger | `created_by` (FK, **NOT NULL**) + `created_by_user_name` — это *кто записал*, а не кто выполнил | `backend/app/stock/models.py:243` |
| Завершение задачи | `eff_executor = executor_user_id or actor_id` — один, с откатом на текущего пользователя | `operations_tasks.py:813`, `:1104` |
| Завершение задачи | пишется на каждую порцию (good / scrap / transform) — то есть на проводку, а не на задание | `operations_tasks.py:502,567,591,669` |
| Передача | `executor_user_id` приходит payload'ом и пишется на проводку; сама `Transfer` исполнителя **не хранит** — только `created_by` | `transfers/schemas.py:23`, `transfers/api.py:90`, `models/transfer.py:126` |
| Журнал действий | `Action.actor` — **строка имени**, не FK, без разделения на created/executor | `models/action_journal.py:65` |
| Аудит | `AuditLog.user_id` + `user_name` — один субъект на запись | `models/audit_log.py:51-52` |
| UI: массовое завершение | `executor_user_id: me?.id` — исполнитель всегда текущий пользователь, выбирать нельзя | `SectionsTasksPage.tsx:994` (и `809`, `899`) |
| UI: передача | одиночный `Select` исполнителя; есть причина отказа `"no_executor"` | `BulkTransferFooter.tsx:44,129,142`, `runTransferBatch.ts:171` |
| Тип API | `BulkCompleteEntry.executor_user_id?: number \| null` — одно число | `shared/api/shopfloor.ts:572` |

## 2. Чего модель не может выразить сегодня

1. **Список исполнителей — нигде.** Ни одна таблица не имеет массива или
   связки «действие → исполнители». `Action.actor` — строка, `Transfer` —
   вовсе без исполнителя, проводка — один `executor_user_id`.
2. **Разделение «кто записал» и «кто выполнил» проведено только на проводке.**
   В `Action` и `AuditLog` этого разделения нет вовсе: там один субъект.
3. **Имя исполнителя хранится снимком** (`executor_user_name`), а не ссылкой.
   Список из снимков переживёт переименование, но не даст ни FK-целостности,
   ни агрегации по людям без разбора строки.

## 3. Что ломается, а что нет (проверено, не предположено)

**Не ломается от добавления списка:**

- **Складские инварианты.** `assert_no_stock_ledger_invariants_violations`
  (`tests/test_integrity_invariants.py:394`) проверяет количества, балансы,
  сегменты и пары проводок. Слово `executor` в файле инвариантов не встречается
  **ни разу** (проверено: `grep -c executor` → 0). Исполнитель ни читается, ни
  суммируется — список на проводку инварианты не затрагивает.
- **Количества и `planned_quantity` получателя.** Ни `transfer_send`, ни
  `complete_task` не читают исполнителя при расчёте количеств: executor —
  чисто пишущее поле. Проверки «сколько можно передать» к исполнителю не
  обращаются, поэтому «сделали вдвоём» на количество не влияет.
- **Идемпотентность** — по ключу, к исполнителю не привязана.

**Ломается или требует решения:**

- **Компенсации (откат) уже сегодня не зеркалят исполнителя.** `PlannedEntry`
  копирует `created_by`, но **не** `executor_user_id`
  (`reversal/stock_compensator.py:111`), и при записи компенсации executor не
  пишется вовсе (`:253-254` — только `created_by`/`created_by_user_name`).
  То есть у откатанной операции исполнитель сегодня пуст. Любой вариант должен
  ответить, что происходит с исполнителями при откате.
- **Аудит и журнал действий** останутся с одним субъектом, если носитель
  выбран не в `Action`. Тогда «кто делал» и «кто отвечает за запись» живут в
  разных местах — это нужно зафиксировать явно, иначе получится два источника
  правды (п. 5 тикета).
- **Отчётности по исполнителям сегодня нет вообще.** Ни один отчёт и ни одна
  выборка в `api/routes` не группирует по executor (все вхождения —
  пишущие). Если владелец ждёт «кто сколько сделал», это новая сущность, а не
  расширение существующей.

## 4. Три варианта контракта

### Вариант A. Список на проводке (JSONB `executor_user_ids` + имена снимком)

Носитель: массив в `stock_transactions` рядом с существующим одиночным полем.

- Плюсы: правка локальна, компенсации зеркалят тем же полем, откат не ломается
  структурно; «кто выполнял» видно ровно там же, где сегодня видится один.
- Минусы: связность по людям не выражается — аналитика по исполнителю
  превращается в разбор JSONB; появляются два способа ответить на один вопрос
  (старый `executor_user_id` и список), если не оговорить приоритет; отчётность
  «по исполнителям» по этой дороге почти невозможна без отдельной проекции.

### Вариант B. Таблица-связка «действие → исполнители»

Носитель: отдельная таблица с `(action_id, user_id, role)`; проводка ссылается
на `Action`.

- Плюсы: единственный источник правды на действие, нормальные FK, отчётность
  по людям получается обычным `GROUP BY`; компенсация получает свой `Action`
  и естественно несёт свой список.
- Минусы: это самая дорогая по объёму правка — миграция, запись во все пути
  (`complete_task`, `transfer_send/receive`, компенсации), перечитывание в
  интерфейсах; `Action` сейчас не несёт FK на пользователя (только строку
  `actor`), то есть придётся договариваться, кто «главный» actor для старых
  записей.

### Вариант C. Список на `Action` (JSONB), проводка не меняется

Носитель: `Action.executors` (массив id/имён); `stock_transactions` остаётся
с одиночным исполнителем и трактуется как «кто вёз/записал эту партию».

- Плюсы: одна запись на действие (а не на каждую порцию) — при завершении
  трансформации порций несколько, и список исполнителей у них общий; не
  трогаем горячий путь ledger вообще.
- Минусы: «кто выполнил» для отдельной проводки перестаёт быть точным (все
  проводки действия получат одно и то же одиночное поле, взятое у кого-то
  одного); печатный лист участка и журнал операций, которые строятся по
  проводкам, покажут одного человека — придётся либо везти список в UI из
  `Action`, либо принять неполноту.

## 5. Один список вопросов — там варианты расходятся

1. **Где «кто делал» должно быть видно как список?** Печатный лист участка и
   журнал операций строятся по **проводкам**; журнал действий — по `Action`.
   Ответ решает между A и C больше, чем всё остальное: список на проводке
   виден везде, список на действии — только в журнале действий.
2. **Откат: исполнители копируются или затираются?** Сегодня компенсация
   исполнителя не несёт. Вариант A зеркалит автоматически; C требует явного
   решения, а B — отдельного правила для `reversed`-действия.
3. **Нужна ли отчётность по людям сейчас?** Если да — A и C отпадают без
   проекции; если задача только «записать факт», A/C дешевле B.
4. **Старое одиночное поле живёт или заменяется?** Если заменяется — нужна
   миграция данных и окно, где часть записей без списка; если живёт — нужна
   формулировка приоритета, иначе получится два источника правды.
5. **«Главный» исполнитель для отчётов** — это отдельный вопрос к п. 5 AC:
   явное поле (`primary_executor_id`) или позиция в списке. Он не зависит от
   носителя и должен быть решён независимо, иначе отчётность будет зависеть
   от порядка в JSONB.

## Границы разбора

- Прав/ролей и `canForceDelete*` не касался (граница тикета).
- Объём распространения (только `bulk-complete` или ещё передачи/отправка/
  отмена) намеренно не предрешён: он зависит от выбранного носителя и вынесен
  в вопросы 1–2.
- Код не трогал, миграций не писал, тесты не запускал ради измерений —
  задача разбора, а не реализации.
