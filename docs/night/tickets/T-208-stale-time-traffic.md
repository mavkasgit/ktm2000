# T-208 — замер трафика при `staleTime` 3 с против 5 мин (#208)

- **Статус:** DONE (замер сделан; ничего не переключено)
- **Ветка/дерево:** `night/2026-10-01-c`, база `63cb2b9`
- **Скрипт замера:** `frontend/e2e/traffic-stale-time.tmp.spec.ts` (проект `tmp`,
  включается только при `E2E_TMP=1`)
- **Условия:** «под нагрузкой» — dev-стек человека (`:5172`, `:8012`),
  прод-контейнеры (`:8082`), Postgres `:5440`/`:5441`, два соседних агента.

## Способ измерения

Playwright на e2e-стенде своего worktree (клон шаблонной БД, порты выдаёт ОС).
Счёт — на стороне клиента: `page.on('request')` + `page.on('response')`, только
URL с `/api/`; байты — из `content-length` (uvicorn отвечает без сжатия, то есть
это байты по проводу).

Второй режим (`staleTime` 5 мин) включается **только в сценарии**: модуль
`/src/app/main.tsx` перехватывается у dev-сервера (`page.route`) и поле
`staleTime` подменяется (`1e3 * 3` → `1e3 * 300`; esbuild отдаёт литерал как
`1e3 * 3`, поэтому замена — по имени поля, а не по исходному выражению).
Продуктовый `frontend/src/app/main.tsx` не менялся: `staleTime: 1000 * 3`
(`git diff` по файлу пуст, значение совпадает с HEAD).

Переходы — **клики по боковому меню** (клиентский роутинг). `page.goto`
перезагружал бы приложение и обнулял кеш React Query — тогда `staleTime` не влиял
бы ни на что, и замер был бы не про него.

Сценарий (по шагам, как требует тикет): вход (break-glass, `DEV_BYPASS_AUTH`) →
доска участка → контроль выполнения → передачи → справочник сырья → планирование,
затем возврат на контроль выполнения и на доску участка. Пауза 1.5 с на экран.
Бизнес-действий нет, только переходы. **Диалоги не открывались** (в исходной
методике тикета — «один-два открытых диалога»): в бриф ночи они не входили.

```
E2E_TMP=1 npm --prefix frontend run test:e2e -- \
  e2e/traffic-stale-time.tmp.spec.ts --project=tmp --retries=0
```

## Числа

Один терминал, один проход по сценарию (в зачёт — 7 шагов: 5 разделов + 2 возврата;
вход и прогрев не считались):

| Режим | Запросов | Уникальных URL | Байт | Смена раздела (5 шагов) | Повтор того же экрана (2 шага) |
|---|---|---|---|---|---|
| `staleTime` 3 с (текущее) | **21** | 15 | **17 861** | 15 запросов / 10 647 Б | **6 запросов / 7 214 Б** |
| `staleTime` 5 мин | **15** | 15 | **10 647** | 15 запросов / 10 647 Б | **0 запросов / 0 Б** |
| разница | +6 (+40 %) | 0 | +7 214 (+68 %) | 0 | +6 |

**Смена раздела от `staleTime` не зависит вовсе**: первый заход на экран — это
всегда промах кеша, поэтому 15 запросов и 10 647 Б совпали в обоих режимах
до байта. Весь эффект короткого `staleTime` — в **возврате на уже посещённый
экран** (6 запросов, 7 214 Б; 29 % запросов и 40 % байт сценария).

Что именно перечитывается на возвратах (по эндпоинтам):

| Шаг | Эндпоинт | Байт |
|---|---|---|
| повтор: контроль выполнения | `GET /api/production-planning/rows?limit=50&offset=0` | 43 |
| повтор: контроль выполнения | `GET /api/sections?limit=500&offset=0` | 3 644 |
| повтор: доска участка | `GET /api/auth/me` | 260 |
| повтор: доска участка | `GET /api/shopfloor/sections/summary` | 3 206 |
| повтор: доска участка | `GET /api/shopfloor/sections/2/board?limit=50&offset=0` | 59 |
| повтор: доска участка | `GET /api/daily-plans/sections/2` | 2 |

Вес дают два запроса: `sections?limit=500` + `shopfloor/sections/summary` =
6 850 Б из 7 214 Б (95 %); остальные четыре — 364 Б.

### Две вкладки (тот же стенд, `staleTime` 3 с)

| Что | Запросов | Байт |
|---|---|---|
| вкладка 1: вход в контроль выполнения | 5 | 5 082 |
| вкладка 2: полный проход (7 шагов) | 21 | 17 861 |
| вкладка 1 после возврата фокуса | 0 | 0 |
| **сумма** | **26** | **22 943** |

Кеш у вкладок свой (два экземпляра приложения), общего трафика нет: цена
терминала умножается на их число, второй терминал стоит столько же, сколько
первый.

**Предел:** возврат фокуса на вкладку 1 дал 0 запросов — в headless-браузере
Playwright фокус эмулируется, и настоящее событие фокуса/размытия не приходит.
`refetchOnWindowFocus` в приложении не переопределён (дефолт TanStack Query —
`true`), поэтому в живом браузере возврат фокуса после 3 с перечитает то, что
протухло. По составу смонтированных на `/execution` запросов это [INFERENCE]
2 запроса (`production-planning/rows` + `sections`, ≈3.7 КБ на пустых таблицах) на
каждый возврат фокуса в режиме 3 с и 0 в режиме 5 мин. Отдельным числом это не
измерено — названо как остаток.

### Ограничение по байтам

Производственные таблицы стенда пусты (`apiResetAll()` перед замером; сид — только
справочники: 12 участков, 5 ГХП, 2 маршрута). Поэтому байты — **нижняя граница**
для рабочей смены. Важно, что перечитываемые эндпоинты — как раз тяжёлые по данным
(`production-planning/rows` 43 Б, `shopfloor/…/board` 59 Б, `daily-plans/…` 2 Б на
пустой базе): на реальном плане байтовая разница вырастет примерно линейно объёму
плана, а **число запросов останется 6**.

## При каком числе терминалов это значимо

Опросов по таймеру нет: короткий `staleTime` не создаёт фоновой нагрузки, он лишь
перечитывает экран при возврате. Поэтому добавка пропорциональна **частоте
переходов**, а не времени:

- пока оператор никуда не переходит, обе схемы дают 0 запросов/с;
- при непрерывных переходах по сценарию замер дал ≈1.75 запроса/с (3 с) против
  ≈1.25 запроса/с (5 мин) — добавка ≈**0.5 запроса/с** на активно работающий
  терминал;
- в пересчёте на проход: +6 запросов / +7.2 КБ на каждый возврат к экранам.

Для одной смены (1–5 терминалов, переходы «раз в минуту») добавка — единицы
запросов на проход, то есть **в пределах шума**: менять `staleTime` ради трафика
основания нет. [INFERENCE] Добавка становится заметной серверу примерно с
**20–30 одновременно активно переключающихся терминалов** (≈10–15 дополнительных
запросов/с на весь парк): порог прямо зависит от запаса сервера, а нагрузочный
замер сервера в этот тикет не входил — это отдельная задача.
