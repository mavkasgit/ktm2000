# T-297 — `/production-planning/rows` без per-позиционных резолвов

## Проблема

Страница «Контроль выполнения» опрашивается каждые 12 секунд. На dev-данных
(91 позиция) один вызов стоил **1909 SQL-запросов**.

## Замер «до»

Методика #290: прямой вызов сервис-функции в транзакции с `rollback`, счёт SQL —
engine-слушатель `before_cursor_execute`/`after_cursor_execute`. Dev-данные
`:5440/ktm2000_prod` — только SELECT, никогда не мигрировались.
Мералка: `docs/night/logs/t297_measure_before.py`.

| Эндпоинт | SQL | строк | wall-мс |
|---|---|---|---|
| `rows` limit=100 | 1909 | 91 | 5087.0 |
| `rows` limit=500 | 1909 | 91 | 4926.7 |

## Разбор: откуда 1909

Профиль верхних запросов по числу вызовов показал, что 1010 из 1909 — это
загрузки секций:

| Вызовов | Форма |
|---|---|
| 215 | `section_operations` по `section_id` |
| 215 | `spg_sections` join `storage_production_groups` |
| 215 | `user_sections` join `users` |
| 183 | `section_operations` (вторая форма) |
| 182 | `sections` — по одной секции на строку |

Три запроса × ~215 — это в точности `Section.users`, `Section.operations`,
`Section.spg_links`: все три объявлены с `lazy="selectin"`
(`app/models/section.py:48-50`), а `selectin` срабатывает на каждый загруженный
**экземпляр**, а не на запрос.

Изолированная проверка (`t297_trace.py` + фазовый замер) сузила источник:
цикл `route_steps` в `_build_planning_rows_for_positions` грузил
`select(RouteStage, Section).options(selectinload(RouteStage.operations))`
внутри цикла по уникальным `route_id`. На 33 маршрутах это 5 запросов на маршрут
(1 основной + `operations` + 3 связи `Section`) — **165 запросов вместо одного**.
Замер по фазам: 25 SQL на 5 маршрутов против 5 у эквивалентного запроса по
колонкам.

Второй источник — `_resolve_effective_product_ids` вызывался на каждую позицию
**без** `PairResolutionCache`, хотя контракт #292 это предусматривает.

## Что сделано

`backend/app/services/production_planning_rows.py`, функция
`_build_planning_rows_for_positions`:

1. **Резолв маршрутов переведён на batch** (`resolve_position_routes_batch` из
   #292) вместо поштучного `resolve_position_route` в цикле. Результат —
   `route_info_by_position: dict[int, ResolvedRouteInfo]` по `position.id`.
2. **Этапы маршрутов — один запрос по колонкам** на все уникальные `route_id`
   (`RouteStage.route_id/id/sequence/section_id` + `Section.icon/icon_color`) и
   один запрос операций по всем `stage_id`. ORM-объекты `Section` больше не
   грузятся, значит не срабатывают и три `selectin`-связи.
   `Section.is_active == True` и порядок по `sequence` сохранены.
3. **`PairResolutionCache` на запрос** — резолв эффективных продуктов по-прежнему
   поштучный (так устроен `product_pair_resolver`), но пары резолвятся один раз
   на страницу вместо раза на позицию.

Порядок вычислений сохранён: сначала резолв маршрутов, затем этапы, затем
эффективные продукты, затем индикатор остатка, затем подвесы.

## Границы (что НЕ трогал)

- `get_production_planning_row_detail` (единственное оставшееся
  `resolve_position_route` в этом модуле) — это одиночная позиция, там N+1 нет.
- `_operation_name_search_exists` и прочие EXISTS — они уже на индексах из #291.
- SQL-формы выборок, фильтры, сортировка, пагинация — без изменений.
- `overview` и `imports/{id}/positions` не трогал: у них другой корень
  (см. ниже), они в тикетах #298 / #296.

## Замер «после»

**−98% SQL** (1909 → 37), wall −86…−95% (под нагрузкой, вторично).

## AC «число SQL не растёт с числом позиций» — проверено отдельно

Проверять на dev-данных бессмысленно: там всего 91 позиция, лимит не связывает,
поэтому limit=100 и limit=500 давали одинаковые 1909 запросов ещё ДО правки.
Чтобы показать зависимость, поднят изолированный клон dev-данных с
`plan_positions`, раздутым до **900 позиций** (`t297_scaling.py`):

| limit | строк | SQL до | SQL после |
|---|---|---|---|
| 50 | 50 | 1080 | **37** |
| 100 | 100 | 1928 | **37** |
| 250 | 250 | 1928 | **37** |
| 500 | 500 | 1928 | **37** |

До правки число запросов росло вместе со страницей и упиралось в 1928; после —
**константа 37** на любом размере страницы. AC выполнен.

Оговорка про честность сравнения: на dev-данных (91 позиция) снижение видно
только как 1909 → 37; эффект пагинации в цифрах не виден именно потому, что
лимит не связывает. Цифры выше сняты на раздутом клоне — это и есть проверка AC.

## Опрос стабилен (нет кэша между запросами)

Два последовательных вызова подряд дают одинаковое число SQL. Кэши
(`route_steps_cache`, `PairResolutionCache`, мемо-кеш
`resolve_position_routes_batch`) — локальные переменные функции
`_build_planning_rows_for_positions`, они живут ровно один вызов; наружу не
выносятся и в модуле не хранятся.

## Что НЕ помогло / что осталось за тикетом

- **Индексы тут ни при чём.** Все ~1000 запросов шли по primary key и были
  оптимальны. Ускорение целиком из числа запросов.
- `rows` — 37 SQL на страницу. Оставшиеся 37 — это разумный пол: пагинация,
  агрегаты по позициям, снимок справочников маршрутов, подвесы, индикатор.
  Дальше сокращать имеет смысл только если появятся новые per-строковые
  резолвы.
- **`overview` (2723 SQL) и `imports/{id}/positions` (1796 SQL) не тронуты** —
  они в тикетах #298 и #296. У `overview` свой корень: 921 запрос из 2723 —
  это scalar `get_task_cache` в цикле (`production_planning.py:541`), при том
  что рядом в том же файле (`production_planning.py:1879`) уже есть bulk
  `get_tasks_cache_bulk`. У `imports/{id}/positions` — тот же класс проблемы
  с загрузкой `Section` по одной.
