## #302 — два красных `ui-narrow` после двухрежимного ввода факта

## #303 — `selectin` на связях `Section`

### Исправлено (лёгкое)

**1. Мёртвый словарь `section_ids_by_route` в `overview`.**
`backend/app/api/routes/production_planning.py`, после правки `07a416fa`
остался словарь, который наполнялся в цикле по `stage_rows` и нигде не читался.

Доказательство — разбор AST функции `get_production_planning_overview`:
единственные обращения к имени —

```
section_ids_by_route refs inside overview: [(473, 'Store'), (513, 'Load')]
```

`Store` — объявление, `Load` — вызов `setdefault(...).append(...)`, то есть
запись. Ни одного чтения значения. Запах: Speculative Generality (структура
под будущую надобность), по факту — остаток промежуточной версии правки.

Коммит `3de3de5b`. Поведение ручки не меняется: набор `section_ids` делает
соседний `section_ids`, он читается в цикле выдачи.

**2. Тест счётчика `selectin` проходил на пустой базе.**
`backend/tests/test_dead_selectin_303.py::test_materializing_route_does_not_load_its_rules`
проверял `assert counter["n"] == 2`, но маршрутов в базе не было: `select`
отдавал ноль строк, selectin не срабатывал, и ассерт проходил, **ничего не
проверяя**. Защитный ассерт рядом — `assert rows is not None` — тоже ничего
не проверял: `.all()` не возвращает `None`.

Вторая ошибка в том же тесте, найденная при исправлении: счётчик считал **все**
`before_cursor_execute`, включая `SAVEPOINT`, который делает фикстура
(транзакция на тест по `backend/tests/AGENTS.md`). Поэтому «2» означало
«1 SELECT + 1 SAVEPOINT», а не «2 SELECT».

Замер на данных (5 маршрутов, у каждого этап), снят пробником до правки:

```
[probe] маршрутов: 5, запросов: 4
    SAVEPOINT sa_savepoint_3
    SELECT production_routes.id, production_routes.code, …
    SELECT route_stages.route_id, route_stages.id, …
    SELECT route_operations.route_stage_id, route_operations.id, …
```

То есть настоящая цена — **3 SELECT**, и «2» было правдой только потому, что
тест считал транзакционную обвязку вместо запросов.

Правка (коммит рядом, см. ниже): тест сам заводит маршруты со этапами;
`_counting` считает только `SELECT` и собирает список таблиц; вместо «число
упало» проверяется **причина** — `route_matching_rules` не должно быть среди
таблиц, плюс `counter == 3`.

Проверка чувствительности (обязательная: тест должен уметь падать). Подмена
`ProductionRoute.rules` обратно на `lazy="selectin"`:

```
FAILED test_dead_selectin_303.py::test_materializing_route_does_not_load_its_rules
AssertionError: потянулись правила маршрутов: ['production_routes',
  'route_stages', 'route_matching_rules', 'route_operations']
2 failed, 5 passed
```

Мутация откачена (`git checkout -- backend/app/models/route.py`).
На текущем коде: **7 passed**. До правки тот же откат проходил зелёным.

### Не исправлено (нужно решение)

**3. Осталось `select(Section)` в `_compute_excluded_sections` — общий код
#303, который сам срез правил в двух других местах того же файла.**
`backend/app/services/route_builder.py:509`:

```python
sections = (await db.execute(
    select(Section).where(Section.id.in_(excluded_ids))
)).scalars().all()
return {s.code for s in sections}
```

Читается только `.code`, а ORM-`Section` тянет три `selectin`-связи — то есть
здесь **тот же** класс затрат, который срез снимал в `load_route_build_batch_cache`
(строка 145) и `load_route_selection_batch_cache` (строка 555), и
`load_section_refs` под это уже написан и лежит рядом. Правка на
`SectionRef`/`select(Section.code)` тривиальна и по смыслу обязана быть сделана
в том же стиле.

Почему не починил: `_compute_excluded_sections` идёт по пути **без батча**
(`batch is None`). Замер «до/после» требует прогона с профилем, а этот путь
на живых данных не воспроизводится — ровно та ловушка, о которой писал оркестратор
в комментарии к #303 («профиль говорит о том, что *выполнялось*»). Без замера
число снятых запросов я назвать не могу, а правка без замера в этом классе
работ — ровно то, что тикет называет «отправлять сложность без измеримого
выигрыша смысла нет» (см. комментарий по доске). Влияет ли это на ответ —
не знаю; читается одно поле.

Смежное, тоже мимо правки: `plan_import_service.py:886` — `db.get(Section, …)`
в цикле по активным маршрутам, кэш `sections_by_id_cache` есть, но нужен
`section.is_active`, то есть ORM-объект. Там проекция не поможет, нужен
`select(Section.id, Section.is_active)`. Отдельная задача.

**4. `SectionRef` объявлен в шести полях, но `icon`/`icon_color` нужны только
одной ручке.** `backend/app/services/section_ref.py` — маршрутные сервисы
(`route_builder`, `route_selection`, `route_storage_classifier`) читают четыре
поля; `icon`/`icon_color` добавились ради `api/routes/routes.py`
`_section_step_fields`. Комментарий в модуле это признаёт.

Это Data Clumps наоборот: широкая проекция под один потребитель, и маршрутные
сервисы получают две лишние колонки. На 13 секциях цена нулевая, так что
правки это не требует — отмечаю как решение, а не как дефект: сузить проекцию
нельзя, не заведя вторую, и выигрыш от сужения не измерим.

### Запахи, найденные чтением (без правки)

* **Duplicated Code / shotgun:** перевод `Section` → колонки повторяется в
  трёх местах одним и тем же приёмом, и каждое место тянет свою локальную
  проекцию. `section_ref.py` — правильная абстракция, но её используют не все
  подходящие места (см. п. 3). Это расхождение между «появился метод» и
  «метод применяется», а не сам метод.
* **Speculative Generality:** `SectionLike = Union[Section, "SectionRef"]` в
  `route_storage_classifier.py` — объединение вместо узкого контракта. Читается
  одно поле `.type`, то есть годился бы `Protocol` с одним атрибутом; `Union`
  требует правки при каждом новом носителе `.type`. Оценочное суждение,
  правкой не является.
* **Primitive Obsession:** `stages_by_route: dict[int, list[tuple[int, int, int]]]`
  в `overview` — тройка `(id, section_id, sequence)` безымянна; её приходится
  распаковывать в цикле и читать по позициям. `ops_by_stage` — та же история с
  парой `(operation_name, operation_code)`. Обе структуры пережили перенос с
  именованных полей ORM на кортежи, и потеряли читаемость. Оценочное суждение.

### Проверка «мёртвые связи не читаются» — корректна

Отдельно проверил главный риск правки `lazy="selectin"` → `lazy="raise"`
(связь не нужна ≠ её не читает; об этом писал и сам срез):

* `ProductionRoute.rules` — потребителей нет: `backend/app/api/routes/routes.py:252`
  берёт правила отдельным `select(RouteMatchingRule).where(route_id=…)`;
  `grep '\.rules\b'` по `backend/app` даёт только совпадения в
  `route_builder`/`route_selection`, где речь о `batch.rules`
  (`RouteSelectionRule`, другой объект) и о поле `rule_profile_id`.
* `RouteRuleProfile.rules` — `load_selection_rules_for_profile` идёт прямо
  `WHERE profile_id IN (…)`.
* `StorageProductionGroup.sections` — `api/routes/spg.py` читает участки через
  `SpgSection` отдельной выборкой (`_build_spg_out`), обращений
  `spg.sections` в `backend/app` нет.

Записи через эти связи (`users.py:172,174,191,280,283,288` — `user.sections = …`)
при `lazy="raise"` не ломаются: append на непрочитанной коллекции не читает
её. `User.sections` возвращена в `selectin` осознанно (её читает свойство
`section_ids` через `from_attributes`) — это поправка инвентаризации, верная.

## #304 — кейс ленивого создания задачи в `/transfers/ready`

полностью изменённой ручке, если бы ключи остались.

AC #304, п. 4: «Ответ `/transfers/ready` до/после не изменился: JSON-сверка по
`task_id`, `dimensions`, `transferable_quantity`». Пункта `dimensions` в тесте
вообще не было — требование было заявлено и не выполнено.

Рядом мёртвый код: `shape = sorted(re.findall(r'"([a-z_]+)":', str(sorted(rows[0].keys()))))`
по списку ключей не находит ничего. Проверено: результат `[]`. И
`assert fx["product"].id  # фикстура живая` — тавтология, id ненулевой по
построению фикстуры.

Правка: тест переименован в `test_ready_response_identical_before_and_after_lazy_creation`
и сравнивает **полные списки строк** первого и второго GET — ленивое создание
не должно исказить ни `task_id`, ни `dimensions`, ни `transferable_quantity`,
ни состав/порядок. Ключи проверяются поимённо. Мёртвые `re`/`shape` и
тавтологический ассерт убраны. Прогон: **3 passed**.

Плюс убран дубль докстринга `_seed_case` — два подряд, остался только первый
(следствие линт-чистки `da6781da`, который правил импорты, а не докстринги).

### Не исправлено (нужно решение — это не ревью, а продуктовое решение)

**2. Сам выбор «запись остаётся или переносится» не сделан.**
Тикет, п. 3: «Решить по фактам, один из двух вариантов с измерением». Исполнитель
по комментарию решил **не решать** и передал решение владельцу, потому что
`app/transfers/` в том же модуле занят срезом A.

Это правильный по процессу ход, но по AC тикет остаётся открытым: из четырёх
пунктов приёмки закрыты «кейс построен» и «регресс #176», а решение и его
измерение — нет. Риск «GET, который пишет» в тикете **не зафиксирован**: при
выбранном варианте следовало записать его цену числом, этого нет.

Конкретика, которую стоит проверить при разборе: измерение автора даёт
`SELECT 8, INSERT 1` на одной строке без задания и `SELECT 16, INSERT 1` на
пяти, причём задание создаётся не для всех строк, а только для прошедших
бюджет (`queries.py:1103` — в `db.add_all` идут лишь budget-passing строки).
То есть «сколько запросов добавляет поштучный путь на N строках» из п. 2 AC
не измерено: `INSERT 1` на пять строк — это не «цена поштучного пути», это
«цена одной вставки».

### Ключевой механизм подтверждён по коду

`app/transfers/queries.py:975-994` — `is_new_task = fake_task is None`, и
`db.add_all(new_tasks)` на строке ~1103 после бюджетного фильтра. Это
подтверждает наблюдение автора про то, что вставок меньше, чем строк выдачи,
и что «GET, который пишет» ограничен одной вставкой на стоку, прошедшую бюджет.
