# T-296 — `/imports/{batch_id}/positions` на батче в сотни строк

## Проблема

Карточка пакета импорта звала `resolve_position_route` на каждую позицию без
LIMIT. На батче в 900 строк это **17 167 SQL-запросов**.

## Первый вопрос: не починено ли это уже смежными тикетами?

Прежде чем править, «после» снято на текущем `main` (где слиты #292, #297, #298)
и на моём коммите — то есть **до** единой строки в `imports.py`:

| Состояние | SQL |
|---|---|
| dev-данные до волны (91 позиция) | 1796 |
| `main` после #292/#297/#298 (900 позиций) | **17 167** |

Вывод: **смежные тикеты N+1 здесь не устранили** — `imports.py` никто не трогал,
и `Section` с тремя `lazy="selectin"` по-прежнему грузится по одной на позицию.
Чинить было нужно.

## Методика

Как в #290/#297/#298: прямой вызов ручки в транзакции с `rollback`, счёт SQL —
engine-слушатель `before_cursor_execute`/`after_cursor_execute`. «До» снято
`git stash`-снятием этой же правки на той же БД.

База — изолированный клон dev-данных, где батч 6 раздут до 900 позиций с
**уникальным** `source_payload` (в каждую дописан её `id`). Это существенно:
ключ локального кэша маршрутов включает `source_payload`, у реальных строк батча
из разных строк Excel он разный, и без этого локальная мемоизация схлопыла бы
повторы и N+1 не проявился бы.

На dev-данных мерить нельзя: батч один, 91 позиция.

## Замер

| | SQL | wall-мс | строк |
|---|---|---|---|
| До | 17 167 | 35 245.2 | 900 |
| После | **23** | 856.9 | 900 |

**−99.9% SQL**, wall −97.6% (под нагрузкой, время вторично).

Число запросов **не зависит от размера батча**: на 191 позиции в том же клоне —
те же 23 SQL. AC «число SQL не растёт с числом позиций» выполнен с запасом.

## AC «≤ 20 SQL» — не выполнен, 23

Честно: AC просил ≤ 20, получилось 23. Разница — 4 запроса, и они не в
`imports.py`. Это `select(Section)` **целиком**, без фильтра, в двух местах
общего кода маршрутов:

- `app/services/route_builder.py:144` — `select(Section)` для всех секций;
- `app/services/route_selection.py:551` — то же при построении
  `RouteSelectionBatchCache`.

Каждый такой вызов возвращает ORM-объекты `Section`, а у `Section` три связи с
`lazy="selectin"` (`users`, `operations`, `spg_links`) — то есть **1 запрос +
3 дочерних = 4**. Ровно эти 4 видны в профиле остатка:

```
x1  SELECT sections.id, sections.code, …
x1  SELECT spg_sections.section_id, storage_production_groups…
x1  SELECT user_sections.section_id, users.id, …
x1  SELECT section_operations.section_id, …
```

Плюс 5 запросов справочников маршрутов, которые срабатывают дважды
(`import_batches`, `production_routes`, `route_stages`, `route_matching_rules`,
`route_operations`) — это внутренняя кухня `position_route_batch` из #292.

**Почему не починил:** `route_builder.py` и `route_selection.py` — общий код,
которым пользуется и `app/transfers/`, а по указанию оркестратора срез C
(#295/#299/#300) сейчас идёт в `app/transfers/`. Переписывать там выдачу
`Section`-объектов на колонки — это изменение общего контракта (потребители ждут
объекты), и оно задевает чужую зону работы. Это правильно сделать отдельным
тикетом на общий корень, а не замазать здесь.

Замечу: это **тот же корень**, что я чинил в #297 (`Section` + `lazy="selectin"`),
и он бьёт по всем спискам, включая transfers. Стоит вынести его в отдельную
задачу — тогда и #296 уйдёт ниже 20, и transfers получат то же лечение.

## Ответ не изменился

SHA-256 полного JSON ответа на 900 позициях (438 085 Б):

| | digest |
|---|---|
| До | `a8828699d02a67e7` |
| После | `a8828699d02a67e7` |

**Побайтово идентичен**, включая порядок позиций (`source_row_number`) и все
`route_id`/`route_source`/`route_origin`/`route_match_*`.

## Что сделано

`backend/app/api/routes/imports.py`, `list_import_positions`:

1. **Резолв маршрутов на батч** — `resolve_position_routes_batch(db, positions)`
   (контракт #292) вместо `resolve_position_route` в цикле с локальным кэшем.
2. **Имена продуктов — одним запросом по колонке.** Раньше на каждый новый
   `product_id` звался `db.get(Product)`, а у `Product` есть `column_property`
   с `EXISTS` по `product_pairs` и связи `processing_flags`/`composition` —
   на каждый продукт отдельная волна. Ответу нужно только `product.name`,
   поэтому ORM-объекты `Product` не грузятся вовсе.

Порядок позиций и набор полей ответа не менялись.

## Границы (что НЕ трогал)

- `route_builder.py` / `route_selection.py` — см. выше, намеренно не трогал.
- Остальные ручки `/imports/*` — не трогал.
