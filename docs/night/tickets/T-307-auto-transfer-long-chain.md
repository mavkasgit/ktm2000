# T-307 — авто-передачи: батчинг окупается на длинной цепочке

**Тикет:** #307 (остаток #300) · **Ветка:** worktree #307 · **Состояние: батчинг применён.**

## Кейс

`backend/tests/test_auto_transfer_batch_300.py`, фикстура `_prepare_long_chain`:

```
RAW → P1 → W1 → W2 → P2
```

* `P1` — производственный участок (СПГ по умолчанию), материал на него заведён
  приёмом `TRANSFER_RECEIVE` — иначе `complete_task` упадёт на `issued_quantity`;
* `W1`, `W2` — **транзитные** этапы (`stage_kind='transit'`,
  `storage_section_id` на `wip_stock`), каждый в своём СПГ;
* `P2` — производственный финальный этап в четвёртом СПГ; его задание ждёт
  материал (`waiting_previous`).

Три перехода `P1 → W1 → W2 → P2`, из них два — транзитные хопы. Длиннее
цепочку в текущем коде не сделать: `auto_create_transfer_after_complete`
продолжается только через `next_stage.is_transit`, после первого
производственного шага — `break`. Вариант 2 из тикета (несколько пар выходов)
не понадобился: длинная цепочка дешевле по фикстуре и разворачивает цикл
именно по шагам.

Замер — слушатель `before_cursor_execute` на engine, `transfer_send`
обёрнут вложенным счётчиком (`_measure_completion` в тест-файле), транзакция
теста откатывается фикстурой `session`. Счётчик сбрасывается перед
`complete_task`. Полный ответ пишется в `response_full`
(`json.dumps(..., sort_keys=True, default=str)`) и сверяется до/после по
рецепту [`docs/testing-guide.md`](../../testing-guide.md#замер-sql-допосле);
«до» снято на базе `126630c4` тем же тест-файлом (продуктовый код без
батчинга), «после» — на этой ветке, одно и то же подмножество тестов.

| `transfer_send` × 3 | 156 | 156 | 0 |
| время `complete_task`, мс (один прогон) | 449 | 326–466 | шум, вторично |

Полный ответ совпал побайтово (длинная цепочка, одна и та же БД и порядок
тестов):

```
{"completed_quantity": "100", "defect_id": null, "status": "completed", "task_id": 2, "transaction_ids": [3, 4]}
```

Передачи идентичны: `P1→W1→W2→P2`, по 100 шт, `dimensions=None`,
`accepted`, у каждой пара проводок `TRANSFER_SEND`/`TRANSFER_RECEIVE`.
Инварианты ledger'а зелёные.

Семь SELECT'ов цикла после правки: строки позиции (1), этапы (1) + selectin
операций этапов (1), СПГ всех секций (1), открытые задачи всех строк (1) и
два `db.get` задач, созданных самими передачами (identity map держит их
слабой ссылкой — те же два запроса были и до правки). Снимок фиксирован
(5 SELECT'ов), но каждый созданный передачей транзитный воркер-таск
по-прежнему читается отдельным `db.get`; на трёх переходах это 7 SELECT, на
более длинной цепочке вырастет на один запрос за хоп. До правки было
~7 SELECT'ов **на шаг**.

## Цена на короткой цепочке (#300)

| | до | после |
|---|---|---|
| `complete_task` всего | 96 | **97** |
| цикл (SELECT / всё) | 4 / 5 | 5 / 6 |
| `transfer_send` × 1 | 48 | 48 |

Один шаг и одна пара: поштучные `db.get` попадали в identity map и стоили
ноль, снимок добавил свой запрос. Это ровно результат #300 (96 → 97) и
осознанная цена: фиксированный проход окупается с третьего перехода.
Ответ на короткой цепочке тоже совпал побайтово:
`{"completed_quantity": "100", "defect_id": null, "status": "completed", "task_id": 9, "transaction_ids": [13, 14]}`.

Пороги закреплены двумя бюджетными тестами: `test_short_chain_sql_budget`
(5 SELECT в цикле, до правки — 4 при 96 всего) и `test_long_chain_sql_budget`
(не больше 8 SELECT, до правки — 22). У обоих есть нижняя граница, чтобы
поломка атрибуции фаз не превращалась в «0 ≤ порог»; на старом коде оба
падают.

## Что применено (строго по ТЗ T-300)

* строки позиции — один `select(SectionPlanLine)` по `plan_position_id`;
* этапы по id — один `IN`;
* членство секций в СПГ — один `select(SpgSection.section_id, spg_id)` на все
  секции цепочки; «общий СПГ» — пересечение множеств, потому что участок
  может состоять в нескольких СПГ (`uq_spg_sections` — на пару, не на
  участок). Точечный `sections_share_spg` читал одну произвольную строку
  (`db.scalar` без `ORDER BY`) и на таких данных отвечал
  недетерминированно; снимок отвечает по факту. Закреплено тестом
  `test_section_in_two_spgs_shares_any_membership`;
* открытые задачи всех строк — один `select(WorkTask)` с
  `status NOT IN (closed)`; сопоставление габаритов — в Python
  (`_dimensions_equal`), `None` матчит и SQL `NULL`, и JSON `null` так же,
  как `dimensions_match_clause`.

Снимок строк и задач упорядочен по id: прежние пошаговые чтения не задавали
`ORDER BY`, поэтому при дублях `sequence` (уникального
`(plan_position_id, sequence)` в схеме нет) или нескольких открытых задачах
выбор не был гарантирован. Снимок делает его стабильным — наименьший id.

`transfer_send`, формулы бюджета, побочные эффекты цепочки и миграции не
тронуты. Задачи, созданные передачами внутри цикла, добавляются в снимок
строки — следующая пара/шаг видит их так же, как увидел бы точечный SELECT.

## Правки после ревью (2026-10-25)

* `_share_spg` — пересечение множеств членства: участок может быть в
  нескольких СПГ, прежнее точечное чтение брало произвольную строку;
  добавлен тест `test_section_in_two_spgs_shares_any_membership`.
* Порядок снимка по id зафиксирован явно; снято неверное утверждение, что
  старый `db.scalar` возвращал «порядок вставки» — `ORDER BY` не было.
* У бюджетных тестов появились нижние границы; короткая цепочка получила
  свой `test_short_chain_sql_budget` (раньше порог был только в прозе).
* «До» снято на базе `126630c4` тем же тест-файлом, ответ сверяется полным
  JSON, а не четырьмя полями.
* Исправлено «число не зависит от длины цепочки»: снимок фиксирован, но
  каждый созданный передачей транзитный таск читается отдельным `db.get`.
