# T-289 — изоляция БД по воркерам Playwright

**Статус:** DONE (изоляция доказана; `workers: 1` в конфиге оставлен — решение человека)
**Ветка:** `night/2026-10-02-c`, база `7471b4e`
**SHA:** см. комментарий в #289

## Проблема

`--workers>1` был непригоден: 10 красных из 10 при ускорении ~4–5× (#253,
`T-253-workers2-series.md`). Механизм поломки — ровно тот, что тикет и называл:

`e2e:prep` даёт прогону **один клон** БД, а воркеры Playwright внутри прогона
делят его. `apiResetAll()` в `beforeEach` — `TRUNCATE … CASCADE` по таблицам,
поэтому параллельные файлы сносили данные друг друга (профиль #253:
`sawing-four-lengths-cycle` 17/17, `transfers-auto-accept` 11/17, …).

## Что сделано

Клон на воркера, а не на прогон. У каждого воркера своя БД **и свой backend**,
а общий адрес `/api` стенда разводит роутер по заголовку `x-e2e-worker`.

| Файл | Что |
|---|---|
| `scripts/e2e-db.py` | `prep --workers N` (`E2E_WORKERS=N`) клонирует шаблон N раз: `<база>_run_<stamp>_<run-id>_w<i>` + свой env-файл. `E2E_RUN_ENV_FILES` (JSON) — все; `E2E_RUN_ENV_FILE` — первый, прежний. `drop --run-id` снимает все клоны прогона. При `N == 1` имена прежние. |
| `frontend/scripts/e2e-api-router.mjs` | **новый.** Роутер `/api` и `/static`: backend по `x-e2e-worker`, без заголовка — слот 0. |
| `frontend/scripts/run-e2e.mjs` | Выдаёт `WORKERS + 2` портов (backend на воркера, роутер, frontend), поднимает роутер и снимает его с прогоном. |
| `frontend/playwright.config.ts` | `webServer`: backend на каждый воркер (свой `ENV_FILE`, свой `BACKEND_PORT`); `VITE_PROXY_TARGET` уводит на роутер. Проверка равенства числа env-файлов и backend'ов. |
| `frontend/e2e/worker-slot.ts` | **новый.** Слот = `workerIndex % E2E_WORKERS`. |
| `frontend/e2e/fixtures.ts` | `extraHTTPHeaders` = `x-e2e-worker: <слот>`. |
| `frontend/e2e/api-helpers.ts` | `BACKEND_URL` — адрес backend'а **своего** слота; сид берёт DSN из env-файла своего клона. |

### Три находки, которые стоили больше всего

1. **`router` в `server.proxy` vite не работает.** Опция есть у http-proxy, но в
   сборке vite 6.4.2 она **молча игнорируется**: заголовок `x-e2e-worker: 1`
   дошёл до backend 0 (проба). Тихий увод в чужой backend опаснее отсутствия
   фичи — тест был бы зелёным на данных соседа. Поэтому роутер вынесен в
   отдельный процесс.
2. **`workerIndex` — не номер среди живых воркеров.** Это сквозной счётчик
   процессов: на `--workers=2` доходили `workerIndex` 2, 3, 4 → `urls[4]`
   при двух адресах. Слот считается по модулю числа воркеров.
3. **Прямые вызовы из Node идут мимо заголовка.** `api-helpers` бил в `E2E_API_URL`
   (всегда backend 0): воркер сеял в чужую БД, а страница работала со своей.
   Отсюда падения входа и «не нашёлся task».

## Доказательство

Проба изоляции в настоящем стенде (`--workers=4`, 4 файла, чтобы работа
разошлась по воркерам): каждый воркер пишет метку `E2E-ИЗОЛЯЦИЯ-<слот>` в свою
БД, проверяет, что чужих меток у него нет, зовёт `reset-all` и убеждается, что
свои данные на месте.

Причина установлена — это отдельный тикет **#302**: дневные коммиты `470a9ce`
(два режима ввода факта: «+100» добавить, «500» факт станет 500), `446d8a3`

новой семантике означает «факт станет 75» — на второй порции это уменьшение,
которое сервер отклоняет законно, и диалог остаётся открытым. Состояние
диалога в момент падения: `Вход: 150 … Раскроено: 75 … Осталось: 75`.
Устарели тесты, продуктовая логика не сломана.

**Приёмку «0 флейков» на этом срезе закрыть нельзя:** красные два теста падают
