# T-289 — изоляция БД по воркерам Playwright

**Статус:** DONE по изоляции; приёмка `workers=2` не закрыта — чистый
перепрогон 2026-10-25 дал **1 падение в 10 прогонах**, `workers: 1` в конфиге
не переключён.
**Ветка:** `night/2026-10-02-c`, база `7471b4e`
**SHA перепрогона:** `e45148f6` (`e45148f62ca7c3e880f91e8ecbb6f39beb4059a0`)

## Проблема

`--workers>1` был непригоден: 10 красных из 10 при ускорении ~4–5× (#253,
`T-253-workers2-series.md`). Механизм поломки — ровно тот, что тикет и называл:

`e2e:prep` даёт прогону **один клон** БД, а воркеры Playwright внутри прогона
делят его. `apiResetAll()` в `beforeEach` — `TRUNCATE … CASCADE` по таблицам,
поэтому параллельные файлы сносили данные друг друга (профиль #253:
`sawing-four-lengths-cycle` 17/17, `transfers-auto-accept` 11/17, …).

## Что сделано

Клон на воркера, а не на прогон. У каждого воркера своя БД **и свой backend**,
а общий адрес `/api` стенда разводит роутер по заголовку `x-e2e-worker`.

| Файл | Что |
|---|---|
| `scripts/e2e-db.py` | `prep --workers N` (`E2E_WORKERS=N`) клонирует шаблон N раз: `<база>_run_<stamp>_<run-id>_w<i>` + свой env-файл. `E2E_RUN_ENV_FILES` (JSON) — все; `E2E_RUN_ENV_FILE` — первый, прежний. `drop --run-id` снимает все клоны прогона. При `N == 1` имена прежние. |
| `frontend/scripts/e2e-api-router.mjs` | **новый.** Роутер `/api` и `/static`: backend по `x-e2e-worker`, без заголовка — слот 0. |
| `frontend/scripts/run-e2e.mjs` | Выдаёт `WORKERS + 2` портов (backend на воркера, роутер, frontend), поднимает роутер и снимает его с прогоном. |
| `frontend/playwright.config.ts` | `webServer`: backend на каждый воркер (свой `ENV_FILE`, свой `BACKEND_PORT`); `VITE_PROXY_TARGET` уводит на роутер. Проверка равенства числа env-файлов и backend'ов. |
| `frontend/e2e/worker-slot.ts` | **новый.** Слот = `workerIndex % E2E_WORKERS`. |
| `frontend/e2e/fixtures.ts` | `extraHTTPHeaders` = `x-e2e-worker: <слот>`. |
| `frontend/e2e/api-helpers.ts` | `BACKEND_URL` — адрес backend'а **своего** слота; сид берёт DSN из env-файла своего клона. |

### Три находки, которые стоили больше всего

1. **`router` в `server.proxy` vite не работает.** Опция есть у http-proxy, но в
   сборке vite 6.4.2 она **молча игнорируется**: заголовок `x-e2e-worker: 1`
   дошёл до backend 0 (проба). Тихий увод в чужой backend опаснее отсутствия
   фичи — тест был бы зелёным на данных соседа. Поэтому роутер вынесен в
   отдельный процесс.
2. **`workerIndex` — не номер среди живых воркеров.** Это сквозной счётчик
   процессов: на `--workers=2` доходили `workerIndex` 2, 3, 4 → `urls[4]`
   при двух адресах. Слот считается по модулю числа воркеров.
3. **Прямые вызовы из Node идут мимо заголовка.** `api-helpers` бил в `E2E_API_URL`
   (всегда backend 0): воркер сеял в чужую БД, а страница работала со своей.
   Отсюда падения входа и «не нашёлся task».

## Серия 2026-10-24/25 при чужой нагрузке — не приёмка

Изоляция уже слита в `main`; здесь — первая попытка проверить условие
переключения `workers` из тикета: 10 последовательных прогонов подмножества
`smoke + ui-narrow` при `--workers=2 --retries=0`, `CI` пуст.

**Эта серия приёмкой не является.** Двухосевой разбор нашёл четыре причины:

1. **Общий namespace вместо своего.** Прогоны шли на трекаемом `.env.e2e`
   (база `ktm2000_e2e`), а не на нетрекаемом `.env.e2e.<имя>.local` со своей
   базой и `STORAGE_ROOT`, как требуют §1 п.3 и §5 «Подготовка свежего
   worktree» канона. Чужая база стенда — это общий `apiResetAll()`, то есть
   ровно тот риск, ради устранения которого делалась изоляция.
2. **Машина была занята.** В части окна (23:20–23:31) соседний агент гонял
   backend pytest — логи в worktree `agent-general-purpose-92518cfd`
   (`logs/pytest-*.log`). #289 требует свободной машины: «чужие
   vitest/pytest/playwright искажают и флейки, и времена».
3. **Нет обязательных полей отчёта.** Ни SHA, ни точной команды, ни состояния
   `CI`, ни строки «клон прогона …» — без них прогон не доказывает, что шёл
   на своём клоне и на той ревизии.
4. **Wall включает `e2e:prep`.** `startedAt` в `frontend/e2e/run-tier.mjs`
   ставится до `e2e:prep`, поэтому «Wall» ниже — это подготовка + прогон +
   уборка, а не время тестов.

**Стенд:** worktree `agent-general-purpose-368fedc2`, база `ktm2000_e2e`
(шаблон + два клона на прогон: `…_w0`, `…_w1`), Postgres `:5441`, два
backend'а и роутер на свободных портах. Команда:

### Падение прогона 7

`[ui-narrow] sawing-four-lengths-cycle.spec.ts:314:3` — это строка
**объявления теста** (внутри `test.describe`), её печатает Playwright в

отрисовать маршрут. Признаков конфликта данных нет: у каждого воркера свой
клон (`…_w0`/`…_w1`) и свой backend (порты 65195/65196), чужой `TRUNCATE` в
логе не проявляется. В трёх контрольных прогонах (11–13) и остальных девяти

не вывод.** Она опиралась на занятую машину, а чистый перепрогон (ниже)
воспроизвёл то же падение при пустой машине, поэтому «под нагрузкой» не
объясняет его. Факт из этой серии: API отвечал `200 OK`, после `goto`
запросов `/api/sections` нет, у каждого воркера свой клон и свой backend.
Кандидаты на отдельную работу остаются: бюджет ожидания заголовка, повтор
`goto` при его отсутствии (не ослабляя проверки), изоляция frontend по
воркерам.
