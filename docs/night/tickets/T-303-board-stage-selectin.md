# T-303 (доска участка) — инцидентный selectin оказался не инцидентным: правку откатил

- **Категория:** производительность / отрицательный результат инвентаризации
- **Статус:** DONE — измерено, правка откачена, код доски не тронут
- **Дата:** 2026-10-03, ночная смена, срез D
- **Тикет:** [#303](https://github.com/mavkasgit/ktm-2000/issues/303), пункт 4 инвентаризации
- **Основание:** `docs/night/tickets/T-303-inventory.md`, п. 4 «`board:241,262` — `select(RouteStage)` ради `route_id`/`section_id`»

## Что предлагала инвентаризация

`all_stages` в `get_section_board` грузится как ORM-сущности `RouteStage`, а у
них `operations` объявлены `lazy="selectin"`. Вывод инвентаризации: ручка
использует отсюда только `route_id`/`section_id`, а операции грузит явно ниже,
значит selectin-батч инцидентный и его можно убрать.

## Что показал замер

Методика #290/#303: прямой вызов `get_section_board`, счёт SQL — engine-слушатель
`before_cursor_execute`, данные — синтетика (участок, 5 и 100 заданий, маршруты
по два этапа, чтобы у задания был следующий этап).

| Сценарий | SQL до | SQL после |
|---|---|---|
| 5 заданий | 16 | **16** |
| 100 заданий | 16 | **16** |

**Правку откатил: выигрыша нет.** Отчёт доски при этом остался побайтово тем же
(сверено на 5 и 100 заданиях) — рефакторинг вел себя нейтрально, но не снимал
ни одного запроса.

## Почему инвентаризация ошиблась

Предпосылка «операции отсюда не читаются» неверна: они читаются в двух местах,
и оба — из `all_stages`:

1. **История маршрута** (`queries_sections.py:498,500,511,512`): у каждого
   предыдущего этапа берётся `s.operations[0]` — код и имя операции, иначе
   строка истории осталась бы пустой.
2. **Подпись следующего этапа** (`:579`): `next_stage.operations` склеивается в
   `next_operation_name`.

Поэтому «убрать инцидентный selectin» значит заменить его **явным батчем** по тем
же операциям. Один батч на все этапы маршрутов стоит ровно столько же, сколько
стоил selectin-батч: 16 → 16. Выигрыш возможен, только если исчезнут **оба**
батча разом, а для этого пришлось бы перестать материализовывать `RouteStage` ещё
и в **главной** выборке доски — там `stage.operations` нужен для
`operation_codes`/`operation_names` строки (`:607-614`). Это уже переписывание
главной выборки.

## Состав 16 запросов доски (сверка с инвентаризацией)

Явные батчи: `count(*)`, главная выборка, `route_stages` (справочник этапов),
`section_plan_lines`, `plan_positions`, `product_pairs` (EXISTS на парность),
`product_lengths`, `work_tasks` (задания линий), `section_operations` (явный, с
`ORDER BY` — инвентаризация правильно не считает его ленивым),
`stock_transactions` (прогресс), два запроса балансов (`bulk_send`/`bulk_recv`).

Ленивых на доске ровно **два**, оба — `route_operations`: один для `RouteStage`
из строк доски, второй для `all_stages`. Связей `Section` (`users`/`operations`/
`spg_links`) на доске **нет вообще**: секции там — целые числа из колонок,
ORM-объект `Section` не материализуется. Это подтверждает общий вывод
инвентаризации и уточняет его по доске.

## Что предлагаю

Не трогать доску в этом ключе. Снять ещё один запрос можно только переписыванием
главной выборки (заменить `RouteStage` в `select` на колонки и перевести
`operation_codes`/`operation_names` на общий снимок операций). Это отдельная
задача с отдельным замером, и она задевает `in_daily_plan` из #301.
