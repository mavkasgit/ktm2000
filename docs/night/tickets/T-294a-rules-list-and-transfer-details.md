# T-294a — точечные N+1: список правил подбора и детали передачи

**Тикет:** #294, места 1 и 3 · **Ветка:** `night/2026-10-02-a**
Места 2 и 4 не взяты (см. «Что осталось»).

## Место 1 — `GET /route-selection-rules`

`_rule_out` на каждое правило читала участки (`select(Section).where(id.in_(...))`),
операции участка (`select(SectionOperation).where(section_id == sid)` — кэш
только внутри одного правила) и профиль (`db.get(RouteRuleProfile, ...)`).

Сделано: `RuleOutPrefetch` + `_load_rule_out_prefetch` + `_rule_outs` — снимок
справочников на весь список (3 запроса: участки, операции, профили), после чего
`_rule_out` ходит только в память. Одиночный вызов `_rule_out(db, rule)` без
снимка сохранён как был — им пользуются создание и правка правила.

## Место 3 — `get_transfer_details`

На каждое `TransferDiscrepancy` уходил свой `select(TransferDiscrepancyDefectItem, DefectItem)`.
Сделано: один запрос по всем расхождениям (`IN (...)`) с группировкой по id.
Порядок ссылок внутри расхождения теперь задан явно (`ORDER BY
transfer_discrepancy_id, id`) — раньше он был произвольным, без `ORDER BY`.

**Разница по месту 3 на dev-данных нулевая, и это не ложное срабатывание, а
отсутствие данных:** в базе владельца **0 расхождений передач** и 0 ссылок на
дефекты (проверено `SELECT count(*)`), поэтому цикла не выполняется ни разу и
обе версии стоят одинаковые 2 запроса (сама передача + пустой список
расхождений). N+1 проявляется только на передаче с расхождениями; на таких
данных он и устранён, но измерить его на этой базе нельзя. Доказательство правки —
прямой прогон функции на dev-данных (2 SQL, ответ без ошибок) и устранение запроса
из кода.
