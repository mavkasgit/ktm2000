# T-293 — Доска участка: батчевый transform_progress и хэнджер без per-парных запросов

- **Категория:** производительность (N+1 на поллимом экране)
- **Статус:** DONE
- **Дата:** 2026-10-03, ночная смена, срез D
- **Тикет:** [#293](https://github.com/mavkasgit/ktm-2000/issues/293)
- **Файлы:** `backend/app/services/shopfloor/task_status.py`,
  `backend/app/services/shopfloor/queries_sections.py`,
  `backend/app/services/plan_position_hanger.py`,
  `backend/app/services/product_pair_resolver.py`

## Проблема и доказательство

Доска (`GET /shopfloor/sections/{id}/board`) — поллимый экран, и два её пути
росли линейно с числом заданий:

1. `sync_work_task_status` на каждое трансформирующее задание звал
   `get_transform_progress(db, task.id)` — свой `GROUP BY` на задание, хотя
   `get_transform_progress_bulk` на той же доске уже посчитан строкой выше и
   результат просто не переиспользовался.
2. `resolve_positions_hanger` на каждую парную позицию без снапшота тянул
   `SELECT * FROM product_pairs` + `SELECT products` (поштучный поиск пары без
   кэша справочника), а по найденной паре — ещё и `product_lengths`.

Замер (методика тикета): прямой вызов `get_section_board` в тестовой БД, счёт
SQL — engine-слушатель `before_cursor_execute`. Данные — синтетика нужного
масштаба (участок с маршрутом из одного трансформирующего этапа, парные позиции с
компонентами, которые есть и которых нет в справочнике пар).

### До (замер на коде без правки, `logs/measure-293-BEFORE.md`)

| Сценарий | SQL |
|---|---|
| 5 заданий, пара разрешается | 28 |
| 5 заданий, пары нет в справочнике | 28 |
| 100 заданий, пара разрешается | 218 |
| 100 заданий, пары нет в справочнике | 218 |

Разложение по 100 заданиям: 101 `SELECT stock_transactions … GROUP BY` (по
одному на задание), 100 `SELECT product_pairs`, 100 `SELECT product_lengths`.

## Что сделано

1. **Прогресс трансформации переиспользуется.** `sync_work_task_status` принял
   готовый снимок `TransformProgress`; `sync_work_tasks_status_bulk` — карту
   батча, а без неё считает её сам одним запросом. Доска передаёт свою
   `transform_progress_map`. Ключевая тонкость: `get_transform_progress_bulk`
   не возвращает задания без движений, и в батче это «нули», а не «не
   спросили» — иначе код тихо падал обратно в поштучный запрос. Контракт
   записан в докстринге параметра.
2. **Набор id для батча — объединение предикатов.** Синхронизация статусов
   смотрит на `input_quantity` + `outputs`, а карточки — на маркер этапа
   `transforms_dimensions`. Список id расширен до объединения, поэтому карта
   покрывает оба потока. Набор для вывода не изменился: гейт построения
   `outputs_progress` по-прежнему требует `transforms_dimensions`.
3. **Хэнджер парных позиций.** Справочник пар читается один раз на вызов через
   `PairResolutionCache` (уже есть в репозитории после #292) вместо поштучного
   `SELECT * FROM product_pairs` на позицию; длины всех пар батча собирает новый
   `pair_length_candidates_bulk` — один `SELECT product_lengths` вместо одного
   на пару. Разбор по парам вынесен в чистую функцию, общую для одиночного и
   батчевого пути, поэтому значения совпадают по построению. Мёртвый
   `_resolve_paired_position_hanger` удалён.

## Ответ доски не изменился

Полный JSON ответа доски снят на коде до и после (`logs/board-before-*.json` /
`logs/board-after-*.json`, `sort_keys`, четыре сценария: 5 и 100 заданий, пара
разрешается и нет). Файлы **побайтово идентичны** — задачи, статусы, прогресс,
`outputs_progress` и `in_daily_plan` (пункт самопроверки: аддитивный признак
из #301 пережил переписывание выборки) совпадают.

## Про flush в GET

Запись статусов не убрана и не размножилась: `sync_work_tasks_status_bulk`
по-прежнему делает **один** `flush` на весь батч. Отдельный тест считает
savepoint'ы (их и порождает `flush` в asyncpg-сессии) на доске из 20 заданий —
ожидается не больше одного. Статусы синхронизируются по-прежнему: тест с
полностью списанным входом проверяет, что доска переводит задание в
`completed` — то есть карта батча даёт тот же прогресс, что и поштучный запрос.

## Проверенные тесты (`backend/tests/test_section_board_batching_293.py`)

- `test_board_sql_does_not_grow_with_transform_tasks` — 5 против 100 заданий;
- `test_board_sql_does_not_grow_with_paired_positions` — 5 против 100 парных позиций;
- `test_board_still_flushes_status_writes_once_per_board` — один flush на доску;
- `test_board_syncs_transform_status_from_ledger` — статус по ledger ставится.

Оба «не растёт» — настоящие охранники: на коде без правки они падают
(`5 заданий → 23 SQL, 100 → 117` и `5 парных позиций → 28 SQL, 100 → 217`).

## Границы: что НЕ трогали

- **Выборку доски не переписывал** — правил только то, что после неё: набор id
  для батча и передача готовой карты. Конфликта со срезом, который переписывает
  выборку целиком, не возникло.
- `sync_work_task_status` (одиночная функция) сохранила прежнее поведение: без
  готового снимка она по-прежнему считает прогресс сама.
- `plan_import_service.py` — свой поштучный кэш пар там не трогал: он в другом
  экране и вне тикета.
- Про `Section.users/operations/spg_links` (`lazy="selectin"`, общий корень среза B):
  на доске не проявляется — доска грузит `SectionOperation` явным `select`, а
  экземпляры `Section` в этом пути не создаются; в замерах доски таких запросов
  нет ни одного. Тикет не мой.
- Фронт не трогал вовсе.
