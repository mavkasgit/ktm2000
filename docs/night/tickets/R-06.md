## #287 — флейк e2e `transfers-auto-accept` (`fc82e2f2`, `eda86db7`)

Коммиты среза — только правка `docs/night/MORNING_REPORT.md`. Кода в срезе нет:
причина диагностирована и оставлена на отдельный заход. **Я эту причину
проверил и починил** — она живая.

### Исправлено (лёгкое)

**План импорта не виден клиенту в момент ответа → 404 в `apply`.**

`POST /api/imports/excel` (`imports.py:107`) и `/excel/simulate` (`:327`) отдают в
ответе `production_plan_id`/`change_set_id`, по которым e2e сразу бьёт
`apply` (`transfers-auto-accept.spec.ts:88`). Ни один из обработчиков не
коммитил: `grep -c commit backend/app/api/routes/imports.py` → **0**. Коммит
делал teardown зависимости `get_db`.

Докстринг `core/database.py:18-36` называет эту ловушку прямо, и она
подтверждается кодом установленного FastAPI: в
`fastapi/routing.py:147-152` (`request_response`) `response = await f(request)`
идёт **внутри** `function_stack`, а `request_stack` — та, что держит
`yield`-зависимости — выходит **после** `await response(scope, receive, send)`
на `:152`. То есть коммит после ответа клиенту.

**Доказательство «до/после», а не рассуждение.** Тест-регресс
`backend/tests/test_import_commits_before_response.py` повторяет харнесс
`test_bulk_approve_commit.py`: зависимость `get_db` подменена такой, чей
teardown делает **rollback**, поэтому выживает ровно то, что обработчик
закоммитил сам — отложенный коммит убран из проверки намеренно.

### Проверено — остальные пункты разбора не подтвердились как отдельные причины

- **`apiResetAll` в `beforeEach` ни при чём** — п. 4 диагностики в комментарии
  тикета. Он чистит состояние, но не мог вызвать 404 «Production plan not
  found» сам по себе: план в этом прогоне создаётся заново после сброса, и
  причиной может быть только момент его фиксации в БД.
- **Единственный источник этой строки 404** — `_require_visible_plan`
  (`production_plans.py:93-99`), вызываемая первой строкой `apply`
  (`:305`): `await _require_visible_plan(db, production_plan_id)`. Второй 404
  в этом обработчике — «Набор изменений не найден», другая строка; в отчёте
  флейка именно «Production plan not found».
- **`apply` не архивирует план сразу после импорта**: `_reject_legacy_plan_mutation`
  и `apply_change_set` не меняют `deleted_at` на этом пути; гипотеза «импорт
  архивирует план» из «Границ» тикета не подтвердилась — 404 даёт именно
  отсутствие фиксации, а не фильтр видимости.
- **Гонка в тесте?** Нет: спека делает два последовательных `await`
  (`apiSimulatePlanImport` → `apiApplyChangeSet`), узкое место — между
  транзакцией импорта и её фиксацией, а не между строками спеки.

### Не исправлено (нужно решение)

**Остальные мутирующие роуты импорта.** Коммит-до-ответа я поставил двум
точкам, где id сущности **уходят в ответе** и клиент идёт за ними сразу.
Остальную ручку по grep я не трогал: их карта — отдельная работа, а граница
«правка — в бэкенде, не в тесте» из тикета соблюдена.

**Признак закрытия — красный без retry больше не воспроизводится.** Правка
убирает конкретный 404 в сетапе и доказана тестом, но серия прогонов e2e
(`--retries=0`, слот семафора) ночью не гонялась — по регламенту слоты e2e
достались не всем. Закрывать тикет по одному зелёному прогону рано; нужно
прописать в тикете, что кодовая часть сделана, а критерий «красный без retry»
ещё не закрыт.

## #286 — домен «Размера» на доске (`3d7619ad`)

Тикет закрыт, решение принято и зафиксировано в ADR-0063. **Расхождений с AC
не нашёл** — все три вопроса тикета отвечены, каждое изменение снабжено
адресной причиной.

### Проверено — решения тикета закрыты

AC тикета — три вопроса без формальных критериев приёмки, поэтому проверял
по существу:

1. **«Какой домен считать размером»** — `WorkTask.dimensions`, и это ровно то
   поле, что сравнивает фильтр (`queries_sections.py:159`
   `dimensions_match_clause(WorkTask.dimensions, dims)`) и по которому идёт
   сортировка (`:81`). ADR-0063 «Решение» + «Рассмотренные варианты» (3
   варианта с отклонениями).
2. **«Как оператор должен видеть это в UI»** — одной колонкой; раскрой
   «вход → распилы» уносится в «Операцию» (ADR-0058), второй вариант
   отклонён явно.
3. **«Распространить справочник на „Размер“»** —
   `BOARD_COLUMN_VALUE_FIELDS = {"product_sku", "dimensions"}` (`queries_sections.py:672`),
   фронт: `BOARD_SERVER_VALUE_FIELDS = ["productSku", "dimensions"]`
   (`boardQueryParams.ts:101`). Про «остальные серверные колонки» — их в
   доске ровно эти две (`buildBoardServerQueryParams` отдаёт
   `search | product_sku | dimensions | sort`), так что «остальные» закрыты
   автоматически.

**Значение справочника действительно сужает выборку** — это главный риск тикета,
и он покрыт тестом `test_column_values_dimensions_narrow_the_board`: при
`transforms_dimensions=True` и `input_dimensions={"length_mm":3000}` против
`dimensions={"length_mm":2000}` справочник отдаёт `'{"length_mm":2000}'`, а доска
по этому значению отдаёт `total == 2`. То есть ровно тот случай, из-за которого
«Размер» раньше держали вне справочника.

**Безразмерные — одно значение.** Тест
`test_column_values_dimensions_offer_dimensionless` смешивает SQL `NULL` и
JSON `null` и ждёт `["null", '{"length_mm":2000}']`. Проверил порядок в
Postgres пробой (проба удалена), а не по комментарию: при
`ORDER BY v ASC NULLS FIRST` Postgres даёт
`[NULL, 'null', '{"length_mm": 2000}', '{"length_mm": 3000}']` — SQL `NULL`
первым, JSON `null` следом, и `dict.fromkeys` сличает их в одно значение. Так
что `nulls_first()` тут корректен, а комментарий в коде (`queries_sections.py:726-728`)
точно описывает поведение.

### Замечания (не блокеры)

**1. Standards — `values[].union` двух представлений NULL в строках, не в SQL.**
`queries_sections.py:740-745`: для `dimensions` значения сливаются после
сериализации (`json.dumps`), потому что SQL-уровня `DISTINCT` на паре
`NULL`/`'null'::jsonb` не существует. Работает (доказано выше), но список
значений перестаёт быть чистой проекцией SQL — и `truncated` (`:752`) считается
по `len(rows)`, то есть по строкам **до** сличания. На малых данных не видно,
но если безразмерных строк много, поповер может показать «—» и обрезать список
раньше, чем оператору реально упёрся в лимит. При `BOARD_COLUMN_VALUES_LIMIT=200`
и типовом dozen-е значений это не проявляется; отмечаю как границу, а не как
дефект — правка меняет контракт `truncated`, это не лёгкое.

**2. Standards — «—» первым строкой поповера, но не первым в `values`.**
Комментарий обещает «„—“ идёт первой строкой независимо от способа хранения
NULL». Для JSON-`null`-без-SQL-`NULL` наборов это верно; проверенный порядок
`[NULL, 'null', …]` означает, что при **отсутствии** SQL `NULL` JSON `null`
окажется не первым элементом списка, если Postgres отсортирует его иначе.
На данных с обоими представлениями (проверочный кейс) — первым. Формулировка
комментария чуть сильнее гарантии кода; поправил бы текст, но это правка
комментария в коммите, уже прошедшем ревью других, — оставляю владельцу.

**3. Scope creep — оценён и принят.** ADR-0063 затронул «Выдачу» плана участка
(`planTableRows.ts`): строка «Выдачи» теперь по габариту задания, а не по
входу. Это выходит за буквальные три вопроса тикета, но прямо следует из
решения — иначе «Выдача» печатала бы размер, которого в колонке «Размер» нет.
ADR фиксирует это в «Плохо» («на многоосном входе печатает длину»), то есть
цена названа явно. Не scope creep, а следствие решения.

**4. Переименование тестов по смыслу, а не по функции** — соответствует
`backend/tests`/`frontend` правилам: «резка не меняет домен размера» вместо
«берёт вход».

## #288 — файлы-сироты в хранилище импортов (`7c269e50`, `a8846160`)

Тикет в `needs-triage`, код в срезе не трогал — правильно: он просит **решения
владельца** (судьба файла при удалении батча, retention-политика), а не правки.

### Найдено: механизм, порождающий сироты, назван в коде

Тикет фиксирует картину «файлы на диске без строки в `import_files`» и просит
решить, чья это вина. Ответ в коде есть, и он конкретный:

`backend/app/seeds/seeders/cleanup_seeder.py:59-64` — при очистке
генерируемых данных **удаляет строки** `import_files`, на которые больше не
ссылается ни один `import_batch`:

```python
result = await db.execute(
    delete(ImportFile).where(
        ~exists().where(ImportBatch.source_file_id == ImportFile.id)
    )
)
```

Файл на диске при этом **не трогается**: запись создаётся как
`<sha256><ext>` (`plan_import_service.py:538-539`, `stored_path`), и удаления
файла из кода нет — `grep` по `backend/app` на удаление `stored_path` даёт
только чтение (`imports.py:653`, `import_history_api.py:231`). То есть
`db:seed --force` / очистка делает ровно то, что описано в тикете: метаданные
исчезают, байты остаются. Это и есть источник «накопителя, который растёт
молча» (п. 1 тела тикета) — не гипотеза, а конкретная строка.

Следствие для решения владельца: сироты **воспроизводимы**, поэтому команда
уборки (п. 2 тела тикета) без учёта этого пути будет бить по живым данным —
например, файл, чей батч откатили, станет сиротой и попадёт под retention.

### Проверено — остальные утверждения текета по коду верны

- **П. 2 «файл нельзя достать штатно»** — подтверждаю: `download_import_file`
  (`imports.py:641-651`) сначала делает `db.get(ImportFile, file_id)` и на
  отсутствии строки отдаёт 404, не доходя до диска. Ровно тот путь, которым
  «пропал» оригинал для #279.
- **П. 3 «импорт остатков зависит от того же каталога»** — подтверждаю по
  коду: `import_history_api.py:231` тянет `ImportFile` по `batch.file_id` и
  на `None` отдаёт 404. Модель `ImportBatch.source_file_id` — NOT NULL FK на
  `import_files.id` (`models/imports.py:52`), то есть удаление строки ломает и
  эту ручку тоже.

### Не проверено — честно

**Числа из тела тикета (2 строки / 9 файлов / 7 сирот в dev, 4 файла в prod)
перепроверить не удалось:** хранилище в моём worktree пусто —
`ls data/storage-dev/imports` → 0, `ls data/storage-prod/imports` → 0, каталога
`data/` в дереве нет вовсе. Dev-БД я не поднимаю (`db:up` запрещён регламентом),
поэтому таблицу `import_files` тоже не смотрел. **Проценты и конкретные файлы
из тела тикета я принимаю на верфь автора, а не проверял.** Структурная часть
(владелец файла — строка `import_files`, удаление строк без удаления файлов,
404 в двух местах) проверена и верна.

## Запахи — суждение по срезу

- **Duplicated Code**: новых нет. В #286 вместо дублирования выбран общий
  источник (`taskGroupingDimensions`), это ровно то, чего требовал тикет.
- **Repeated Switches / Feature Envy / Primitive Obsession**: не проявляются;
  диффы малы и локальны по домену.
- **Mysterious Name**: имена ADR-0063 и комментариев проясняют домен, а не
  добавляют новый словарь.
- **Speculative Generality**: один спорный случай — `BOARD_COLUMN_VALUE_FIELDS`
  остаётся `frozenset` из двух элементов с ветвлением по строке
  (`_board_value_expression`). На две колонки это оправданно; на третью
  понадобилась бы карта «колонка → выражение». Не трогал: это предпосылка
  следующего расширения, а не дефект текущего.
