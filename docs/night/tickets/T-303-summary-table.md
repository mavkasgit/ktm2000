# T-303 — сводная таблица замеров «было / стало»

Одна таблица по всей линии #303 вместо чтения пяти тикет-файлов. Только для
утреннего отчёта; детали и обоснования — в файлах, перечисленных внизу.

**Методика везде одна:** прямой вызов ручки/сервис-функции в транзакции с
`rollback`, счёт SQL — engine-слушатель `before_cursor_execute` /
`after_cursor_execute`, dev-данные `:5440/ktm2000_prod` только на чтение,
«после» сравнивается с «до» через `git stash` **той же правки на той же БД**.
Время замеров под нагрузкой и вторично; основная метрика — число SQL и план.

**Числа «до» в каждой строке —baseline на момент своего изменения**, а не
общий снимок начала ночи: линия шла в несколько заходов, и каждая правка
мерялась против того состояния, которое она исправляла. Столбец «итого»
суммирует цепочку одного и того же эндпоинта.

## Что было и что стало — по классам

**Было.** У `Section` три связи с `lazy="selectin"`: `users`, `operations`,
`spg_links`. Ключевое свойство, на котором стоял весь класс проблемы:
**`selectin` срабатывает один раз на коллекцию, а не на объект** — загрузка
100 `Section` даёт один запрос на связь, а не сто. Поэтому «много `selectin`» в
профиле ещё ничего не значит; значит, когда ORM-объект материализуется **внутри
цикла**. Связи `Section` тянули за собой эхом и чужие: материализация `User`
(через `Section.users`) включала `User.sections`, материализация
`StorageProductionGroup` (через `Section.spg_links`) — `spg.sections`. То есть
связь, которой никто не зовёт, всё равно стоит, если кто-то материализовал
владельца. Ни одна из трёх связей `Section` не была нужна ни одной из семи
тяжёлых ручек.

**Стало.** Мёртвые связи сняты (`ProductionRoute.rules`,
`RouteRuleProfile.rules`, `StorageProductionGroup.sections` — с `selectin` на
`raise`, чтобы будущее чтение падало, а не платило молча). Вместо
материализации `Section` в трёх местах — плоская проекция `SectionRef`
(`services/section_ref.py`, шесть полей: `id`, `code`, `name`, `type`, `icon`,
`icon_color`). Появился **метод**: инвентаризация связей по ручкам с
атрибуцией места вызова по цепочке `greenlet.parent`. И отдельный тест,
фиксирующий, что инвентаризация врёт про `User.sections` (см. ниже).

## Что не помогло — чтобы не начали заново

1. **Проба подменой `rel.lazy` в рантайме врала.** Она переключала стратегию
   связи на уже сконфигурированном маппере и рапортовала «ОК» во всех трёх
   режимах, включая те, где чтение обязано было упасть. Стратегия выбирается на
   этапе `configure`, подмена атрибута ничего не меняет. Проба выброшена.
   **Урок: способ проверки, который не может упасть, ничего не проверяет.**
   Единственный источник истины — прогон тестов.
2. **Первая версия правки `overview` дала 99 → 97.** Старый `route_stages_cache`
   обслуживал **обоих** потребителей сразу, и перенос второго в отдельный
   ленивый загрузчик просто передвинул 33 запроса из одного места в другое.
   Выигрыш дала следующая версия — одна выборка колонок на всех.
   **Урок: меряй после первой попытки, а не только перед ней.**
3. **Колонки в `summary` не дали ничего.** Срез D уже закрыл ручку через
   `raiseload("*")`, и загрузка участков стала одним запросом; колонки дали бы
   тот же один запрос. Ноль минус ноль — и я не стал делать вторую правку.
   **Урок: перед «очевидной» оптимизацией проверь, не сделана ли она уже.**
4. **Инвентаризация объявила `User.sections` мёртвой, и это было неверно.** Её
   читает свойство `section_ids`, а его отдают `UserOut` и `MeResponse` через
   `from_attributes`. Нашлось тестами: с `lazy="raise"` упали **27 тестов**
   (`test_users.py`, `test_me_ttl.py`). Связь возвращена и закреплена тестом.
   **Правило для следующей ночи: связь жива, если на неё ссылаются не только
   другие связи и атрибуты, но и сериализация (`from_attributes`).** Grep по
   `user.sections` этого не видит — нужен либо grep по свойствам, либо тест.
   Из-за этого же «мёртвые связи» дали **−1, а не −3**: две из них срабатывали
   эхом за материализацией `Section`, а не сами по себе.
