### AC «≤ 20 SQL» — выполнено, автор ошибся в оценке остатка

Комментарий автора объясняет невыполнение AC («23 против 20») четырьмя
запросами `select(Section)` в `route_builder.py:144` и `route_selection.py:551`.
На текущем дереве это **не так**: обе точки уже читают участки колонками
через `load_section_refs` (`backend/app/services/section_ref.py:69`,
`SELECT sections.id, sections.code, sections.name, sections.type, sections.icon,
sections.icon_color FROM sections` — **1 запрос**, а не 4). Это сделал #303
(`044be52a`), который слит в `main` после коммита автора.

Фактический остаток — **не Section, а повторная загрузка справочников**. Мой
пробник с вложенной обёрткой лоадеров (`load_position_route_batch_cache`,
`load_route_selection_batch_cache`, `load_route_sections`,
`load_selection_rules_for_profile`) дал такую картину для одного вызова
(17 запросов, порядок сохранён):

```
<handler>                    SELECT import_batches…
<handler>                    SELECT plan_positions…
prb.load_cache               SELECT production_routes…        ← 1-й
prb.load_cache               SELECT route_stages…            ← следствие selectin
prb.load_cache               SELECT route_operations…        ← следствие selectin
prb.load_cache               SELECT route_rule_profiles…
prb.load_cache               SELECT EXISTS(product_pairs…) + products
prb.load_cache               SELECT product_processing_flags…
prb.load_cache               SELECT import_batches…          ← дубль <handler>
prb.load_cache > rs.selection_rules   SELECT route_selection_rules…
prb.load_cache               SELECT production_routes…        ← ДУБЛЬ
prb.load_cache               SELECT route_stages…            ← ДУБЛЬ
prb.load_cache               SELECT route_operations…        ← ДУБЛЬ
prb.load_cache > rs.route_sections    SELECT route_stages JOIN sections…
prb.load_cache               SELECT sections… (колонки)
prb.load_cache               SELECT section_operations…

```

Четыре дубли (`production_routes`, `route_stages`, `route_operations` — по
`selectin` у `ProductionRoute.stages`, и `import_batches`) возникают потому, что
снимок `load_position_route_batch_cache` грузит маршруты сам, а затем
`load_route_selection_batch_cache` (`route_selection.py:551-556`) грузит их
вторым запросом для того же профиля.

**Не чинил** — это общий корень `position_route_batch`/`route_selection`,
общий с `app/transfers/`, и по #303 там уже работал другой тикет. AC при этом
выполнен, поэтому это не блокер: 17 < 20.

### AC «≤ 30 на default-фильтре» — не достигнуто, на один запрос

Замерил 31. Причина видна в профиле: 8 из 31 запроса — снимок
`load_position_route_batch_cache` (те же 4 дубля, что в #296), плюс 3
`route_stages`/`route_operations`. Автор писал «37 SQL — это разумный пол»;
после #303 пол стал ниже, но до 30 не дотянул. Расхождение не оспариваю —
целевое число в AC стояло.

### AC «сверка JSON до/после на 2-3 фильтрах, включая фильтр по участку» — автор фильтр по участку не снял

В комментарии автора пять сценариев: default, limit=500, сортировка,
`status=released`, offset. **Фильтра по участку среди них нет** — а AC его
требует явно («включая фильтр по участку»). Это пробел в приёмке, а не в коде.

Закрыл его замером: снял digest до/после по каждому из 13 участков
(`section_id=1..13`) — **все 13 совпали побайтово**, число SQL 1454 → 31 на
участках с позициями (2 на пустых). Проверено и то, что новый путь не оставил
`route_steps` пустыми: на каждом непустом участке `with_route_steps = rows`
(7/7, 6/6, 7/7, 22/22, 7/7, 6/6).

### AC «опрос стабилен» — подтверждён

Два последовательных вызова в одной сессии: `rows` 31 → 31, `overview` 26 → 26,
`sections=6` → 6, digest первой строки `rows` одинаковый. Кэши локальны для
вызова, утечки между тиками нет.

Все четыре ответа совпали побайтово.

`all-positions` — ноль строк на dev-данных (все позиции `released`, ручка
фильтрует по статусам планирования), поэтому разница 3 → 3 неинформативна;
автор это оговорил и мерял на клоне. Меня этот пункт не опровергает и не
подтверждает — данных на dev-БД нет, и я это фиксирую честно.

### Находка: `RuntimeError` в цикле — недостижимая ветка

`production_planning.py:609-614`:

```python
wt_cache = tasks_cache_bulk.get(wt.id)
if wt_cache is None:
    raise RuntimeError(f"task {wt.id} missing from bulk task cache")
```

`StockProjectionManager.get_tasks_cache_bulk` (`backend/app/stock/services.py:610-654`)
**всегда** возвращает запись для каждого переданного id: для отсутствующей
задачи он подставляет нули (`if task is None: result[tid] = {...Decimal(0)...}`).
Проверено пробником: `get_tasks_cache_bulk([-999999])` → `keys=[-999999]`.
Значит `.get(wt.id)` не может вернуть `None`, и ветка не исполняется никогда.

Смысл комментария автора («молчаливый ноль — это разные вещи, чем неизвестно»)
нарушен на уровне контракта: ноль подставляет сам `get_tasks_cache_bulk`, и
guard выше этого места ничего не ловит.

**Не чинил.** Правка здесь не локальная: чтобы guard стал осмысленным, bulk
должен различать «задачи нет» и «задача есть, движений нет» — это изменение
общего контракта `stock/services.py`, у которого есть и другие потребители
(`shopfloor/queries_sections.py:345`, `queries_spg.py:97`,
`daily_plan_service.py:34`). Такое — отдельный тикет на общий корень, не
правка ночного ревью.

### Scope creep

Мелкий, но реальный: кроме пяти эндпоинтов из AC затронут ещё
`cancelled_positions` (`production_plans.py:1743`) — шестой эндпоинт, в списке
AC его нет. Правка там ровно та же (поштучный резолв → батч), риска не несёт,
но формально это выход за границы тикета. Не откатывал: изменение
однотипное, безопасное, а реверс здесь был бы хуже самой правки.

### Запахи (Standards)

- **Duplicated Code — да, и это следствие самого решения.** Один и тот же
  блок «собрать `ops_by_stage` по `route_stage_id` → разложить по
  `route_id`» теперь написан дважды: `production_planning.py:481-517` и
  `production_planning_rows.py:685-726`. Это ~35 строк почти дословно. Общая
  функция потребовала бы знания и формы ответа (`steps_by_route` против
  `remainders_by_route`), то есть это уже не механическая склейка, а отдельная
  работа. Не чинил.
- `overview` остаётся длинной функцией с вложенным циклом
  `sections × positions × lines × tasks` — длина выросла незначительно, но
  Divergent Change тут остаётся: любая правка `overview` тянет с собой и
  кэш задач, и кэш этапов, и выдачу по секциям. Это следствие формы, а не
  этого тикета.
- `section_ids_by_route`, который я видел мёртвым в `overview` на своей копии
  дерева, в слитом `main` уже удалён (`3de3de5b`, ревью #303) — не находка
  этого среза.

### AC «пагинация production не трогается» — соблюдено

`all_plan_positions` по-прежнему делает `count` + `LIMIT/OFFSET` на стороне БД
(код не менялся в коммите), `/all-locations`-семантика не тронута.
