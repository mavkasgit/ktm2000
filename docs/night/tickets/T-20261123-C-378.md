# T-20261123-C-378 — Распараллелить pytest в CI с замером стены

- **Категория:** скорость CI (M3 — стена конвейера)
- **Статус:** локальный A/B DONE (−53.3% по медиане wall); CI-чередование 2+2 **НЕ запускалось** — передано человеку с правами администратора, тикет не закрыт
- **Дата:** 2026-11-23, внеочередная ночная смена, срез C
- **Issue:** #378 (ready-for-agent), волна `night-2026-11-03`
- **Ветка:** `night/2026-11-23-c`, ревизия замеров `1c1bad50`
- **Зона файлов:** `.github/workflows/backend-tests.yml`, `backend/tests/AGENTS.md`, этот файл

## Суть и границы

Issue требует: замер стены на одной ревизии, serial против parallel, **чередование
≥ 2+2 через `workflow_dispatch`** с приложением `gh run view --json jobs`; число
тестов одинаковое и coverage-порог `--fail-under=73` не снижен; решение — только
при выигрыше ≥ 25% без роста флаков, иначе REJECTED с числами; изоляция run-DB
в CI подтверждена.

`backend-tests.yml` к моменту смены **уже** гоняет `-n 4 --dist loadfile` с
coverage воркеров через `COVERAGE_PROCESS_START` + `sitecustomize.py`
(правка предыдущей смены, замер `0bd84c00` 2026-11-18: serial 983.9 с против
`-n 4` — 290.1 с, −70.5%, по одному прогону каждого режима). Критерию (а) это не
удовлетворяет: 2+2 чередования не было.

**Ограничение агента:** `workflow_dispatch` требует прав администратора
репозитория, поэтому данный агент CI-прогоны не запускал и не запускает.
Вместо этого подготовлена параметризация dispatch и выполнен локальный A/B.

## Что изменено в workflow

- `workflow_dispatch` получил input `pytest_mode` (`parallel` по умолчанию /
  `serial`). Значение читается только в ручном dispatch; на push/PR input
  отсутствует, и всегда собирается боевой режим.
- Шаг прогона выбирает планировщик:
  `parallel` → `-n 4 --dist loadfile`, `serial` → `-p no:xdist`.
- Оба режима гоняют **один и тот же набор** и один и тот же coverage-гейт
  (`--fail-under=73` не тронут; `sitecustomize.py` стартует coverage и в serial).
  Любое иное значение `pytest_mode` падает шаг с явной ошибкой.

Это позволяет человеку с правами администратора сделать ровно то, что просит
критерий (а): `serial → parallel → serial → parallel`, приложив к тикету
`gh run view --json jobs` для четырёх run_id.

## Локальный A/B (НЕ CI)

Условия: Windows, worktree среза C, ревизия `1c1bad50`, интерпретатор
`C:\Users\LogoPrint\VibeCoding\ktm2000\backend\.venv\Scripts\python.exe`
(3.14.10, pytest 9.2.0), `PYTEST_NUM_WORKERS=2`, Postgres `:5441` уже healthy,
один heavy-слот на весь пакет, прогоны строго последовательные.

- **A (serial):** `powershell -ExecutionPolicy Bypass -File scripts\test-run.ps1 --full`
  → launcher не добавляет `-n`, весь набор, slow включён.
- **B (parallel):** `powershell -ExecutionPolicy Bypass -File scripts\test-run.ps1 -m "slow or not slow"`
  → launcher добавляет `-n 2 --dist loadfile`, свой `-m` отзывает фильтр
  `not slow`, весь набор.
- Чередование **A/B/A/B/A/B** (по 3 прогона каждого), медиана по трём.
- Оба режима собирают **2564 теста** (`pytest --collect-only -q` с маркером и без
  него — 2564 / 2564), то есть состав набора идентичен.

### Изоляция run-DB

Каждый из шести прогонов создал и в `finally` дропнул **свою**
`ktm2000_test_<12 hex>` — шесть имён в таблице выше и в `results.csv` все
различны, каждая строка `[6/6] Cleaning up database` содержит своё имя.
Launcher не трогает чужие БД. В CI та же механика: `RUN_ID=$(uuid…[:12])`,
`DB_NAME=ktm2000_test_${RUN_ID}`, `trap … drop` на EXIT, сервис Postgres живёт
внутри job-а на отдельном runner-е — соседний прогон базу не делит.

переносить его на CI как готовый результат нельзя.

## Решение

<!-- DECISION-BEGIN -->
Локальный вердикт: **гипотеза подтверждена, откат к serial не требуется** —
−53.3% по медиане wall, все парные сравнения ≥41%, состав набора одинаковый
(2564 собрано → 2562 passed + 2 skipped в каждом прогоне), новых флаков и
падений нет, `--fail-under=73` не изменён.

Но критерий (а) #378 требует чередования 2+2 **именно в CI** через
`workflow_dispatch` с приложением `gh run view --json jobs`. Этот шаг агентом
не выполнен и не может быть выполнен без прав администратора репозитория.
Поэтому #378 этим срезом **не закрывается**: человеку нужно на одной ревизии
прогнать четыре dispatch с `pytest_mode=serial,parallel,serial,parallel`,
приложить JSON jobs к тикету и сверить стены с coverage. CI подтвердит ≥25% —
закрывать #378; не подтвердит — REJECTED с CI-числами и откат на serial
(см. раздел «Откат»).
<!-- DECISION-END -->

**CI-прогоны `workflow_dispatch` не запускались.** Критерий (а) в части 2+2 через
CI остаётся неподтверждённым; локальный замер не подменяет CI-результат и не
является основанием для закрытия #378 без участия человека с правами
администратора репозитория.

## Откат

Вернуть последовательный запуск в `backend-tests.yml`: убрать input
`pytest_mode`, заменить `$PYTEST_SCHEDULER` на `-p no:xdist` (или на исходный
`pytest -q -p no:xdist -p no:pytest-testmon`), coverage-блок оставить как есть —
он работает и в serial.
