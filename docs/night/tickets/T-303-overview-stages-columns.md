# T-303 (шаг 2) — `overview`: этапы и секции по колонкам

## Поправка к инвентаризации (шаг 1)

В отчёте-инвентаризации я написал, что кэш этапов в `overview` читается
**только** для `stage.section_id`. **Это было неверно.** При переводе на колонки
я это перепроверил, как и просил оркестратор, — и вот где ошибка:

```python
# production_planning.py, ветка «позиция без задач стоит в очереди»
work_tasks_out.append(WorkTaskOut(
    route_stage_id=stage.id,                                   # нужен id
    operation_name=", ".join(op.operation_name for op in stage.operations),  # нужны operations
    operation_code=stage.operations[0].operation_code,          # нужны operations
    sequence=stage.sequence,                                   # нужен sequence
))
```

`operations`, `id` и `sequence` там **нужны**. В профиле инвентаризации этого не
было видно только потому, что на dev-данных у всех 91 позиции есть задачи, и эта
ветка **не срабатывала ни разу** — то есть профиль показал «связь не читается»
не потому, что её не читают, а потому, что ветка не выполнялась.

**Отсюда правило для инвентаризации:** «связь не видна в профиле» ≠ «связь не
нужна». Профиль показывает только то, что исполнилось на этих данных.

## Что сделано

`backend/app/api/routes/production_planning.py`, `get_production_planning_overview`:

1. **Этапы маршрутов — один запрос по колонкам** на все уникальные `route_id`:
   `(route_id, id, section_id, sequence)` + один запрос операций по всем
   `stage_id` (`operation_name`, `operation_code`). Вместо `select(RouteStage)`
   в цикле по `route_id`, из-за которого ORM-объект тянул две selectin-связи
   (`RouteStage.operations` и `ProductionRoute.stages` через backref).
2. **Секции — колонками**: `(id, code, name, type)`. `SectionOut` отдаёт ровно
   эти четыре поля, а ORM-объект `Section` тянет три selectin-связи
   (`users`, `operations`, `spg_links`).

Обе выборки — колонками, поэтому `selectin` не срабатывает нигде.

**Промежуточная ошибка, о которой стоит сказать.** Первая версия правки взяла из
кэша только `(route_id, section_id)` и для ветки «в очереди» ввела отдельный
ленивый загрузчик с мемоизацией. Замер показал **99 → 97**: почти ничего. Причина
в том, что старый `route_stages_cache` обслуживал **оба** потребителя сразу, и
перенос второго в отдельный загрузчик просто передвинул 33 запроса из одного места
в другое. Правильное решение — забрать всё нужное обоим потребителям одной
выборкой по колонкам; тогда запросов действительно становится два, а не 33.
