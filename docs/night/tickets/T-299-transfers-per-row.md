## Пункт 5 (`db.add` + `db.flush` в GET) — замер, правки нет

`list_ready_to_transfer` (`backend/app/transfers/queries.py:1092-1095`) создаёт
для складской строки без открытой задачи временный `WorkTask` («fake task»),
складывает их в бюджетный расчёт и затем **пишет их в базу**:
`db.add_all(new_tasks)` + `await db.flush()` — внутри GET-ручки.

Замер на dev-данных (`docs/night/logs/measure_299_p5.py`), 49 строк из 49:

| глагол | число |
|---|---|
| SELECT | 14 |
| INSERT | **0** |
| UPDATE | **0** |

Сумма по БД 240.5 мс, wall 506.8 мс (под нагрузкой).

**Вывод: на текущих данных записи нет.** У всех строк, попавших в выборку,
уже есть открытая задача, поэтому `is_new_task` нигде не истинен и `new_tasks`
пуст — `add_all`/`flush` не вызываются. Тикет прав: #290 показала, что этот путь
запросов не даёт.

**Почему я не выпилил запись.** Удаление `db.add_all` + `flush` — это не
оптимизация, а **смена поведения**: задачи на складских строках создаются лениво
(#176), и без этой записи они перестанут появляться при первом просмотре
списка. Менять это без кейса, где путь срабатывает, — значит менять код без
доказательства: замер показал ноль, а риск (задачи перестанут создаваться,
второй read-path и write-guard начнут видеть разные данные) реальный.

Чтобы убрать запись правильно, нужен тест-кейс, где складская строка без
задачи попадает в выдачу, и проверка, что после удаления записи write-guard
`task_transferable` и второй read-path видят то же. На dev-данных такого кейса
нет, собрать его в изолированной клоне я не успел.
