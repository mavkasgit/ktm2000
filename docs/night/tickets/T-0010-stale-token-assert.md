# T-0010 — Тест «устаревший токен → 409» ничего не проверял

- **Категория:** проверка самих тестов (тесты, которые не могут упасть)
- **Статус:** DONE (коммит см. `JOURNAL.md`)
- **Дата:** 2026-10-01, цикл 3
- **Файл (не в denylist):** `backend/tests/reversal/test_reversal_api.py`

## Проблема и доказательство

Разовый AST-анализ тестовой зоны (`logs/analyze_tests.py`, секция «тесты без
assert/pytest.raises») нашёл `test_reverse_stale_token_maps_409`. Чтение кода
подтвердило: тест делает POST на `/api/actions/{id}/reverse` с устаревшим
`plan_token`, кладёт ответ в `resp` — и **не проверяет его вообще**. Функция
заканчивалась сразу после запроса, поэтому тест проходил при любом статусе:
404, 500, 200 — всё «зелено».

Имя теста при этом заявляет конкретный контракт: устаревший токен → 409.
Соседний тест в том же файле (`test_preview_and_reverse_endpoints`) для
аналогичной ситуации уже пишет `assert again.status_code == 409`.

## План изменений

Добавить одну строку — утверждение, соответствующее имени теста и соседнему
паттерну:

```python
assert resp.status_code == 409, resp.text
```

## Граница: что НЕ затронуто

- Продуктовый код — не менялся (утверждение описывает уже существующее
  поведение, а не новое требование).
- Ничего не удалено и не ослаблено: тест только получил проверку, которой у
  него не было.
- Прочие тесты файла — без изменений.

## Критерии готовности (измеримые)

1. `tests/reversal/test_reversal_api.py`: `5 passed` (до и после).
2. Новое утверждение **проходит** — значит, контракт «409 на устаревший токен»
   действительно выполняется (если бы падало, это был бы продуктовый дефект →
   отдельный тикет, а не правка теста).
3. Полный прогон: `1945 passed, 0 failed, 43 warnings` — число тестов не
   изменилось (правка внутри существующего теста).
4. Диффа — одна строка в одном файле.
