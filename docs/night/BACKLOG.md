## B-0001 — CI прогоняет только миграции, не прогоняет тестовый набор

- **Категория:** CI-эффективность
- **Статус:** NEW
- **Доказательство:** `.github/workflows/` содержит единственный файл
  `migrations.yml`. Его шаги: `alembic upgrade head && alembic check`,
  `pytest tests/test_migrations.py`, `scripts/validate_seeds.py`,
  `generate_frontend_labels.py --check`, `verify-profile-settings.py verify --strict`.
  Шага с полным pytest-набором, с `vitest run` и с Playwright нет.
- **Эффект:** регрессии в backend/frontend не ловятся до мержа; на CI нельзя
  опереться как на арбитр «зелено/красно», что критично для ночных правок.
- **Риск:** средний. Нужен Postgres service (в workflow он уже есть на порту 5212),
  seed-данные и сборка frontend; время прогона и стоимость минут CI — вопрос
  политики, решает человек. Плюс текущий pytest-набор на Linux ни разу не
  запускался — ожидаемы платформенные падения (Windows-специфика в тестах).
- **Первый шаг:** прогнать полный набор на Linux-раннере вручную (workflow с
  `workflow_dispatch`, без блокировки PR) и собрать список платформенных падений.

- **Категория:** повторяемость / метрики
- **Статус:** NEW
- **Доказательство:** `backend/pytest.ini` содержит только `asyncio_mode`,

- **Риск:** низкий. `pytest-cov` / `@vitest/coverage-v8` — dev-зависимости,
  нужны только при явном `--cov`/`--coverage`. Отдельно решить, хранить ли
  baseline-число и порог (порог на непокрытом legacy-коде может краснеть всегда).
- **Первый шаг:** замерить текущее покрытие обоих наборов, записать в BASELINE,

## B-0004 — Playwright: `workers: 1`, `fullyParallel: false` — e2e полностью serial

- **Категория:** скорость
- **Статус:** BLOCKED_NEEDS_HUMAN — ночному агенту e2e запрещён (`AGENTS.md`:
  агент не запускает `npm run test:e2e`), поэтому критерий «выигрыш подтверждён
  прогонами» недостижим. Решение и замер — за человеком.
- **Доказательство:** `frontend/playwright.config.ts:111-114` —
  `fullyParallel: false`, `workers: 1`, `retries: process.env.CI ? 2 : 0`.
  Тир-проекты `ui-e2e` / `ui-narrow` объявлены через `dependencies: ["smoke"]`
  (`:196-205`), т.е. ещё и выстроены цепочкой.
- **Эффект:** потенциально самый крупный выигрыш по времени, но требует
  доказательства, что тесты не делят состояние (одна БД стенда на прогон).
- **Риск:** высокий. При `workers > 1` ожидаемы flaky из-за общего состояния
  БД/сидов и порядка; выигрыш надо подтверждать 10 прогонами без флейков.
  Начинать только после baseline по времени.
- **Первый шаг:** прогнать стенд с `--workers=2` на подмножестве и посмотреть,
  воспроизводимы ли падения.

## B-0007 — Run-DB миграционных тестов не попадают в уборку вообще

- **Категория:** диагностика / гигиена БД
- **Статус:** DONE (тикет `T-0007`, коммит `38df604`): добавлен
  `drop --force` для невладелых `ktm_mig_*` (отказ при активных соединениях и
  на служебных именах). Регистрация `ktm_mig_*` в owner-таблице из самих
  миграционных тестов (34 сайта) осталась как возможное продолжение.
- **Доказательство:** `scripts/test-db.py:36` `RUN_DB_PREFIX = "ktm2000_test_"`,
  а `cleanup()` сканирует `WHERE datname LIKE 'ktm2000_test_%'` (`:166`).
  Миграционные тесты создают БД с другим префиксом —
  `tests/test_migrations.py` и `tests/test_hanger_norm_key_migration_218.py`
  (17 мест `CREATE DATABASE`, все `ktm_mig_<uuid10>`), и owner-строку они не
  пишут. Итог: БД убитого/прерванного прогона миграционных тестов не удаляются
  ни `drop`, ни `cleanup` — только вручную через psql. В контейнере
  `ktm2000-postgres-test` такие БД наблюдались (`ktm_mig_3c6bbeebaa` и др.).
  Отдельно: `drop` без owner-строки печатает `Skip drop …: no matching owner
  row` — то есть убрать чужую осиротевшую `ktm2000_test_*` руки тоже не могут.
- **Эффект:** мусор копится на общем тестовом Postgres; при отладке непонятно,
  какие БД «чьи».
- **Риск:** средний: 34 сайта create/drop в двух файлах, общего хелпера нет.
  Безопасный первый шаг — не рефакторить тесты, а расширить уборку:
  либо регистрировать `ktm_mig_*` в owner-таблице, либо дать `drop --force`
  (с явной проверкой «нет активных соединений», как в `cleanup`).
- **Первый шаг:** решить, где регистрировать владельца (тест или скрипт).

## B-0008 — Режим распределения xdist не подобран под структуру набора

- **Категория:** скорость
- **Статус:** DONE (тикет `T-0003`, коммит `57044a3`): параллельный прогон идёт
  с `--dist loadfile`. A/B 3+3 прогона: медиана **370.68s → 256.55s** (−31%),
  сумма `setup` 327s → 287s, результаты идентичны (1945 passed).
- **Доказательство:** `scripts/test-run.ps1` запускал `python -m pytest -n <N>`
  без `--dist`, то есть действовал дефолт `--dist load` (по одному тесту на
  воркер). При этом схема БД создаётся **на модуль на воркер**
  (`backend/tests/AGENTS.md`). Сумма по `--durations=0` (baseline №1):
  `call 681s`, `setup 340s`, `teardown 17.5s` — setup это треть работы, и часть
  его дублируется, когда тесты одного модуля попадают на разные воркеры.
  Идея: `--dist loadfile` (модуль целиком одному воркеру).
- **Эффект:** ожидаемое сокращение дублирующегося setup и общего wall time;
  проверяется замером.
- **Риск:** средний — `loadfile` может ухудшить балансировку: самый тяжёлый
  файл `test_packing_plan_demo_seeder.py` весит ~204s и целиком сядет на один
  воркер. Решение — только по цифрам трёх прогонов в каждом режиме.
