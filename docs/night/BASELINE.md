Замер сделан без новых зависимостей — системным `coverage 7.16.2`

Топ файлов по числу непокрытых строк: `app/api/backups.py` (558),
`app/api/routes/production_plans.py` (364),
`app/api/routes/production_planning.py` (334), `app/api/routes/products.py` (313),
`app/services/production_planning_rows.py` (307),
`app/services/production_plan_service.py` (304).

Оговорки (важно для сравнений в следующие ночи):

1. Замер **серийный**: под `-n` воркеры — отдельные процессы, и без
   `COVERAGE_PROCESS_START` контроллер измерил бы пустоту. Сравнивать числа
   можно только с такими же серийными замерами.
2. В серийном режиме предупреждений 11, а не 43: в параллельном режиме каждый
   воркер печатает свою копию предупреждений, возникших при импорте. Поэтому
   «43» в baseline — это 11 уникальных предупреждений, размноженных по воркерам.
3. Покрытие frontend (vitest) не замерено: в worktree нет `node_modules`
   (`npm --prefix frontend run test` там не запускается).

## Уборка БД: уточнено позже

Первая запись в журнале предполагала, что осиротевшую run-DB нельзя удалить
руками (`Skip drop …: no matching owner row`). Уточнение по фактам:

- `drop` действительно требует совпадения owner-строки — это защита, а не
  баг: launcher при убийстве прогона сам дропает свою БД в `finally`.
- Настоящая дыра была в другом: базы миграционных тестов (`ktm_mig_*`) не
  попадают ни в `drop`, ни в `cleanup` — их создают сами тесты, без
  owner-строки. Исправлено тикетом `T-0007` (`drop --force`).
- TTL-уборка `npm run test:db:cleanup` покрывает `ktm2000_test_%` и остаётся
  штатным механизмом для run-DB.
