# E2E: ярусы, теги, время и канон спек

Справочник к [`frontend/e2e/AGENTS.md`](../../frontend/e2e/AGENTS.md).

**Когда читать:** выбираете, в какой ярус положить новую спеку; нужны замеры
времени, состав канона `@ui`/`@ui-narrow`, правила `@mobile`, `@smoke`, `@tmp`
или xlsx-фикстур; разбираетесь, почему тег сматчился не так.

## Слои тестов и порядок прогона

Прогон разбит на три яруса **от общего к узкому** плюс отдельный мобильный
ярус **вне этой цепочки**. Каждый следующий ярус цепочки зависит от
предыдущего (`dependencies` в `playwright.config.ts`), поэтому первый
сломанный ярус останавливает прогон, а не отрабатывает вхолостую через
полчаса.

| Ярус | Тег | Playwright project | Зависит от | Назначение |
|------|-----|-------------------|-----------|------------|
| 1. Smoke | `@smoke` | `smoke` | — | Быстрая проверка с API-setup. Сломалось здесь — дальше идти незачем |
| 2. Широкий UI | `@ui` | `ui-e2e` | `smoke` | Бизнес-путь через UI; сетап данных — API/визарды |
| 3. Узкий UI | `@ui-narrow` | `ui-narrow` | `ui-e2e` | Доменные сценарии (пила, ЮП-460): долгие, зависят от всего предыдущего |
| 4. Телефон | `@mobile` | `mobile` | — | Окно 390×844, `isMobile`, `hasTouch`: те же экраны под тач. Вне цепочки — ни предусловие, ни следствие десктопных ярусов |
| Временные | `@tmp` | `tmp` (только при `E2E_TMP=1`) | — | Разовый прогон; вне цепочки зависимостей |

`@ui-narrow` — подмножество `@ui`: такие спеки помечены **обоими** тегами в
`test.describe`, а `ui-e2e` исключает их через `grepInvert`, иначе спека
прогонялась бы дважды.

`@mobile` — **другой ярус, а не другой viewport у `ui-narrow`**: `ui-narrow`
это доменный сценарий (пила, ЮП-460), он идёт широким окном, как и остальные.
Мобильный проект гоняет короткие smoke-проверки тех же экранов при 390×844;
десктопные ярусы исключают его тегом (`grepInvert` от `MOBILE_TAG_RE` у `smoke`
и `ui-narrow`, `tagRe("@ui-narrow", "@mobile")` у `ui-e2e`), поэтому сочетание
тегов `@smoke @mobile` на одной спеке не прогнало бы её дважды.

**Тег — токен, а не подстрока (#342, ревью 5).** Все `grep`/`grepInvert`
в конфиге собираются из `tagRe(...)` (`e2e/mobile-project.mjs`), и тот же
шаблон читает отчёт прогона (`selectMobileSpecs`). Подстрочный `/@mobile/`
утащил бы спеку с `@mobile-wide` в мобильный прогон, которого его же отчёт не
назвал бы: «что прогналось» и «что напечатано» разошлись бы молча. Проверка
расхождения — `--list`: `npx playwright test --list --no-deps
--project=<ярус>` против строк `[e2e:run] ярус mobile: …` из прогона.

```bash
npm --prefix frontend run test:e2e:smoke      # ТОЛЬКО ярус 1 (smoke)
npm --prefix frontend run test:e2e:ui         # ТОЛЬКО ярус 2 (ui-e2e)
npm --prefix frontend run test:e2e:ui:narrow  # ТОЛЬКО ярус 3 (ui-narrow)
npm --prefix frontend run test:e2e:mobile     # ТОЛЬКО мобильный ярус (mobile)
npm --prefix frontend run test:e2e            # вся цепочка smoke → ui-e2e → ui-narrow (all)
```

**Одиночный ярус идёт без зависимостей.** `run-tier.mjs` добавляет `--no-deps`
для любого яруса, кроме `all`, поэтому `test:e2e:ui` — это ровно `@ui`, без
smoke-шлюза, а `test:e2e:ui:narrow` — ровно `@ui-narrow`. `dependencies` в
`playwright.config.ts` работают только на `all`: там они разбивают прогон на
фазы и дают fail-fast между ярусами — красный `ui-e2e` пропускает `ui-narrow`
целиком (`N did not run` в выводе). Прежняя редакция этого раздела утверждала
обратное — она разошлась с кодом.

**Мобильный прогон называет окно сам.** Строка `=== ярус mobile: Ns, код N ===`
одинакова для любого окна, поэтому `run-tier.mjs` перед прогоном печатает две
строки: габариты `390×844`, `isMobile`/`hasTouch`/`deviceScaleFactor` и список
`@mobile`-спеков (он собирается чтением каталога `e2e/`, а не списком в коде).
Цифры окна живут в одном месте — `e2e/mobile-project.mjs`: оттуда их берут и
проект в конфиге, и отчёт, иначе отчёт утверждал бы одно окно, а проект гонял
другое. Логика этого отчёта закрыта `e2e/mobile-project.test.ts`.

**Мобильный ярус и семафор.** Слоты `E2E_MAX_PARALLEL_RUNS` считают прогоны, а
не проекты: `test:e2e:mobile` берёт тот же слот и тот же лок дерева, что и
остальные ярусы, поэтому параллельный мобильный прогон не запускается поверх
чужого и не мешает соседнему worktree.

**Геометрия телефонной таблицы — одна на два экрана.** `e2e/mobile-table-helpers.ts`
держит то, что проверяют и «Передачи» (#343), и доска участка (#345): поиск
скролл-контейнера примитива, метрики переполнения, ассерт «ячейка целиком в
кадре 390px», перетаскивание мышью с дроблением шагов (порог жеста 8px) и
контракт закреплённых ячеек — `primeRowForMeasure`/`stickyCells`/`swipeAcrossRow`
(обе закреплённые ячейки целиком в кадре, между ними полоса прокрутки не уже
16px = 2 × порог жеста, после свайпа `scrollLeft` вырос, закреплённые ячейки
стоят). Третье копирование этих проверок означало бы, что рамка кадра
разъехалась бы между экранами, — поэтому у неё один источник.

Подмножество из двух ярусов собирается extra-аргументами (они уходят в
`playwright test` как есть):

```bash
npm --prefix frontend run e2e:run -- ui-narrow --project smoke   # smoke + ui-narrow
```

**В какой ярус попадает новая спека:** спрашивайте «насколько это широко».
Проверяет общий бизнес-путь (цикл, импорт, маршрут) — `@ui`. Проверяет один
доменный сценарий на конкретном артикуле (пила, ЮП-460) — `@ui-narrow`.
Проверяет, что экран работает **на телефоне** (окно 390×844, тач) — `@mobile`;
это отдельный тег, а не второй тег к `@ui-narrow`.

### Сколько занимает каждый ярус

Замер 27.09.2026, `npx playwright test --project=<ярус> --no-deps --reporter=list`.
`--no-deps` отключает только зависимости проектов, но не стек: `webServer`
поднимается в любом случае, поэтому к сумме времён добавь его старт
(1–2 мин поверх).

| Тест | Время |
|------|-------|
| `dimensions-sawing` — API остатков по группам | **0.3s** |
| `reversal-journal` | 6.8s |
| `dimensions-sawing` — доска пилы | 6.4s |
| `final-release` | 7.7s |
| `route-workflow` — визард импорта | 8.7s |
| `yup460-shared-raw-pile` | 13.2s |
| `catalog-dimensions` | 16.5s |
| `route-workflow` — маршрут в плане | 21.4s |
| `transfers-auto-accept` | ~30s |
| `sawing-four-lengths-cycle` | ~30–45s (с ретраем) |
| `full-cycle` | ~36s |

Итого по ярусам: **smoke ≈ 1 мин, ui-e2e ≈ 1–2 мин, ui-narrow ≈ 1 мин**.
Полный прогон `test:e2e` — около **5–7 минут**; стек поднимается **один раз на
запуск** Playwright, а не по разу на ярус: все три проекта — один вызов
`playwright test`, `dependencies` лишь разбивают его на фазы.

**Не ориентируйтесь на эти числа как на эталон.** Здесь они полезны только для
выбора, что гонять в первую очередь при правке: дешёвое — в пределах
10–20 секунд, дорогое — 30+. Но фактическое время сильно плывёт: те же тесты
в разных прогонах отличались в 2–3 раза (например, `dimensions-sawing` — 5.5s
и 6.4s, `transfers-auto-accept` — 16s зелёным и ~30s красным), потому что
время сильно зависит от прогрева бэкенда и от того, на каком тесте стек
упал. Замерять свои значения: `npx playwright test --project=ui-e2e --no-deps
--reporter=list`.

Отдельно: `--no-deps` нужен, чтобы замерить **все** ярусы подряд. Без него
fail-fast остановит прогон на первом красном ярусе, и хвост не измерится.

### Канон `@ui` и `@ui-narrow`

- Ярус 2 (`@ui`): `full-cycle.spec.ts` (канонический полный цикл ЮП-009),
  `route-workflow.spec.ts`, `single-line-cycle.spec.ts` (одна строка плана:
  сквозной маршрут передачи ↔ участки до «Отправлено»).
  `approve-freshness.spec.ts` (свежесть: позиция, утверждённая на плане, видна
  на «Контроле выполнения» без перезагрузки — одиночным и массовым путём).
  `remainders-import-preview.spec.ts` (предпросмотр остатков ОСВ: пропуск с
  причиной, фильтр «Только пропущенные», весь лист без пагинации).
- Ярус 3 (`@ui-narrow`): `sawing-four-lengths-cycle.spec.ts` (пила в полном
  цикле: раскрой 2,75 м на четыре длины), `sawing-multi-length-split.spec.ts`
  (распил задачи на разные длины), `yup460-shared-raw-pile.spec.ts` (три
  варианта ЮП-460 делят одну кучу сырья), `equivalents-pool.spec.ts` (общий
  пул эквивалентов: A видит и выдаёт остаток B, две позиции не выдают больше
  кучи, экран остатков показывает группу одной строкой — ADR-0073).
- Хелперы: [`ui-helpers.ts`](../../frontend/e2e/ui-helpers.ts) — seed через `/settings/dev`, approve,
  take-to-work, чтение журнала передач; [`api-helpers.ts`](../../frontend/e2e/api-helpers.ts) — бесфайловый сетап.
- **Строку адресуем по `data-row-key="<position_id>"`**, а не поиском по видимому
  `#<id>`. Колонка `id` скрывается набором колонок, поэтому текстовый локатор
  переставал находить строку ровно тогда, когда её статус менялся, — и падал
  уже после того, как продукт отработал верно. Атрибут стоит и на строках
  доски передач, и на строках «Контроля выполнения»
  ([`ExecutionRow.tsx`](../../frontend/src/features/execution/components/ExecutionRow.tsx)).
- Сетап данных — обычно через API ([`api-helpers.ts`](../../frontend/e2e/api-helpers.ts)): артикул
  (`apiEnsureCatalogProduct`), остаток (`apiAddRemainder`), план
  (`apiSimulatePlanImport` → `POST /api/imports/excel/simulate`, без xlsx).
  В кадре — бизнес-действия UI (approve, запуск, передачи, завершение задач).
- **Запрещено** в бизнес-шагах: прямые `fetch` к бизнес-API (approve, take-to-work, передачи).
- Живые xlsx-импорты — только в `full-cycle.spec.ts` (каталог + остатки),
  `route-workflow.spec.ts` (план) и `prep-stage-plan.spec.ts` (план подготовки,
  #313); остальные сетапятся бесфайлово (см. «xlsx-фикстуры»).

### xlsx-фикстуры

По одному основному варианту на вид импорта, всё в
[`testdata/`](../../frontend/e2e/testdata/):

| Файл | Что | Живой UI-импорт в |
|------|-----|-------------------|
| `Упаковочный план.xlsx` | главный план (~318 строк, десятки артикулов) | `route-workflow.spec.ts` |
| `Каталог E2E.xlsx` | справочник сырья ЮП-009 | `full-cycle.spec.ts` |
| `Склад импорта остатков E2E.xlsx` | остатки ЮП-009 на «Склад сырья» | `full-cycle.spec.ts` |
| `ОСВ E2E.xlsx` | лист 1С ОСВ: годная, пропущенная реестром и ошибочная строки | `remainders-import-preview.spec.ts` |
| `План подготовительного участка.xlsx` | подготовительный маршрут, три варианта (#313) | `prep-stage-plan.spec.ts` |

Остальные сценарии эти виды данных **не хранят**: план — `apiSimulatePlanImport`
(строки в теле запроса, workbook собирается на бэкенде в памяти и идёт обычным
change-set); каталог/остатки — прямые вызовы API (`apiEnsureCatalogProduct`,
`apiAddRemainder`). Отдельные e2e-xlsx под ЮП-2083/ЮП-4610 удалены — не плодим файлы.

Файлы из таблицы выше **закоммичены** — это единственный набор, который
нужен в репозитории (`!frontend/e2e/testdata/*.xlsx` в `.gitignore` снимает
общее правило для этого каталога). Любой другой `*.xlsx` в `testdata/`
игнорируется: он остаётся локальным и в коммит не попадает.

### @smoke

- Спеки: `transfers-auto-accept`, `final-release`, `catalog-dimensions`, `dimensions-sawing`, `reversal-journal`
- Хелперы: [`api-helpers.ts`](../../frontend/e2e/api-helpers.ts) — ускоренный setup через API
- Основные проверки — через UI; setup может идти через API
- В CI ярус гоняет отдельный джоб
  [`e2e-smoke.yml`](../../.github/workflows/e2e-smoke.yml): Postgres — сервисом в
  джобе, `--retries=0` явно, трасса всегда уходит артефактом. Статус —
  **информационный**: `e2e smoke` не входит в required checks, поэтому красное
  здесь merge не блокирует. В required переводится после **10 зелёных прогонов
  подряд на push в `main`** (тикет #276); серию смотреть в истории прогонов
  (`gh run list --repo mavkasgit/ktm2000 --branch main --workflow e2e-smoke.yml`),
  а полный состав CI-проверок и способ сверить статус — в
  [`docs/testing-guide.md`](../../docs/testing-guide.md), раздел «CI».
  Прогон джоба локальный не заменяет и наоборот: серия считается только по CI,
  потому что у runner'а свой контейнер и ни один локальный прогон её не засчитывает.

### @tmp (временные, разовые)

- Инструмент отладки/разовой проверки, а не часть набора: файл называется
  `*.tmp.spec.ts`, тег `@tmp`, в шапке — что и зачем проверяем и с чем удалять.
- Проекта `tmp` нет, пока не задан `E2E_TMP` → `test:e2e`, `test:e2e:ui`,
  `test:e2e:smoke` такие спеки не трогают.
- Запуск разово:

  ```bash
  cd frontend && E2E_TMP=1 npx playwright test --project=tmp e2e/<file>.tmp.spec.ts
  ```

- Задача закрыта → спека и её фикстуры удаляются (одноразовый артефакт).
