# ADR-0076: Отмена выдачи — два режима, выбирает оператор

Дата: 2026-11-18. Статус: принято.
Тикеты: [#349](https://github.com/mavkasgit/ktm2000/issues/349) (выделен из
[#282](https://github.com/mavkasgit/ktm2000/issues/282)).
Связанные: ADR-0019 (журнал действий и preview-first откат), ADR-0071
(авто-приёмка — не основание запрещать отмену), GLOSSARY «Авто-приём».

## Контекст

Одна выдача материала в работу — это N передач, по одной на склад-источник,
связанных общим `issue_no` (#282). Отменять их по одной — четыре клика на
передачу и двадцать на пять складов.

ADR-0071 развёл «принято системой» (авто-приёмка при создании передачи) и
«принято получателем» (факт исполнения: частичная приёмка, завершённая или
бракованная работа). До #349 факт исполнения запрещал отмену всей выдачи:
«дальше путь только через правку записанного факта».

Владелец продукта решил, что запрет — не тот ответ: оператору нужны оба
сценария, и выбор между ними должен быть явным.

## Решение

`POST /transfers/issues/{issue_no}/cancel` принимает обязательный `mode`:

1. **`remainder` — «Отменить остаток».** Отменяются только передачи, по
   которым получатель ещё ничего не сделал. Передачи с фактами исполнения
   (частичная приёмка, завершённая/бракованная работа) остаются как есть и
   возвращаются в `kept_transfers` с текстовой причиной. Их проводки не
   компенсируются, материал остаётся на участке, склад-источник возврата не
   получает.
2. **`full` — «Полный откат».** Отменяется вся выдача, включая принятую
   часть. Каждая передача проходит тот же `cancel_transfer` →
   `ReversalService` (ADR-0019), что и обычная отмена, поэтому обратные
   проводки зеркальны приёмке, а остатки складов сходятся. Task-level
   guard «на приёмной стороне уже есть факты» снимается только в этом
   режиме; покрытие приёмного участка всё равно проверяет откат — если
   материал израсходован и вернуть его нечем, выдача не отменяется вовсе.

Режим не выбирается за оператора: `cancel-preview` отдаёт оба сценария
(что вернётся, что останется, что блокирует, какие этапы снова пойдут в
работу) и количество уже принятого, а окно требует явного выбора.

Правила, общие для обоих режимов:

- **Запрещающие статусы полного отката** — `amended` (запись заменена
  новой, компенсация задвоилась бы) и `rejected` (получатель отказался,
  материал уже вернулся). Наличие такого статуса отказывает всей операции
  до первой проводки: выдача отменяется целиком или никак.
- **Пропуски этапов** снимаются только когда в выдаче не осталось живых
  передач. Если принятая передача осталась, материал всё равно пришёл
  дальше по маршруту, и ранние этапы остаются «Пропущено».
- **Идемпотентность** — по ключу операции (`idempotency_key`): повтор с тем
  же ключом возвращает записанный исход, движения склада не задваиваются.
  Повтор без ключа при отсутствии живых передач тоже отвечает исходом
  (`idempotent_replay: true`), а не вторым возвратом.
- **Аудит** пишется в обоих режимах: на каждую отменённую передачу (кто,
  когда, передача, режим, номер выдачи, ключ операции, `reversed_tx_ids`) и
  одной записью на операцию целиком — по ней воспроизводится повтор.

## Последствия

- «Отменить выдачу целиком» из #282 остаётся частным случаем: пока ничего
  не принято, оба режима дают один и тот же результат.
- Правка записанного факта больше не единственный путь для принятой части:
  полный откат возвращает материал на склад, а не переписывает историю.
  Журнал действий и компенсации остаются append-only (ADR-0019).
- Права не расширены: ручка отмены держит `TRANSFER_WRITER_ROLES`, как и
  остальные операции с передачами.
- Покрытие обязательно в обе стороны: остаток не трогает принятое, полный
  откат возвращает и его. Тесты —
  `backend/tests/transfers/test_issue_cancel_modes.py` и
  `test_issue_cancel_acceptance.py`; окно — `IssueCancelDialog`.
