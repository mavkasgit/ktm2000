# ADR-0018: Ledger-примитив нетто-агрегации по причине — implementation slice

## Статус

Принято

## Связь с ADR-0017

ADR-0017 фиксирует архитектурный принцип: компенсация — **общая способность
ledger**, нетто по причине — `net(reason) = Σ активных − Σ компенсирующих`,
capability и policy разделены. ADR-0018 — **implementation slice** этого
принципа: что из него реализуется сейчас.

## Контекст

`transfer_ledger` исторически предоставлял публичный API, ориентированный
только на причины `TRANSFER_SEND` и `TRANSFER_RECEIVE`, хотя внутренние
builder'ы уже поддерживали произвольный `Reason`.

В коде существовали отдельные локальные формулы для `FINAL_RELEASE`
(`_released_qty_subquery`, `_net_released_by_dimensions`,
`already_released_by_size`). Это создавало риск расхождения семантики между
передачей и выпуском, особенно в присутствии компенсирующих проводок: три
неконсистентных чтения одного понятия «уже выпущено».

При этом «уже отдано» используется write-guard'ами и должно иметь единую
семантику: для соответствующей причины учитывается нетто-количество, то
есть исходные проводки с учётом компенсаций.

## Решение

**Единственный семантический primitive** — row-level `net_quantity_expr()`
(публичный, переименован из приватного `_net_quantity_expr`). Он один
интерпретирует `compensates_tx_id`: `case(compensates_tx_id IS NULL → qty,
else_ −qty)`. Ни один consumer сам не считает net — только через него.

**Публичные query-композиции** поверх него для удобства потребителей:

- `net_by_reason(reason, ...)` — scalar net по причине;
- `net_by_reason_by_dimensions(reason, ...)` — grouped net по габаритам;
- `net_by_reason_sq(reason, ...)` — SQL-подзапрос для set-based потребителей.

Существующие `net_transferred`, `net_received` и их варианты сохранить как
thin wrappers над новым ядром, чтобы не создавать churn у существующих
потребителей. Никаких других копий формулы нетто не остаётся.

`FINAL_RELEASE` становится полноценным пользователем того же примитива
с `Reason.FINAL_RELEASE`.

Следующие локальные реализации `FINAL_RELEASE` мигрируют на общее ядро:

- `_released_qty_subquery` → `net_by_reason_sq(Reason.FINAL_RELEASE)`;
- `_net_released_by_dimensions` → `net_by_reason_by_dimensions(Reason.FINAL_RELEASE)`;
- `already_released_by_size` → `net_by_reason(Reason.FINAL_RELEASE)`.

Таким образом, «уже отдано» по `(задача, размер)` определяется через нетто
по соответствующей причине, а не через отдельную локальную формулу.

## Переименование модуля

`stock/transfer_ledger.py` переименовывается в `stock/ledger.py`; alias /
re-export не оставляется. Это часть данного среза: новый API не должен жить
в старом misleading namespace.

## Capability / policy

Ledger-capability универсальна: `net_quantity_expr()` умеет net для **любой**
причины. **Решение о том, какие причины бизнес-операция вправе компенсировать,
принадлежит операции, а не ledger.** Сегодня компенсируемы только передачи
(`cancel_transfer`).

**COMPLETE/SCRAP остаются gross** — не потому что ledger не поддерживает их
net, а потому что текущий доменный контракт не требует компенсационного
поведения для них. Их gross-чтения в этом срезе не изменяются. Появление
универсального primitive не означает, что все quantity reads обязаны
перейти на net: переход происходит там, где домен требует.

## Границы решения

Этот срез не реализует бизнес-операцию отмены `FINAL_RELEASE`.

`FINAL_RELEASE` лишь получает ту же comp-aware семантику агрегации, что и
остальные причины. Примитив поддерживает компенсации как часть общей модели
ledger, но создание компенсирующей проводки для выпуска не входит в данный
срез.

## Инварианты и верификация

Добавляется независимый D4-инвариант:

> Нетто `FINAL_RELEASE` по `(задача, размер)` не превышает произведённое
> количество по `(задача, размер)`.

Также добавляется regression-тест, подтверждающий, что компенсированный
`FINAL_RELEASE` не блокирует дальнейший выпуск.

Проверки S6/D2 сохраняются на сыром SQL и не переводятся на новый примитив.
Они намеренно остаются независимым oracle, чтобы тесты могли обнаруживать
расхождения самого примитива и его потребителей.

## Последствия

### Положительные

- Одна семантика net-агрегации для `TRANSFER_SEND`, `TRANSFER_RECEIVE`
  и `FINAL_RELEASE`.
- Единственная реализация компенсационной арифметики — `net_quantity_expr()`;
  ни один consumer не интерпретирует `compensates_tx_id` для вычисления net.
- Новая причина ledger не требует отдельного семейства публичных функций.
- Write-guard'ы используют тот же comp-aware источник истины, что и
  остальные потребители.
- Старый API остаётся совместимым через thin wrappers.
- Независимые SQL-проверки сохраняют способность обнаруживать ошибки
  в primitive.

### Отрицательные

- Публичный API становится более общим и требует понимания `Reason`.
- Семантика компенсаций теперь распространяется и на `FINAL_RELEASE`, хотя
  отдельной операции отмены выпуска пока нет.
- В системе появляется дополнительный уровень абстракции между
  специализированными wrappers и reason-параметризованным ядром.
