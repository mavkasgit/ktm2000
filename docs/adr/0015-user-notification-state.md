# Состояние уведомлений — UserNotificationState

## Статус

accepted

## Решение

Модель уведомлений разделена на контент и состояние:

- **Notification** — что произошло и что показать (тип, заголовок, payload,
  ссылка на объект). Чистый контент, не знает про прочтение.
- **Адресация** — деталь хранения, а не тип: `user_id IS NULL` = общее
  уведомление для всех, `user_id` заполнен = персональное конкретному
  пользователю. Термин «broadcast» — только технический жаргон, не домен.
- **UserNotificationState** — состояние уведомления относительно конкретного
  пользователя: `read_at`, `closed_at`. Единственное место хранения состояния
  и для общих, и для персональных уведомлений. **Ленивое создание**: запись
  появляется при первом действии пользователя; отсутствие записи означает
  «непрочитано и активно».

## Почему

В `InternalNotification` состояние (`read_at`/`closed_at`) жило на общей
строке, из-за чего read/close общего уведомления мутировал состояние для
всех пользователей (тикет #86). Разделение контента и per-user состояния
устраняет это: общее уведомление существует одно, а каждый пользователь
имеет своё состояние относительно него.

## Последствия

- `internal_notifications` переименовывается в `notifications`; поля
  `read_at`/`closed_at` со строки уведомления удаляются.
- Новая таблица `user_notification_states(notification_id, user_id,
  read_at, closed_at)` с UNIQUE-индексом `(notification_id, user_id)`,
  каскадами на обе стороны; upsert без перезаписи дат.
- Список и `unread_count` считаются через join: отсутствие state-записи =
  активное непрочитанное; прочитанное-но-не-закрытое остаётся в списке,
  не в `unread_count`.
- Доступ сохранён как в #78: чужое персональное → 404, общее доступно
  любому аутентифицированному пользователю.
