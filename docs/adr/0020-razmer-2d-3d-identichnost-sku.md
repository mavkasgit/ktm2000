# ADR-0020: Размер 2D/3D — часть идентичности SKU

Дата: 2026-08-25. Статус: принято (правило помечено как пересматриваемое).

## Контекст

ADR-0001 установил «один SKU может лежать в нескольких размерах» безусловно.
С введением размерностей артикула (`dimension_state`, ADR-0012, #72)
выяснилось: для листов (`area`/`volume`) размер жёстко определяет площадь,
а площадь — количество на подвес. Хранение нескольких разных листов под
одним SKU лишено смысла: каждый размер = свой SKU.

## Решение

Правило мультиразмерности становится state-зависимым:

- **1D (`length`)** — один SKU, много длин (как в ADR-0001);
- **2D (`area`) / 3D (`volume`)** — ровно один типовой набор значений
  в `product_dimensions`; набор — часть идентичности SKU.

Инвариант enforced на входах домена (импорт остатков, импорт плана,
API прихода): проводка под 2D/3D-SKU с `dimensions` ≠ типовому набору —
ошибка строки/422 с объяснением, почему отвергнуто и что исправить.
Ledger остаётся генериком: группировка баланса по полному `dimensions`
не меняется.

## Отклонённые альтернативы

- **Мультиразмер для всех состояний** — модель проще, но остатки
  разъезжаются с карточкой артикула; «размер = SKU» существует только
  на бумаге.
- **Мягкий режим** (UI показывает типовой набор, ledger принимает любой) —
  расхождение данных обнаруживается постфактум, чинить дороже.

## Последствия

- Валидаторы импорта (#87 и импорт остатков) отклоняют несовпадающие
  наборы с человекочитаемым объяснением.
- Импорт справочника (#87): изменение самого набора 2D/3D у существующего
  SKU — ошибка строки («заведите новый SKU»), а не тихая правка.
- Глоссарий (`CONTEXT.md`: «Размеры», «Размерность артикула») синхронизирован.
- ⚠️ Правило зафиксировано как **пересматриваемое**: возможен пересмотр
  при развитии домена листов — см. пометку в статусе.
