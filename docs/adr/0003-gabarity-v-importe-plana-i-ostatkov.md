# ADR-0003: Габариты в импорте плана и импорте остатков

Дата: 2026-07-30. Статус: принято.

## Контекст

Импорт плана (`app/services/excel_import.py`) уже парсит колонки
«кол-во шт. в 2,7» (`input_quantity`), «Длина, м» (`input_length`),
«Длина после упак, м» (`output_length`), «кол-во штук готовой продукции»
(`output_quantity`) — но складывает их в `source_payload` как текст,
не влияя на учёт. Импорт остатков (`app/stock/import_service.py`)
длину не принимает вовсе.

Разбор реального файла «Упаковочный план.xlsx» (2026-07-30) показал:
операция резки с несколькими выходами записана **группой строк
с объединёнными ячейками** — вход («кол-во шт. в 2,7», «Длина, м»)
объединён на все строки группы, выходы идут построчно. Пример
(ЮП-2083, строки 34–35): вход `150 × 2,7` объединён на две строки,
выходы `150 × 0,9` и `150 × 1,8`. Баланс группы всегда сходится точно
(строки 36–37: 1500×0,9 + 900×1,8 = 1100×2,7). Соседние строки того же SKU **без**
объединения — отдельные операции со своим входом.

## Решение

1. **Группа строк = одна позиция плана.** Единица импорта — группа по
   объединённой ячейке входа: строка с собственным входом открывает
   группу; строка-продолжение (тот же артикул, вход пуст/объединён) —
   ещё один выход той же группы. Одиночная строка — группа из одного
   выхода. АТ-7121 (150 × 2,7 → 350 × 0,9 + 50 × 1,8) — **одна**
   PlanPosition с двумя выходами.
2. **Payload → первоклассные поля**: при создании PlanPosition вход
   (`input_quantity` × `input_length`) материализуется в dimensions
   входа, все строки группы — в выходную спецификацию
   `[(output_quantity, output_length)]`.
   Конвенция единиц: в Excel метры («2,7») → в dimensions миллиметры (2700).
   Пустая «Длина, м» при заполненном выходе → вход без резки: входная
   длина = выходной, либо типовой размер продукта.
3. **Импорт остатков — длина обязательна** для продуктов, у которых
   в `product_dimensions` измерение помечено `is_required`:
   - колонка «Длина» есть и заполнена → берём её;
   - не заполнена → подставляем типовой размер (`default_value`);
   - нет и типового → строка invalid с ошибкой.
4. **План — источник правды**: задание на трансформирующем участке берёт
   вход/выход только из позиции плана; оператор размеры не назначает.

## Последствия

- Парсер импорта плана читает merged-ячейки (openpyxl `merged_cells`)
  и/или пустой вход строки-продолжения для сборки групп; fingerprint
  идемпотентности считается по группе.
- `PlanPosition` хранит один вход и **список выходов** (1..N).
- `RemainderItem` получает поле длины/dimensions; шаблон импорта остатков —
  колонку «Длина».
- `StockCommand` / `StockCommandService.record` принимают dimensions
  и пишут его в `StockTransaction`.
- Плановая цепочка (SectionPlanLine → WorkTask) переносит dimensions
  от позиции до задания без потерь.

## Обновление (2026-08-10): дефолтный маппинг остатков — JSON, не шаблон

Пункт 3 выше говорил о «шаблоне импорта остатков» как о колонке «Длина».
Уточняем место хранения маппинга остатков: он **не пользовательский шаблон**.

- **Шаблон импорта** (`ImportTemplate`, таблица `import_templates`) — только
  для импорта плана (сид «Упаковочная карта РП»). Показывается в UI
  (страница планов, «Шаблоны импорта»).
- **Маппинг остатков** — системный дефолт импорта остатков, живёт в JSON-файле
  `backend/app/stock/remainders_columns.json` (колонки + `_config.length_required`),
  читается `load_remainders_default_mapping()` в `app/stock/import_service.py`.
  В таблицу `import_templates` не попадает (миграция `041` удалила
  код `ostaki_ktm`), поэтому в UI не показывается.
- Причина: импорт остатков не имеет селектора шаблона и всегда парсит по
  дефолту; держать дефолт строкой в таблице шаблонов означало показывать
  его в UI как пользовательский шаблон (что сбивало с толку — «Остатки КТМ»
  светился на странице планов).
