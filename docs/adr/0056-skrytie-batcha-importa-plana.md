# ADR-0056: Батч импорта плана — скрытие рядом с физическим удалением

Дата: 2026-09-30
Статус: принято (гриллинг, #233)
Контекст: удаление батча импорта плана было физическим и единственным; у
остатков тот же вопрос решён мягким удалением (ADR-0052 п.5)
Связанные: ADR-0019, ADR-0025, ADR-0052, ADR-0054

## Контекст

`DELETE /production-plans/{p}/batches/{b}` у батча плана — единственный способ
убрать импорт из истории. Он физический: откатывает применённые сеты, каскадно
сносит позиции (`_cascade_delete_positions`), удаляет строку `import_batches`,
а при отсутствии других ссылок — и `import_files` (`_delete_batch_and_orphan_file`).
След остаётся только в `AuditLog` (плюс, при force, в журнале действий).

«Спрятать» батч было нечем: в `import_batches` не было колонок мягкого удаления,
а `_plan_files_query` фильтровал лишь `ProductionPlan.deleted_at IS NULL` — то
есть батч нечем спрятать, не удалив. При этом «Убрать из списка» и «Удалить» —
разные намерения оператора: первое про читаемость, второе про данные. Смешивать
их нельзя, а выбирать приходилось только второе.

Образец уже есть в репозитории: у батча остатков «Убрать из списка» — это
`stock_import_batches.deleted_at` (ADR-0052 п.5), у плана же — архивирование
`production_plans.deleted_at` (миграция 070). Три поля, одна семантика.

## Решение

1. **Скрытие — отдельное действие, не режим `DELETE`.** Новый маршрут
   `POST /production-plans/{p}/batches/{b}/hide` пишет `deleted_at`,
   `deleted_by`, `delete_reason`. Позиции, задачи, ledger, узел журнала
   действий (ADR-0019 п.7) и `AuditLog` не трогаются. В UI — кнопка
   «Убрать из списка» с подтверждением, а не «Удалить».
2. **Статус и скрытость ортогональны.** Скрытым может быть и применённый, и
   распознанный, и откаченный батч: `deleted_at` не влияет ни на статус, ни на
   откат, ни на применение. Строка «Скрытость» в ответе несёт пометку, а статус
   остаётся прежним — в UI видно, что батч применён, но убран из списка.
3. **Список по умолчанию без скрытых**; `include_hidden=true` показывает их —
   так же, как у остатков. Скрытая строка помечена «Убрана из списка» и
   приглушена, кнопки скрытия у неё нет.
4. **Физическое удаление остаётся** отдельным действием с нынешним 409-контрактом
   (§4.4 спеки) и force-удалением (#231, ADR-0019 п.7). «Убрать из списка» не
   отменяет удаление и не является его заменой: снос данных — осознанный шаг с
   подтверждением и последствиями.
5. **Роль — `admin`, как у соседних мутаций батча.** Обсуждение исходило из
   «нового гейта не вводим»: на тот момент `DELETE .../batches/{b}` и
   `.../change-sets/{b}` были доступны любому аутентифицированному, и скрывать
   выходило бы «как и удалять» — гейтить слабое строже сильного нельзя. С тех
   пор маршруты плана закрыты ролями (ADR-0057, #235): удалить батч, применить и
   откатить может `admin`, а прочитать историю — любой из `READER_ROLES`.
   Посылка стала обратной: без гейта скрытие было бы единственной мутацией по
   батчам, открытой зрителю, то есть доступнее удаления. Поэтому скрытие —
   `admin`, как у соседей и как у скрытия батча остатков (ADR-0052 п.5); кнопка
   в UI рисуется по той же политике (`POLICIES.managePlanImport`).
6. **Восстановления из скрытых нет** (у остатков тоже): `include_hidden` даёт
   чтение, а не переключатель. «Спрятать» — не «удалить» и не «отменить».
7. **Бэкфилла нет и быть не может:** физически удалённые батчи невосстановимы —
   их нет ни в одной таблице, кроме `AuditLog`. Миграция только добавляет
   колонки; все существующие строки остаются видимыми.

## Отвергнутые альтернативы

- **Скрывать через `plan_change_sets` или через флаг в JSON.** Скрытость —
  свойство батча, а не его сета: у батча сет один, но не у каждого сета есть
  батч, и прятать «изменения» значило бы прятать не то.
- **Расширить `DELETE` флагом `?hide=true`.** Один маршрут с двумя разными
  последствиями — источник ошибок в клиенте: `method` в UI перестаёт отражать
  разрушительность действия. Разные действия — разные кнопки.
- **Дать скрытому батчу особый статус (`hidden`).** Статус отвечает на вопрос
  «что с батчем в плане», скрытость — на «хочу ли я его видеть». Смешанный
  статус ломает LIFO-откат и выбор последнего применённого (ADR-0025).
- **Скрывать батчи автоматически вместе с удалением.** Тогда «Убрать из списка»
  и «Удалить» перестают быть разными действиями, а 409-диалог §4.4 теряет
  смысл: оператор не может решить, что именно он делает.

## Последствия

- Схема: `import_batches.deleted_at/deleted_by/delete_reason` (миграция 075,
  FK на `users.id` c `ON DELETE SET NULL`, индекс по `deleted_at`).
- Контракт: `PlanFileInfo.hidden` (всегда, не только при `include_hidden`),
  `include_hidden` у `GET /production-plans/all-files` и
  `GET /production-plans/{p}/files`.
- LIFO-откат в UI считается по полному списку, включая скрытые: убранный из
  списка батч не перестаёт быть последним применённым, иначе скрытие разрешило
  бы откатить более старый (ADR-0025). Поэтому панель истории берёт
  `include_hidden=true` для карты «последний применённый», а на экран показывает
  видимое. То же — в диалоге применения: предупреждение о более свежем батче
  про план, а не про видимость строки.
- Кэш списка раздваивается: `include_hidden` входит в query-ключ
  (`allFiles(flag)`), потому что это разные ответы одного маршрута. Для
  инвалидации есть отдельный корень `allFilesRoot()`: префиксом одного варианта
  второй не покрывается, и «Обновить» на странице истории иначе обновлял бы
  только видимый список.
- `_delete_batch_and_orphan_file` считает ссылки на `import_files` по всем
  оставшимся батчам, включая скрытые: иначе удаление соседнего батча сломало бы
  «Скачать» у скрытого.
- `GET /imports/recent` (`/recent`, потребителей в UI нет) скрытые не фильтрует.
  Список-лента остаётся как есть: изменение его контракта — вне задачи, пока у
  него нет ни одного потребителя.
- Восстановления нет: чтобы «вернуть» батч, нужен физический путь, а он один —
  импорт заново.
