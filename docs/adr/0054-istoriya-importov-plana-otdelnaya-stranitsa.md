# ADR-0054: История импортов плана — отдельная страница, список кросс-плановый

Дата: 2026-09-30
Статус: принято (гриллинг)
Контекст: таблица файлов импорта уходила «верхней панелью» на странице плана;
образец размещения — история импорта остатков (ADR-0052)
Связанные: ADR-0019, ADR-0025, ADR-0030, ADR-0034, ADR-0037, ADR-0052

## Контекст

Таблица батчей импорта плана жила в карточке «Общий план» на странице
`/planning` (`PlanPage.tsx`): слева статистика (Файлов / Позиций / Общее
кол-во), справа семь колонок файлов с действиями, лимит пять строк и
«Показать ещё». Это была первая вещь на экране — до таблицы позиций, ради
которой страница и существует, — и при этом неполная: фильтров, сортировки и
пагинации у списка не было, а бэкенд `GET /production-plans/all-files`
(`backend/app/api/routes/production_plans.py:1540`) не принимает ни одного
параметра и отдаёт файлы **всех** планов.

Страница плана показывает файлы одного плана — `plans[0]`
(`PlanPage.tsx:95-96`), а позиции — **всех**: `AllPlanPositionsParams` не
содержит параметра плана (`shared/api/productionPlans.ts:196-219`), каждая
строка несёт свой `production_plan_id`, и массовые операции уже группуются по
нему. То есть карточка называла `{plan_no} · {name}` одного плана над таблицей
чужих позиций: подпись не описывала то, что под ней. Старые планы при этом
недостижимы вообще — переключателя плана нет.

## Решение

1. **История импортов плана — отдельная страница**
   `/planning/import-history` (`features/planning/pages/PlanImportHistoryPage.tsx`),
   ленивый маршрут рядом с `/planning`. Вход — кнопка «История импортов» в
   шапке страницы плана, рядом с «Добавить файл»; пункта в боковом меню нет,
   раздел у истории тот же — «План». Кнопки импорта остаются на странице плана:
   загрузка файла — действие этого экрана, как «Импорт из Excel» на ГХП
   (ADR-0052).
2. **Список кросс-плановый, с колонкой «План».** В таблице батчи **всех**
   планов, подпись плана — `plan_no · name` из `listPlans()` (`PlanSummary`),
   сшитая на клиенте по `production_plan_id` строки: правок ответа API не
   требуется, `/all-files` и так отдаёт все планы. Если план из списка пропал
   (гонка двух запросов), ячейка деградирует до «План #id», а адрес действия
   остаётся верным.
3. **Порядок — серверный** (`ImportBatch.created_at DESC`), свежие сверху.
   Своей сортировки на клиенте нет; фильтров и пагинации тоже — список
   открывают раз в неделю, а серверный контракт сортировки/фильтров
   (ADR-0034, ADR-0037/0038) на `/all-files` не заводится.
4. **Откат — LIFO внутри плана.** «Последний применённый» считается по
   `applied_at` среди батчей **того же** плана (`lastAppliedBatchIdByPlan` в
   `lib/appliedBatches.ts`), иначе свежий импорт второго плана погасил бы откат
   у первого. Правило LIFO — гейт UI (ADR-0025); сервер его не проверяет.
5. **Действия строки и модалки переезжают целиком:** «Просмотр», «Скачать»,
   «Применить» (`parsed`/`cancelled`), «Откатить» (`applied` + LIFO), «Удалить»
   с 409-выбором «только черновики» и force-удалением. Карточка «Общий план» со
   статистикой удаляется: «Файлов» считалось по одному плану, «Позиций» — по
   другому источнику, и держать эти два счётчика рядом больше негде.
6. **Права не меняются.** Ролевых гейтов у маршрутов батчей сегодня нет вовсе
   (`/all-files` и `list_plans` даже без `get_current_user`; apply/rollback/
   batch-delete — аутентификация без роли; force-удаление — admin), и перенос
   таблицы это не чинит и не ломает. Дыра выделена в отдельные задачи: #235
   (ролевая матрица план-импортных маршрутов) и #234 (`reset-all`).
7. **Legacy-план ведёт себя как раньше:** `apply` и отмена черновика дают
   `400 legacy_plan_read_only`, а откат и удаление батча разрешены намеренно
   (`test_plan_import_rollback.py:236-253`, `test_batch_delete_409.py:201-229`).
   UI-гейта для legacy нет: сервер уже отвечает точной причиной, а признака
   legacy в `PlanFileInfo` не существует — заводить поле в ответе ради
   спрятанной кнопки не стали.
8. **Пустое состояние страницы плана считается по позициям**
   (`positionsTotal === 0` при отсутствии активных фильтров), а не по
   `activePlan.total_positions`: позиции кросс-плановые, и план без своих
   позиций с позициями старых планов не должен выглядеть пустым.

## Отвергнутые альтернативы

- **Оставить таблицу на странице плана, добавив вкладки.** Вкладка не убирает
  панель с рабочего экрана, а история импорта нужна реже, чем таблица позиций.
- **Список только активного плана** (поведение как было, просто на другом
  URL). Старые планы остаются недостижимыми, а слово «история» обещает
  обратное.
- **Серверный контракт на `/all-files`** (сортировка ADR-0034, фильтры
  ADR-0037/0038, пагинация). Доработка бэкенда ради списка, который читают
  раз в неделю; объём данных — батчи импортов, а не позиции.
- **Глобальный LIFO отката** — практический тупик: второй план гасит откат
  первого (тот же довод, что в ADR-0052 п.3 для склада).
- **UI-гейт legacy-плана** (disabled «Применить» с подсказкой) — требует
  нового поля в `PlanFileInfo` и дублирует серверное правило.
- **Свой компонент таблицы** вместо `FileRow`: строка уже умеет все три
  действия и модалки, второй набор правил разъехался бы с первым.

## Последствия

- `PlanPage` теряет запрос `all-files`, `findLastAppliedBatchId`,
  `handleDeleteFile`, `handleConfirmDeleteDrafts`, `BatchDeleteBlockersDialog`
  и стат-карточку; пустое состояние экрана плана теперь про позиции.
- `findLastAppliedBatchId` заменён на `lastAppliedBatchIdByPlan` (карта вместо
  одного id) — тест `lib/appliedBatches.test.ts` проверяет то же правило LIFO
  плюс независимость планов.
- `FileRow` принимает `planId` и `planLabel` вместо объекта `PlanSummary`:
  подпись плана и адрес действия собирает тот, у кого есть `listPlans`.
- e2e-хелпер `waitForPlanningTableViaUI` больше не может ждать заголовок
  «Общий план» — ожидание переведено на заголовок сводной таблицы позиций.
- Удалённый батч **не остаётся** в истории: удаление физическое —
  `delete_import_batch` (`services/production_plan_service.py:992`) откатывает
  применённые сеты, сносит позиции и вызывает `_delete_batch_and_orphan_file`
  (`:769`), который удаляет строку `import_batches` и осиротевший
  `import_files`; след остаётся в `AuditLog`, а у force-удаления — ещё и в
  журнале действий (`purged`). Рядом с ним есть мягкое действие «Убрать из
  списка» (`POST .../batches/{b}/hide`, `import_batches.deleted_at`,
  `include_hidden` в обоих списках) — [ADR-0056](0056-skrytie-batcha-importa-plana.md);
  оно прячет строку и не трогает данные, тогда как «Удалить» по-прежнему
  сносит поддерево батча.
- Потолок списка: вся история в одном ответе `/all-files`. Если батчей станут
  сотни, первым шагом будет пагинация на бэкенде, а не клиентский срез.
