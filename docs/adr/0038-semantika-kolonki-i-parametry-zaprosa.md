# 0038. Семантика колонки объявляет и фильтр, и параметр запроса

- **Статус:** принято
- **Дата:** 2026-09-27
- **Связано с:** ADR-0034 (сортировка строк), ADR-0037 (семантика колонок), ADR-0030 (компактная строка)

## Контекст

В #197 семантика колонки объявлялась один раз — в `ColumnSpec` — но только
для двух экранов: доски участка и контроля выполнения. На остальных шести
семантика жила в трёх местах сразу:

1. в разметке шапки (`sortable={false}`, `valueLabel`, отсутствие `onSearchChange`);
2. в функции сборки параметров запроса (`buildXColumnApiParams`);
3. в списке колонок, для которых собираются значения фильтра.

Пяти экранов хватало функции `buildXColumnApiParams`, и в каждой колонка была
перечислена строкой. Шестую колонку нужно было бы дописать в пяти местах.

Описание колонки при этом не умело сказать, **каким параметром** она уезжает.
Серверные имена расходились с именами колонок: «Артикул» на плане — это
`source_sku`, на аудите — `product_sku`, «Ошибки» — это `has_errors` с
перекодировкой «0» → `no`. Имя колонки знала шапка, серверное имя знала сборка,
и связать их было нечем.

### Что вскрылось при переносе

Перенос на описание колонок обнаружил четыре расхождения, которые были не
видны, пока семантика жила в разметке:

- **Фильтр «Размер» на плане не фильтровал ничего.** `buildPlanColumnApiParams`
  отдавал `dimensions`, а страница перечисляла поля запроса руками и
  `dimensions` среди них не было. Колонка была видна, попапер работал, строки
  не менялись. Проверено в backend: параметр принимается и применяется
  (`production_plans.py`, `parse_dimensions_filter`).
- **Попапер «Дата и время» в аудите не делал ничего.** Сервер знает только
  диапазон `date_from` / `date_to`, который уже вынесен в панель фильтров.
- **Счётчик активных фильтров врал на двух экранах.** `useFilterableTable`
  считал любой непустой `sortConfigs` активным фильтром, поэтому экраны с
  сортировкой по умолчанию писали своё условие — и оно расходилось между
  собой.
- **Поиск в поповере габаритов зажигал кнопку сброса.** На доске поиск писался
  в состояние таблицы, на плане — нет, хотя «Размер» на обоих выбирается
  кликом по габариту.

## Решение

### 1. Описание колонки объявляет и параметр запроса

`ColumnSpec` дополнен полями, из-за которых колонка не выражалась:

| поле | смысл |
|---|---|
| `apiParam` | серверное имя параметра, если оно не совпадает с именем колонки |
| `mapValue` | перекодировка значения: «Не назначен» → `no`, «—» → ничего |
| `toParams` | колонка, дающая несколько параметров сразу |
| `clientOnly` | фильтруется на клиенте и в запрос не уезжает |

`buildColumnApiParams(columnFilters, columnSearchQueries, columns)` заменяет
пять функций `buildXColumnApiParams`. Перечисления колонок в ней нет: список
берётся из описания, поэтому шестая колонка не требует правки кода, который
собирает параметры.
### 2. Сортировка по умолчанию объявляется хуку

`useFilterableTable` принимает `defaultSort`. Порядок строк по умолчанию:

- не считается активными фильтрами;
- возвращается сбросом, а не превращается в пустоту;
- не требует `useEffect`, который ставит его после монтирования.

Экраны перестали писать «сортировка нестандартная» руками.

### 3. Один рендерер на все четыре сочетания

`DataTableColumnHeader` получает описание колонки и сам решает, что рисовать:

| фильтр | сортировка | что рисуется |
|---|---|---|
| да | да | попапер фильтра + кнопка сортировки |
| да | нет | попапер фильтра |
| нет | да | текст + кнопка сортировки |
| нет | нет | текст |

До #198 экран выбирал между этими случаями тернарником в шапке, и третья
строка таблицы не существовала: колонка «Дата и время» в аудите потеряла
кнопку сортировки при первом же переносе.

Поиск в поповере точной колонки остаётся локальным и не пишет в состояние
таблицы: иначе счётчик активных фильтров врал бы.

### 4. Колонка без фильтра объявляется честно

Там, где сервер фильтр не принимает, колонка объявлена **без** `filterField` и
без `sortField`, а не с флагом, который ничего не отправляет:

- **«Размер» в журнале передач** — `TransferHistoryListParams` не знает такого
  параметра, `listTransferHistory` его не сериализует;
- **«Размеры» на складских остатках** — `GET /stock/balance` не принимает
  габарит, `_BALANCE_SORT_COLUMNS` его не содержит;
- **«Длина» в предпросмотре импорта остатков** — сервер сравнивает подпись
  `dimensions_label` через `needle in haystack`, параметра точного совпадения у
  него нет.

Объявлять в этих местах `exactMatch` означало бы отправить параметр, которого
сервер не понимает. Молчащий фильтр хуже его отсутствия, поэтому попапер
убран, а диапазон дат остался в панели фильтров.

### 5. Точный фильтр не мультизначен

`buildColumnApiParams` и `readColumnValue` читают значение точной колонки
одним и тем же `pickExactMatchColumnValue`: значение уходит, только если
выбрано **ровно одно**.

Раньше доска и контроль отправляли первое из выбранных значений, а план и
передачи — ничего: один и тот же клик по «Выбрать все» в поповере габаритов
давал разный запрос на разных экранах. Отправлять первое — значит
фильтровать по произвольному размеру, и это молчаливое искажение выбора
оператора.

## Последствия

**Хорошо**

- Семантика колонки объявляется один раз; добавление колонки не требует правки
  сборщика параметров.
- Фильтр «Размер» на плане работает.
- Счётчик активных фильтров и сброс считаются по одному правилу на всех
  экранах.
- Описание можно проверить тестом: `planApiParams.test.ts` держит сверку с
  backend-списком сортируемых полей, новые тесты держат сборку параметров.

**Плохо**

- `ColumnSpec` вырос с четырёх полей до восьми. Это цена единого места: иначе
  серверные имена возвращаются в сборщик, а он — в каждую таблицу.
- `buildColumnApiParams` отдаёт строки, поэтому `plan_position_id`, объявленный
  в контракте запроса числом, требует одного приведения на границе. По проводу
  это одно и то же: значение сериализуется в строку запроса в обоих случаях.

**Нейтрально**

- `SettingsBackupsPage` переведён на `useFilterableTable` вместе с остальными
  экранами: его прежняя одно-колоночная сортировка (замена приоритета) заменена
  мультисортировкой с `defaultSort` `created_at:desc`. Решение принято ради
  единообразия — порядок строк читает один хук, — а не потому, что прежнее
  поведение было неверным: сервер умеет сортировать по любой колонке списка
  бэкапов. Мультисортировка добавляет приоритет, а не заменяет: клик по «Имя
  файла» поверх дефолта даёт `created_at:desc,filename:desc`.
