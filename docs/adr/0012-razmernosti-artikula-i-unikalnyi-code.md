# ADR-0012: Размерности артикула (1D/2D/3D) и уникальный code

Дата: 2026-08-09. Статус: принято.

## Контекст

В рамках #64/#65 (таблица «Расчёт подвесов» и форма артикула) в код влились
два расширения, не заявленных в спеках этих задач: (1) **размерности
артикула** — `dimension_state` `length | area | volume` с переделкой
`ProductDimensionsSection` под 2D/3D-поля; (2) **уникальный `code`** —
строковый идентификатор продукта с уникальным ограничением (миграция 033).
Оба изменения рабочие и покрыты тестами, но без записи решения выглядели
как scope creep.

## Решение

1. **Размерности** — артикул имеет ровно одну размерность
   (`dimension_state`: `length` — «Длина, мм» как ось учёта; `area` —
   «Длина × Ширина × Толщина»; `volume` — «Длина × Ширина × Высота»).
   `length` — размерность по умолчанию и единственная, участвующая в
   подвесе/подвесном расчёте. Кол-во на подвесе настраивается только для
   `length` — в 2D/3D-ветке формы показывается текстовая плашка, а не
   заглушка-инпут.
2. **`code`** — короткий уникальный код продукта (машиночитаемый
   идентификатор для импорта/интеграций), опционален и не конфликтует
   с `sku` (человекочитаемый артикул). Уникальность обеспечивает
   unique-constraint; дубль при create/patch → 409.

## Отклонённые альтернативы

- **Не добавлять размерности** — оставить только «Длину, мм»: проще, но
  справочник сырья содержит и плоские/объёмные изделия (лист, брус), где
  длина как единственная ось бессмысленна.
- **`code` = `sku`** — не разделять идентификаторы: дешевле, но `sku`
  меняется пользователем и переиспользуется как имя; стабильный внешний
  идентификатор пригодится для импорта (Ref #63) и будущих интеграций.

## Последствия

- `dimension_state` и `code` — первоклассные поля продукта, участвуют в
  diff/patch формы и выводятся в списке сырья.
- Смел-находки ревью, связанные с размерностями (ветвление
  `dimension_state` в трёх местах), не откатываются, а решаются
  рефакторингом в рамках плана закрытия findings.
