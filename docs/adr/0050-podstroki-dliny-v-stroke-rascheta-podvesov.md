# ADR-0050: Строка расчёта подвесов разбита на подстроки по длинам

Дата: 2026-09-28
Статус: принято
Связанные: ADR-0013 (основная длина), ADR-0028 (нормальная и сырьевая
длина), ADR-0030 (компактная строка), ADR-0047 (строгий ключ нормы), спека #59
(п. 14, п. 18, п. 25), ADR-0049 (соседнее решение по видимым причинам)

## Контекст

Таблица «Расчёт подвесов» показывала одну строку на артикул, а колонки
разбивки («По площади», «По размеру», «Итог», «Лимитер», «м² на подвес»)
считались **по основной длине**. Остальные длины жили чипами в колонке
«Длины → кол-во», а их разбивка — в тултипе чипа.

Расчёт при этом per-length и всегда им был: `buildCalcItems` отправляет в
`POST /hanger-calc` по одному item на пару «артикул × длина», а
`calcMap: Map<productId, Map<длина, результат>>` хранит результат по каждой
длине. То есть данные для разбивки по всем длинам были на экране, но таблица
показывала одну из них.

Из этого выросли два дефекта, оба — на глазах у оператора:

1. **Разбивка не соответствует тому, что считается.** У ЮП-460 нормальная
   длина 2700 (сырьё 2700), вторая — 2750. Итог строки — 72 шт по 2750, а
   «основная» 2700 без значения; оператор видел «Итог 72» рядом с чипом
   2750 и «основную» 2700, которой в колонках разбивки нет вовсе.
2. **Формулировка причины врёт.** В ручном режиме все пять колонок разбивки
   показывали «—» с подсказкой «Ручной режим: периметр или габарит не
   заполнены, расчёт не запускался». В ручном режиме периметр и габарит не
   нужны вовсе: причина в отсутствии ручной нормы для основной длины.

Отдельно: колонка «Кол-во на подвесе» в **списке «Сырьё»** печатала норму
не основной длины как норму артикула, тогда как её сортировка, фильтр и
попапер читают N основной длины. У 47 линейных артикулов с несколькими
длинами нормы на основной длине нет, и колонка показывала не то, по чему
сортирует (спека #59 п. 25 в том виде, как реализовано, нарушалась).

## Рассмотренные варианты

**(а) N строк таблицы на артикул × длину.** Разбивка честная, но рушит всё,
что держится на «одна строка = один артикул»: `key` строки, состояние
«сохраняется / сохранено» (хранится по `product.id`), попапер значений
фильтра, поиск и сортировка по артикулу становятся «строковыми», хотя это
свойство артикула. Плюс спека #59 п. 14 («одна строка = один артикул»)
снимается целиком.

**(б) Оставить как есть, чинить только формулировку причины.** Дешёво, но
разрыв между «Итогом» строки и чипами длин остаётся: оператор по-прежнему
видит одну разбивку на несколько длин.

**(в) Многострочная строка: одна строка на артикул, внутри по подстроке на
каждую длину.** Разбивка едет рядом со своей длиной, «одна строка = один
артикул» остаётся буквально, правки вне двух вьюмов не нужны.

## Решение

1. **Строка = артикул (или пара A+B), внутри — подстроки по длинам.** Модель
   строки получает `lines: HangerLengthLine[]` — по одной на длину реестра
   (для листа длина одна, подстрока одна). В `<td>` артикула, периметра и
   габарита ставится `rowSpan={lines.length}`; колонки длины и разбивки
   печатают по элементу на подстроку. Новых колонок не появляется: подстрока
   — это содержимое ячейки, а не дополнительные ячейки таблицы.
2. **N подстроки — это N длины, а не N артикула.** Поля периметра и габарита
   принадлежат артикулу, поэтому занимают одну ячейку на всю строку, и
   индикатор «сохраняется / сохранено» — тоже один.
3. **Разбивка берётся у длины подстроки.** «Итог» подстроки — N этой длины:
   авто-итог движка или ручная норма из словаря по ключу этой длины.
   «По площади», «По размеру», «Лимитер» и «м²» печатаются, только если у
   этой длины есть результат расчёта.
4. **Сортировка, фильтр и попапер по «Итогу» и «Лимитеру» — по основной
   длине.** Многозначность в строке иначе означала бы, что клик по колонке
   сортирует по величине, которой на экране нет; `row.total` и `row.limiter`
   остаются агрегатами основной длины и продолжают быть ключом сортировки.
5. **Причина «—» называет длину.** Ручной режим без нормы: «Ручной режим:
   для длины 2500 мм не задана норма». Ручной режим с нормой: «Ручной
   режим: расчёт по периметру не запускался». Нет результата в авто-режиме:
   «Расчёт невозможен: не хватает данных». Причина несовместимости — своя,
   она общая для всех подстрок строки.
6. **Подпись длины печатает сырьё только когда оно отличается** от
   нормальной: `2700 / сырьё 2750 мм`, а при равных — `2700 мм`. Правило
   одно для одиночных строк и пар (`formatLengthLabel`,
   `formatPairedLengthLabel`).
7. **Парные строки A+B устроены так же.** Расчёт пары зависит от длины так
   же, и оставить пару с одной разбивкой значило бы оставить в одной
   таблице два разных правила.
8. **Список «Сырьё» не делится на строки, но становится честным.** Колонка
   «Кол-во на подвесе» печатает N **основной** длины с подписью «при
   2700 мм» и бейджем источника; если у основной длины нормы нет — «—» с
   подсказкой «норма не задана для 2700 мм; для 2750 мм — 51 шт (авто)».
   Это спека #59 п. 25 в том виде, как она и была задумана.
9. **Высота строки уточняется рядом с таблицей.** `ADR-0030` задаёт общий
   набор для строки 40 px; у таблицы подвесов он уточняется собственной
   константой, потому что число подстрок определяется данными артикула.

## Последствия

- Спека #59: п. 14 отменяется в части «разбивка — по основной длине» и
  п. 18 (чипы длин с разбивкой в тултипе); первая фраза п. 14 («одна строка =
  один артикул») и п. 25 остаются в силе и теперь исполняются.
- `ADR-0013` не противоречит: основная длина по-прежнему помечается, теперь —
  в своей подстроке.
- `LengthChips` и `PairedLengthChips` удалены вместе с чипами: колонка
  «Длины → кол-во» становится «Длиной» и печатает по подстроке на длину.
- Данные, запросы и правка не меняются: batch уже per-length, PATCH уже
  per-product. Правка периметра пересчитывает все длины артикула, как и раньше.
- Тесты `hangerCalcRows.test.ts`, `hangerCalcColumns.test.ts` и
  `HangerCalcTable.sorting.test.tsx` переписаны под новый контракт строки.
