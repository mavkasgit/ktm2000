# ADR-0063: «Размер» на доске — один домен: габарит задания

Дата: 2026-10-02
Статус: принято
Тикет: #286
Связанные: ADR-0001, ADR-0002, ADR-0035, ADR-0044, ADR-0058

## Контекст

Колонка «Размер» на доске участка собиралась из двух разных полей:

- **показ** (`taskGroupingDimensions`) — `input_dimensions` трансформирующего
  этапа, иначе `dimensions` (`frontend/src/features/sections/lib/groupTasksByProfile.ts`);
  это же выражение кормило ключ и подпись группы, bulk-панель, «План участка»
  и поле «Размер» карточки;
- **фильтр и сортировка** — `WorkTask.dimensions` точным совпадением JSONB
  (`queries_sections.py`, `dimensions_match_clause`).

На обычных данных расхождения не видно: `WorkTask.dimensions` — всегда
канонический `{"length_mm": N}` (`position_dimensions_for_task`), а у
трансформирующей позиции это длина входа, то есть то же значение, что лежит
в `input_dimensions`, только спроецированное в один ключ (в dev-БД 42 из 42
трансформирующих задач совпадали).

Расхождение достижимо, когда два представления не совпадают:

- вход несёт лишние ключи (`width_mm`, `thickness_mm`) — приходит из
  `resolve_product_dimensions` у 2D/3D-артикула (`plan_import_service.py`);
  ячейка печатала `length_mm: 2700, width_mm: 100`, а фильтр сравнивал
  `{"length_mm": 2700}`;
- вход непуст без `length_mm` — тогда `dimensions` = `NULL`, а показ нёс бы
  сам объект;
- принимающая задача, созданная передачей, лениво: `dimensions` = переданный
  размер, `input_dimensions` = вход позиции (`transfers/services.py`) — показ
  показывал вход позиции, хотя на участок физически приехал размер передачи.

Из-за этого «Размер» был намеренно исключён из серверного справочника значений
(`BOARD_COLUMN_VALUE_FIELDS`, #211): значение, собранное по одному
представлению, для второго было бы чужим.

## Решение

**«Размер» на доске — габарит задания (`WorkTask.dimensions`), и это
единственный домен колонки.**

- `taskGroupingDimensions` всегда возвращает `dimensions`: показ ячейки, ключ и
  подпись группы, bulk-панель, «План участка» и карточка читают одно поле;
- фильтр (`?dimensions=`) и сортировка уже читают его же — не менялись;
- серверный справочник значений колонки расширен на «Размер»
  (`BOARD_COLUMN_VALUE_FIELDS = {"product_sku", "dimensions"}`); значения
  отдаются JSON-строкой того же вида, что собирает поповер
  (`{"length_mm":2700}`, безразмерные — `null`), чтобы выбранное значение
  сужало выборку, а не давало пустую таблицу;
- вход трансформирующего этапа не потерян: раскрой «вход → распилы» несёт
  колонка «Операция» (`CutLayoutCell`, ADR-0058), а количество входа —
  диалог завершения (`TaskActionDrawer`).

Для резки `WorkTask.dimensions` — длина входа (ADR-0002), поэтому оператор
по-прежнему видит, из какого размера получается итоговый, и это значение
теперь ровно то, которое фильтрует доска.

## Рассмотренные варианты

- **Фильтр переезжает на выражение показа** (`CASE WHEN
  stage.transforms_dimensions THEN input_dimensions ELSE dimensions END`).
  Отклонено: доска начала бы фильтровать другой JSONB, чем план, передачи и
  склад для того же материала; на лениво созданной принимающей задаче показ
  давал бы вход позиции вместо приехавшего размера; сортировка потребовала бы
  отдельного выражения.
- **Две колонки** («Размер» = габарит задания, «Вход» = вход этапа).
  Отклонено: дублирует «Операцию», которая уже рисует «вход → распилы».
- **Оставить как есть** (показ по входу, фильтр по габариту). Отклонено:
  описанные выше случаи дают пустую таблицу без объяснения — ровно то, ради
  чего «Размер» держали вне справочника значений.

## Последствия

**Хорошо**

- показ, фильтр, сортировка, список значений и группировка читают одно поле:
  выбранное в поповере значение всегда сужает выборку;
- «Размер» перестал быть исключением в справочнике значений — у доски больше
  нет серверной колонки без справочника;
- поповер «Размера» больше не схлопывается к текущей странице (дефект
  ADR-0044: список собран из загруженных строк).

**Плохо**

- на многоосном входе (2D/3D) колонка показывает только длину («2,7 м»);
  ширина/толщина видны в «Операции» и диалоге завершения. 1D-данные не
  затронуты — там значения совпадают;
- «Выдача» плана участка (строка на группу) тоже читает габарит задания, а не
  вход: на 1D неотличимо, на многоосном входе печатает длину.

**Нейтрально**

- `input_dimensions` в `SectionBoardTask` остаётся — его читает диалог
  завершения; `transforms_dimensions` остаётся гейтом «Операции».

## Связанное

- ADR-0001/0002 — габаритные группы и трансформация: вход/выходы позиции.
- ADR-0035 — подпись размера одна на всех экранах.
- ADR-0044 — поповер: текст фильтрует, значение выбирается одно; страничный
  список значений и его границы.
- ADR-0058 п.6 — колонка «Размер» у трансформирующей строки; этот ADR
  договаривает, что вход этапа в колонку не протекает.
