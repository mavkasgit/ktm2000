# ADR-0071: Авто-приёмка — не основание запрещать полную отмену выдачи

Дата: 2026-11-03. Статус: принято.
Тикет: #282 (Автоподбор источника выдачи), продуктовое решение в комментарии от 2026-11-03.
Связанные: ADR-0019 (журнал действий и preview-first отмена), GLOSSARY «Авто-приём (auto-accept)».

## Контекст

Выдача материала в работу (#282) — это **N передач**, по одной на склад-источник,
связанных одним `issue_no`. Пункт приёмки тикета сформулирован так:

> Если хоть одна передача этой выдачи уже принята — целиком не отменить,
> причина пишется текстом.

Передачи выдачи рождаются уже принятыми: `transfer_send` в нашей модели
принимает материал на участке-получателе автоматически (GLOSSARY
«Авто-приём»), и `_record_issue_transfer` выставляет `accepted` в момент
создания передачи. Буквально прочитанный по статусу пункт дал бы абсурд:
система сама создаёт условие, запрещающее отмену, и «Отменить выдачу
целиком» не работал бы почти никогда. Значит «принята» в этом пункте — не
про технический статус строки.

## Решение

**«Передача принята» в контексте запрета отмены = подтверждённое фактическое
исполнение / действие получателя, а не статус, выставленный системой.**

Различаются два разных факта, которые раньше читались одним словом:

- **принято системой** (авто-приёмка при создании передачи) — техническая
  проекция того, что материал физически уже на участке; сама по себе
  основанием для отказа не является;
- **принято получателем** — осознанное действие стороны-получателя или
  факт исполнения, изменяющий исходное состояние передачи.

Основания запретить полную отмену выдачи (`_acceptance_blocker` в
`backend/app/transfers/issue_service.py`, семантика сохранена, не менялась):

1. передача в статусе частичной приёмки, отказа или ручной правки
   записанного факта (`partially_accepted` / `rejected` / `amended`);
2. на этапе-адресате есть зафиксированные факты исполнения — завершённая
   или бракованная работа (`completed_quantity + rejected_quantity > 0`
   по проекции задания).

Отказывается вся выдача целиком, если блокировка есть хотя бы по одной
передаче; причина пишется текстом с именами этапов и количествами, без
цифровых id (#282, п.9).

Это **осознанная продуктовая интерпретация**, а не буквальная реализация
исходной формулировки требования: владелец продукта зафиксировал правило
комментарием в #282, а не изменил текст приёмки. Формулировку «если хоть
одна передача уже принята» без этого ADR нельзя читать как проверку
`status == accepted`.

## Последствия

- Оператор может пересобрать подбор: отменить выдачу целиком и запустить
  позицию заново — до тех пор, пока получатель ничего не сделал с
  материалом. Это ровно тот путь, который описан в тикете («Пересобрать
  подбор можно так: отменить выдачу целиком и запустить заново»); при
  буквальном статусе он был бы закрыт сразу после создания выдачи.
- Частичная приёмка и отработка по-прежнему закрывают полную отмену —
  остаётся правка записанного факта (известная дыра, отдельный тикет по
  тексту тикета #282).
- Покрытие обязано быть **двусторонним**
  (`backend/tests/transfers/test_issue_cancel_acceptance.py`): выдача с
  авто-приёмкой и без фактического действия → отмена разрешена; хотя бы
  одна передача с частичной приёмкой или фактом исполнения → отмена
  запрещена с русским `reason`. Первый тест краснеет, если свести
  `_acceptance_blocker` к проверке статуса: он и есть страховка от
  буквальной реализации.
- Термин в GLOSSARY («Авто-приём») дополнен парой «принято системой» /
  «принято получателем», чтобы следующая смена не восстанавливала запрет
  по статусу.
