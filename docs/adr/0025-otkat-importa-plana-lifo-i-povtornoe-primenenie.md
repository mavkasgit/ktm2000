# ADR-0025: Откат импорта плана — LIFO по `applied_at`, повторное применение переиспользует позицию

Дата: 2026-09-12
Статус: принято (гриллинг #172)
Контекст: тикет #172; сверка с кодом (`production_plan_service.py`,
`plan_import_service.py`, `api/routes/production_plans.py`,
`features/planning/*`), эмпирическая проверка повторного apply после отката
Связанные: ADR-0016 (тестовые БД), ADR-0024 (импорт плана), спека
[`docs/plan-import-spec.md`](../plan-import-spec.md) §4.3–4.5

## Контекст

Список файлов плана (`/planning`) показывал батчи импорта, но менять их
состояние из списка было нельзя: единственный вызов `applyChangeSet` жил в
визарде, отката в UI не было вовсе. Распознанные батчи копились мёртвым грузом.

Две вещи вскрылись при реализации:

1. **`rollback_change_set` не возвращал строки сета в применимое состояние**:
   после отката все `plan_change_items` оставались в статусе `applied`, а
   `apply_change_set` пропускает такие строки первым же условием — повторное
   применение молча ничего не делало.
2. **Уникальные индексы `plan_positions` не различают отменённые строки**:
   `ix_plan_positions_import_row (import_batch_id, source_row_number)` и
   `ix_plan_positions_import_hash (import_batch_id, source_row_hash)` —
   обычные (не partial) unique. Откат оставляет созданные позиции в БД
   (статус `cancelled`), поэтому повторный apply падал с
   `UniqueViolationError` — воспроизведено тестом до правки.

## Решения

1. **«Последний применённый» — по новой колонке `plan_change_sets.applied_at`.**
   Не по `created_at` батча (порядок загрузки ≠ порядок применения) и не по
   `audit_logs` (журнал — не источник истины для состояния). `apply` пишет
   `now()`, `rollback` очищает в `NULL`. Список файлов отдаёт `applied_at`
   вместе с `change_set_id` и `production_plan_id` (список `/all-files`
   межплановый, поэтому план нужен и на клиенте).
2. **LIFO — правило UI, новых гейтов на бэкенде нет.** «Откатить» доступно
   только у последнего применённого батча плана, у остальных кнопка disabled с
   тултипом. Бэкенд переиспользует существующие `apply`/`rollback` и их 400
   (`Cannot rollback: position already released` — released-позиция
   по-прежнему блокирует откат). Плата: клиент, игнорирующий правило, может
   откатить не последний сет; для внутренней MES этого достаточно, третий
   эндпоинт-гейт не заводим.
3. **Откат возвращает строки в применимое состояние тем же правилом, что
   парсинг** — `plan_import_row_status(errors, warnings)` плюс апгрейд
   `mark_possible_duplicate → warning` при `pending`. Иначе повторный apply
   упирается в `applied → continue`, а правило дублей разъехалось бы с
   серверным счётчиком.
4. **Повторный apply переиспользует свою отменённую позицию, а не вставляет
   вторую.** Кандидат — `plan_change_item.plan_position_id` со статусом
   `cancelled`, принадлежащий тому же батчу. При переиспользовании позиция
   заполняется полями из `after_data`, как при создании, и очищаются следы
   скрытия (`deleted_at/by/reason`) и прежнего утверждения
   (`approved_by/at`, `released_at`) — строка возвращается в план черновиком.
   Партиальный unique-индекс (`WHERE status <> 'cancelled'`) отклонён: ревизия
   этих индексов отложена спекой §6 («отдельный вопрос при регресе записи»),
   а переиспользование сохраняет идентичность строки сета между циклами
   откат→применение и не плодит отменённые дубли.

## Последствия

- Цикл «применить → откатить → применить» идемпотентен по составу позиций:
  тот же `plan_position_id` возвращается в план, новых отменённых строк не
  появляется.
- Повторное применение снимает прежнее утверждение позиции (черновик должен
  быть утверждён заново) — осознанно: сет применяется как новый ввод в план.
- Цифры диалога применения считаются на клиенте по лёгким строкам батча
  (`buildImportRowStats` — зеркало серверного `_item_aggregates`). Для этого
  лёгкие строки API импорта отдают `errors` и `warnings` раздельно: `codes`
  склеивает ошибки с предупреждениями, и «С ошибками» по нему не отделить.
- Откат сета, у которого среди созданных позиций есть released, по-прежнему
  возвращает 400 и ничего не меняет (проверка до мутаций).
- Батчи, применённые до миграции 057, имеют `applied_at = NULL` — откат для них
  недоступен (кнопка disabled), пока батч не применят заново. Бэкфилл из
  `audit_logs` отклонён: порядок применения восстановить нельзя гарантированно,
  а неверный порядок сделал бы LIFO-откат опасным (откат не последнего сета).
  Все-NULL — отказ безопасный: правило «только последний применённый»
  недостижимо, вместо него — ничего.
