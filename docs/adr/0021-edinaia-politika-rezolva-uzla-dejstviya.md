# Единая политика резолва узла действия (reversal)

## Контекст

Контракт компенсатора (`app/reversal/base.py`, ADR-0019 п.3/4) принимает пару
`(ref_id, action_id)`, но политика выбора узла `Action` жила в реализациях и
разилась: `StockCompensator._get_action` молча брал первый попавшийся узел
(`order_by(id).limit(1)`), игнорируя переданный `action_id` (`del action_id`),
а `StockActionCompensator` в той же ситуации требовал ровно одно активное
действие — иначе честный неуспех. Поведение seam'а зависело от реализации за
ним: при двух активных действиях с одним `(action_type, ref_id)` передача
молча откатилась бы «первую», доменное действие — отказалось бы. Дополнительно
`check_amend` не принимала `action_id` вовсе и ходила в `check()` только по
`ref_id`. Констрейнта уникальности активных пар в БД нет и не планируется
(см. отвергнутые альтернативы).

## Решение

Одна политика для всех компенсаторов — чистая функция в общем модуле
(`reversal/resolver.py`), дискриминированный результат без исключений.

1. **`action_id` — старший источник во всех компенсаторах**: передан —
   работаем строго с этим узлом (с проверкой типа действия); `del action_id`
   удаляется; `check_amend` получает параметр `action_id` и пробрасывает его
   в `check()`.
2. **Фолбэк по паре `(action_type, ref_id)` — строгая трихотомия**:
   0 активных → `NotFound`; ровно 1 → `Resolved(action)`; больше 1 →
   `Ambiguous(candidates)`. Угадывание («первый попавшийся», «самый свежий»)
   запрещено.
3. **Неоднозначность — типизированный блокер предпросмотра**
   `kind="ambiguous"` (detail перечисляет id-кандидатов) — развитие
   ADR-0019 п.8. Фронт рендерит блокеры универсально по `detail` и запрещает
   confirm при любом непустом списке блокеров, поэтому правок фронта не
   требуется.
4. На границе `plan()` неуспех резолва конвертируется в обычный `ValueError`
   (внешний контракт плана не меняется); preview-first гарантирует, что до
   `plan()` неоднозначность уже показана пользователю как блокер.

Инвариант «у типа с уникальным ref_id — ровно одно активное действие» держат
резолвер и тесты, а не схема БД.

## Отвергнутые альтернативы

- **«Берём самое свежее» (`order_by(id) desc limit 1`)** — тот же антипаттерн
  угадывания, лишь развёрнутый в другую сторону.
- **Частичный unique-индекс БД на `(action_type, ref_id) WHERE ACTIVE`** —
  часть типов может легитимно иметь несколько активных действий на один
  ref_id; blanket-индекс требует отдельного аудита каждого action_type.
  По построению сегодняшних сценариев дублей не возникает (amend/replay
  создают новый Transfer → новый ref_id, старые записи уходят в
  `AMENDED`/`REVERSED`), поэтому защита на уровне политики достаточна.
- **Слияние классов компенсаторов или поднятие резолва в ReversalService** —
  у transfer остаётся доменная специфика (cancel/amend/replay payload);
  контракт `check/plan(ref_id…)` сохраняется, срез ограничен политикой
  резолва.

## Последствия

Гипотетические дубли активных пар перестают молча откатывать «первый» — такие
узлы становятся нереферсибельными до ручного разбора, что и есть требуемое
поведение preview-first. Для типов с `ref_id=NULL` (manual_adjustment,
import_remainders) фолбэк по паре невозможен по построению — без `action_id`
честный «не найдено».
