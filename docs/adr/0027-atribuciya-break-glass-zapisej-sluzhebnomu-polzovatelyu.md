# ADR-0027: Атрибуция break-glass-записей служебному пользователю

Дата: 2026-09-24
Статус: принято (гриллинг; прод-инцидент — 500 на импорте остатков)
Контекст: `backend/app/api/deps.py`, `backend/app/stock/{api,import_service}.py`,
`backend/app/services/{audit_log_service,profile_service}.py`,
`backend/tests/test_auth.py`
Связанные: ADR-0005 §3 (break-glass не пишет в `users`), ADR-0006 §2
(break glass не несёт `sid`), ADR-0023 (одна служебная сущность вместо двух);
`CONTEXT.md` — «Служебный пользователь», «Break glass», «Автор проводки»

## Контекст

В проде вход шёл через break-glass: OIDC-провайдер (Authentik) недоступен,
`DEV_BYPASS_AUTH=false`, значит break-glass — единственный работающий путь
доступа. Первый же write-эндпоинт (`POST /api/stock/import/remainders`)
упал с 500:

```
api.py:1143 import_remainders_excel → import_service.py:966 apply_remainders_import
→ services.py:639 record → ForeignKeyViolationError:
Key (created_by)=(0) is not present in table "users"
```

Причина: `_BreakGlassUser` (`deps.py:18-33`) — эмулированная идентичность
с `id = 0` и без строки в `users`. В импорте остатков стоит
`created_by=user.id if user else 1` (`import_service.py:913`, `:958`), но
break-glass-объект truthy, поэтому «fallback» не срабатывает и в FK уходит 0.
Проверка «нет пользователя» задумана только в `audit_log_service.py:66`
(`u_id = user.id if user is not None and user.id else user_id`), и даже она
обходится: `routes/audit_logs.py:265` пишет `user_id=current_user.id` напрямую.

Отказ не локальный:

- `users.id` — цель **24 FK-колонок** (`stock_transactions`, `defects`,
  `transfers`, `plan_positions.changed_by`, `audit_logs`, `release_batches`,
  `work_tasks`, `notification_states`, …); `0` — не «пусто», а невалидный
  ключ, поэтому падают и nullable-колонки;
- под break-glass недоступны ~40 write-точек в 12 модулях (shopfloor,
  планирование, передачи, брак/СПГ, уведомления, сессии);
- break-glass покрыт тестами только на auth-поверхности (форма токена,
  `/auth/me`, logout, гибрид с `sid`) — ни один тест не дёргает write,
  поэтому CI и dev-сетап зелёные: в dev работает другая ветка гейта
  (`_get_current_user_dev`), которая отдаёт настоящую строку `users`.

Служебная строка существует в любой мигрированной БД: `system` (id=1)
создаётся миграцией `001_sections_and_users.py` (`OVERRIDING SYSTEM VALUE`)
и пересоздаётся сидером при расхождении id.

## Решение

1. **Break-glass сохраняет право записи** (роль admin, полный доступ).
   Аварийный доступ нужен именно тогда, когда SSO недоступен, а завод
   продолжает работать: read-only MES на время аварии IdP означал бы, что
   смена не может зафиксировать ни одной операции.
2. **Автор записей под break-glass — служебный пользователь** (`system`).
   Резолв — по семантическому ключу `username == "system"`; строка не
   найдена → явная ошибка (нарушение инварианта деплоя), не тихий откат
   к `id=0`.
3. **Один шов — граница идентичности** (`deps.py`): break-glass-ветка
   `_get_current_user_strict` отдаёт `_BreakGlassUser` с валидным `id`
   служебной строки. Прочие атрибуты эмулированного principal сохраняются:
   `is_break_glass=True`, `username="emergency_admin"`,
   `full_name="Emergency Access Admin"`. Ни одна из ~40 точек записи
   не правится.
4. **Машинная отличимость — по имени автора**: `*_user_name` =
   «Emergency Access Admin» (ledger уже так пишет). Отдельной
   колонки-маркера «сделано под break-glass» нет.
5. **Персональный скоуп — исключение**: под break-glass колокольчик
   показывает только общие уведомления; личные уведомления служебного
   пользователя аварийному админу не показываются. Все прочие чтения
   трактуют break-glass как служебного пользователя.
6. **Контракт `GET /auth/me` не меняется**: под break-glass по-прежнему
   `id = 0` («своей записи нет»). Атрибуционный id — внутренний: он отвечает
   на вопрос «кому подписать запись», а не «какая у меня строка», и наружу
   не выставляется. Фронт это поле не читает.
7. **Проверка**: регрессионные тесты по группам — ledger-запись,
   не-ledger запись, скоуп уведомлений — все с токеном break-glass при
   `DEV_BYPASS_AUTH=false`. Шов для теста уже существует
   (`test_auth.py:389-455`).

Инвариант «у любой записи есть актор» сохраняется: FK остаётся обязательным,
nullable-колонок не появляется.

## Отвергнутые альтернативы

- **Read-only break-glass** (403 на все write) — MES на время аварии IdP
  становится непригодным: ни передач, ни завершений, ни импорта. Цена
  атрибуции ниже цены простоя.
- **Guard `user.id or 1` в каждой точке записи** — ~40 правок в 12 модулях
  и постоянный риск «забыли одну»; ровно так этот баг и появился в двух
  точках из трёх.
- **Guard только в `StockCommandService.record`** — чинит ledger, оставляя
  падать передачи, план, брак, журнал и уведомления.
- **NULL-атрибуция** (сделать 24 FK-колонки nullable и «не знать» автора) —
  широкая миграция ради отказа от инварианта «у проводки есть актор»;
  `0` при этом всё равно не NULL, поэтому один nullable сам по себе
  проблему не решает.
- **Возврат настоящей ORM-строки `User` из гейта** (как в dev-ветке) —
  `is_break_glass` в бэкенде несущий: `/auth/me` берёт его через
  `getattr(...)` (`auth.py:216`) и на нём держится бейдж фронта, а
  `profile_service.update_*` блокирует запись профиля именно по нему
  (`profile_service.py:93,170`); без флага break-glass молча получил бы
  право правки профиля. Плюс `_load_user_by_subject(db, "emergency_admin")`
  строки не найдёт.
- **Отдельная служебная строка `break_glass`** — вторая служебная сущность
  там, где одна уже есть; против духа ADR-0023.
- **Магическая подмена `0 → SYSTEM_ID` на flush/в репозитории** — скрытый
  слой, который делает невалидное значение валидным незаметно для читателя
  кода.
- **Колонка-маркер «под break-glass»** — миграция по нескольким таблицам
  ради того, что уже читается из `*_user_name`.
- **Тихий откат к `id=0`, если служебной строки нет** — возвращает тот же
  500, но прячет причину (сломанный деплой вместо явной ошибки).

## Последствия

- Все ~40 write-точек чинятся одним изменением; уйти в FK невалидному
  `created_by` больше неоткуда.
- Сравнения `current_user.id` под break-glass теперь указывают на служебную
  строку: self-checks `users.py:212,219` («нельзя деактивировать себя /
  менять свою роль») начинают защищать служебного пользователя от break-glass
  — принято как полезное; персональный скоуп уведомлений — исключение (п.5).
- В модулях без `*_user_name` (`defects.created_by`,
  `plan_positions.changed_by`, `transfers.sent_by`, `audit_logs.user_id`)
  break-glass-запись неотличима от автоматической — принятый риск, названный
  осознанно.
- ADR-0005 §3 и ADR-0006 §2 уточнены: «`users` не используется для
  **аутентификации**» вместо «не читается вовсе». Чтение служебной строки —
  не session lookup, инвариант ADR-0006 («`sid` — только session semantics»)
  не затрагивается.
- Правки локализованы в host-слое (`api/deps.py`, при необходимости —
  `api/routes/notifications.py`); must-match модули
  (`session_core.py`, `authentik_client.py`, auth-фронт) синка с HRMS
  не требуют.
