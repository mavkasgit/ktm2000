# ADR-0073: Группа эквивалентов — общий пул сырья для остатков и выдачи

Дата: 2026-11-03. Статус: принято.
Спека: [`docs/equivalents-pool-spec.md`](../equivalents-pool-spec.md).
Тикеты: [#393](https://github.com/mavkasgit/ktm2000/issues/393) (эпик),
[#394](https://github.com/mavkasgit/ktm2000/issues/394)–[#398](https://github.com/mavkasgit/ktm2000/issues/398).
Связанные: ADR-0001 (оси остатка), ADR-0023 (пара `product_pairs`),
ADR-0055 (пройденные операции в ключе остатка), ADR-0068 (составной
артикул).

## Контекст

`Product.aliases` объявляет артикулы взаимозаменяемыми, но в учёте это
никак не участвует: индикатор наличия суммирует один `product_id`,
автоподбор источника выдачи фильтрует `StockBalance.product_id ==
product_id`, ручной выбор отвергает материал «другого артикула», а
завершение задания списывает вход по `task.product_id`. Склад, где
физически лежит одна куча (A и B — один и тот же профиль), показывает две
кучи; позиция на A не видит остаток B; две позиции на A и B конкурируют за
один материал, каждая видя только свою половину.

Нужно: для любого артикула группы использовать остатки любого её члена,
если совпадают размер, пройденные операции, качество и склад; склад в
операторском слое — одна группа; при выдаче материал списывается с
фактического SKU, а на участок приходит артикулом задания.

## Решение

1. **Группа — транзитивное замыкание `Product.aliases`** по существующим
   продуктам, включая неактивные; alias-SKU без строки продукта
   игнорируется. Группа строится на чтение, не хранится; канонического
   артикула нет. Модуль-владелец — `app/services/product_alias_groups.py`.
2. **Пул — GOOD-остатки группы** на складах-хранилищах (`raw`/`wip`/
   `finished`). Подходит ровно то же, что и раньше: строгий размер,
   признак операций, принимаемый маршрутом позиции, GOOD. Атрибуты продукта
   не сравниваются: эквивалентность — объявленная взаимозаменяемость.
3. **Наличие — по группе.** Свободно = сумма по группе; спрос = сумма
   открытых позиций на всех членах; доступно = свободно − (спрос − свой
   спрос); дефицит — против потребности позиции. Для пары с компонентами в
   одной группе потребность `2Q`, в разных — по `Q` и связывает минимум.
4. **Выдача — из пула.** Порядок: артикул задания → остальные эквиваленты →
   прежний системный порядок. Ручной выбор остатка принимает любой остаток
   группы; чужой артикул отклоняется. Замок — все строки баланса группы в
   детерминированном порядке.
5. **Канонизация на границе выдачи.** `TRANSFER_SEND` несёт фактический SKU
   источника, `TRANSFER_RECEIVE` — артикул задания; `Transfer.product_id` —
   артикул задания, комментарий называет источник. Дальше маршрут,
   завершение, брак, передачи и выпуск не меняются; отмена зеркалит обе
   проводки. В ledger фактический SKU сохраняется — аудит и S1 честные.
6. **Операторский слой показывает группу одной кучей**: остатки, индикатор,
   окно выдачи — строка группы с раскрытием до SKU; журнал передачи —
   артикул задания + источник в комментарии; журнал движений — фактический
   SKU (аудит). В БД остатки остаются по каждому SKU: **миграции нет**.
7. **Пары не меняются.** `product_pairs` — другое понятие; пары из
   эквивалентов не существует, разделение пары на задачи по компонентам —
   вне рамок.

## Рассмотренные варианты

- **Канонический артикул: остаток группы физически лежит под одним SKU.**
  Отклонено: нужно выбрать каноника, слить существующие балансы миграцией
  и перекладывать остатки при каждой правке `aliases`; правка справочника
  начинает двигать историю, откат дорогой.
- **Группа как ключ `StockBalance`/ledger.** Отклонено: переписывание ядра
  учёта (ADR-0001), импорта, отчётов и передач — отдельный большой проект,
  а операторский эффект тот же.
- **Сохранять фактический SKU на участке и учить завершение/брак/передачи
  пулу.** Отклонено: правка всех точек списания и их инвариантов; на первом
  же завершении SKU всё равно станет артикулом задания, то есть та же
  канонизация, только позже и дороже.
- **Показывать склад по SKU, а пул — только в подсказке.** Отклонено:
  «на складе одна куча, артикул появляется у задания» — это и есть
  требование; две строки на экране остатков ему противоречат.
- **Разделить пару на две задачи по компонентам.** Отклонено: новая
  структура плана/маршрута/доски; к эквивалентности отношения не имеет.

## Последствия

- Миграций нет; правка `aliases` меняет пул для будущих операций, но не
  переписывает уже выданное.
- Два взгляда на один факт намеренны: оператор видит группу, аудит — SKU.
  Журнал движений и `by-product/{id}` остаются SKU-уровнем.
- Спрос группы означает, что позиции на разных членах видят друг друга:
  две позиции не могут обе пообещать одну и ту же кучу.
- Групповой замок расширяет набор блокируемых строк: параллельные выдачи
  на разные SKU одной группы сериализуются.
- Экран остатков обязан группировать, сортировать и пагинировать по
  группам на сервере: клиентская группировка страницы даст ложную «одну
  кучу» на границе страниц.
- `issue-preview` получает `group_key`/`product_id`/`sku` в кандидатах;
  клиент только агрегирует, порядок и количества остаются серверными
  (#282).
- Текст отказа «материал — другого артикула» заменяется на «не из группы
  эквивалентов»; это видимое изменение контракта ошибок.
