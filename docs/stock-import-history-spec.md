# Спека: история импорта остатков (#232)

Тикет: [#232](https://github.com/mavkasgit/ktm2000/issues/232)
Решения: [ADR-0052](../docs/adr/0052-istoriya-importa-ostatkov.md),
[ADR-0053](../docs/adr/0053-otkat-importa-ostatkov-lifo-po-skladu.md)
Термины: [`GLOSSARY.md`](../GLOSSARY.md) — «Импорт остатков», «Батч импорта»,
«Строка импорта», «Файл импорта».

## Проблема

Импорт остатков (`app/stock/import_service.py:apply_remainders_import`) не
оставлял реестра: единственный след батча — строка `action_journal` и общий
`source_ref` на проводках. Имя файла, лист, per-row вердикты и ошибки не
сохранялись, `action_id` не отдавался в ответе. Откат при этом уже работал
через `reversal_service` — отсутствовал именно реестр, из-за которого
«откатить вот тот файл» превращалось в поиск по журналу действий.

## Схема

| Таблица | Роль |
|---|---|
| `stock_import_batches` | Заголовок батча: узел журнала, файл, склад, статус, счётчики, мягкое удаление |
| `stock_import_rows` | Строка импорта: вердикт, ошибки, сырые значения файла, связь с проводкой |
| `import_files` | Переиспользуется как есть (content-addressed по sha256) |
| `action_journal` | Источник истины по откату (ADR-0019 §7) |

`import_batches` плана **не переиспользуется**: там `production_plan_id`,
`mode`, `sheet_name`, `header_row_number` — `NOT NULL` и все про план.

## API

| Метод | Путь | Право |
|---|---|---|
| `GET` | `/api/stock/import/remainders/batches` | `READER_ROLES` |
| `GET` | `/api/stock/import/remainders/batches/{id}` | `READER_ROLES` |
| `GET` | `/api/stock/import/remainders/batches/{id}/file` | `READER_ROLES` |
| `POST` | `/api/stock/import/remainders/batches/{id}/rollback` | `admin` |
| `POST` | `/api/stock/import/remainders/batches/{id}/hide` | `admin` |

Читать историю может любая читающая роль — это факт учёта, а не изменение.
Откатывать и скрывать — только администратор; гейт стоит в двух местах, и
это не дублирование:

* **роль** — `ADMIN_ONLY_REVERSE_TYPES` в `app/reversal/api.py`: общий маршрут
  `/actions/{id}/reverse` иначе обошёл бы гейт за два клика из журнала;
* **состояние батча** (LIFO по складу, скрыт, уже откатан) —
  `import_batch_rollback_blockers` в компенсаторе: сервис отката зовут не
  только хендлеры, и это правило предметной области, а не права доступа.

## Смыслы действий

Три глагола различаются по смыслу, а не по формулировке кнопки:

* **посмотреть** — прочитать строки батча и текущий остаток по каждой;
* **откатить** — зеркально скомпенсировать **обе** фазы батча (гашение
  `clear_existing` и заливку `MANUAL_IN`), вернув остаток к состоянию до
  импорта. Покрытие проверяется зеркально: израсходованный материал даёт
  `CoverageShortfall`, частичный откат запрещён;
* **удалить из списка** — `deleted_at`. Ledger не трогается, узел журнала по
  ADR-0019 §7 не удаляется никогда. Это «не хочу это видеть», а не «отменить».

Причину скрытия в UI не спрашивают: оператору нечего добавить к факту
«запись не нужна». `delete_reason` при этом пишется всегда — системной
строкой «Убрано из списка оператором», — потому что колонка отвечает на
вопрос «на каком основании запись спрятана», а кто спрятал, хранится рядом
в `deleted_by`. Поле `reason` в контракте остаётся необязательным.

Статус батча — **проекция статуса узла журнала**, а не самостоятельное поле:
откат возможен и из истории импортов, и из общего журнала, и два независимых
статуса рано или поздно покажут откатанный батч откатываемым.

## Правила

1. **Однофазность.** Импорт применяется сразу и пишет строку истории. Черновик
   для остатков — ложь в учёте; предпросмотр уже есть и показывает вердикты
   до заливки.
2. **LIFO по складу** (`location_id`), а не глобально: импорт на другой склад
   не делает батч неоткатываемым. Глобальный LIFO — практический тупик.
3. **Строка импорта обязана ссылаться на созданную ею проводку.** При
   `skip_invalid` часть строк пропускается молча; без связи нельзя ни
   объяснить пропуск, ни показать блокировку покрытия.
4. **Скрытие ортогонально статусу:** скрытый батч может быть и откатанным.
5. **Бэкфилл** миграцией для всех `Action(action_type='import_remainders')`:
   `file_id = NULL`, `legacy = true`, `location_id = NULL` — склад
   импорта до миграции не сохранялся, и приписывать им склад значило бы
   соврать. Порядок применения известен точно (монотонный `Action.id`).
6. **Rollback ≠ delete** — два эндпоинта, два подтверждения.

## UI

История импортов — **отдельная страница** `/spg/import-history`
(`features/spg/pages/ImportHistoryPage.tsx`). Вход — кнопка «История
импортов» на экране ГХП, сразу после «Импорт из Excel»; в боковое меню
пункт не добавлен, история остатков относится к ГХП. Разметка списка и
правила отката живут в `ImportHistoryPanel`; модалка импорта её не рендерит —
шаг «Импорт успешно завершён» показывает только итог текущей заливки и ошибки.

Это окончательно заменило первое решение (#232, Q21: секция внутри модалки) —
прошлый импорт нельзя было посмотреть, не пройдя новый до конца, а в модалке
история только занимала место.

Колонки: файл, склад, когда, строк, состояние, действия. У legacy-батчей
вместо имени файла — «файл не сохранился», кнопки «Скачать» нет. У всех
батчей склада, кроме последнего, «Откатить» disabled с тултипом (ADR-0053 п.4).

В модалке «Посмотреть» текущий остаток строки ищется по **полному** ключу
баланса — `(product, section, quality_state, dimensions, completed_operations)`
— одним запросом по всем ключам батча, а не по запросу на строку. Строка
импорта хранит свой `completed_operations` (`StockImportRow`, ADR-0055), и
группировка выборки в `get_batch_rows` включает пятую ось: без неё две строки
одного артикула и длины с разными операциями показали бы одну сумму.

## Инварианты и проверки

* после отката — `assert_no_invariants_violations`
* покрытие при израсходованном материале → блокер, а не частичный откат
* не-последний батч склада → `not_allowed` в preview, `plan_token` не выдаётся
* мягкое удаление → проводки и узел журнала на месте

Тесты: `backend/tests/stock/test_import_history.py`,
`frontend/e2e/stock-import-history.spec.ts` (@ui).

## Найдено при интеграции

`stock_import_rows.stock_transaction_id` создан обычным FK — и это ломало
сид: `DELETE FROM stock_transactions` падал на `ForeignKeyViolationError`
(всплыло на `e2e:prep`). Ссылка справочная, а ledger — источник истины, так
что при чистке проводок она обнуляется: `ON DELETE SET NULL` (миграция
`073`, прецедент `defects.route_stage_id`). Правкой применённой миграции
`072` dev- и e2e-БД бы не обновились, поэтому это отдельная ревизия.


## Побочно исправлено

`IMPORT_REMAINDERS_SOURCE_REF = "import_remainders_excel"` во фронте не
совпадал с фактическим `source_ref = "import_remainders:{action_id}"`, и
подпись «Импорт остатков» в журнале проводок не срабатывала никогда. Теперь
сравнение по префиксу `IMPORT_REMAINDERS_SOURCE_REF_PREFIX`.
