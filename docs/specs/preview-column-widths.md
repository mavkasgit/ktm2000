## 1. Проблема

Таблица предпросмотра импорта остатков (`features/spg`) виртуализирована и содержит
11 содержательных колонок плюс служебные (шеврон разворота, сброс фильтров).
При `table-layout: auto` браузер считает ширины по содержимому **смонтированных**
строк: при скролле виртуализатор меняет строки, колонки «перерисовываются».

Продуктовый фикс уже убрал дрожание: `table-fixed` + `<colgroup>`, фиксированные
доли, однострочные текстовые ячейки с полным значением в `title`, перенос —
только «Ошибкам». Но доли выбраны руками. Из-за этого:

- «Наименование» получает запас, который в типичном ОСВ не нужен;
- «Операции» с тремя пилюлями обрезаются;
- длинные «Ошибки» растягивают строку выше ритма `TABLE_ROW_COMPACT` (40 px),
  а оценка высоты строки у виртуализатора остаётся усреднённой.

Нужен воспроизводимый способ выбирать ширины: минимальная суммарная высота при
заданной ширине таблицы, с явным обменом «пара перенесённых строк против
повсеместной обрезки».

## 2. Цель

Подобрать вектор ширин `w` для заданной ширины таблицы `W`, который:

1. минимизирует суммарную высоту таблицы;
2. допускает небольшое число переносов, если это дешевле обрезки;
3. не меняется при скролле, поиске, сортировке и смене фильтров;
4. даёт предсказуемую высоту каждой строки — её можно отдать виртуализации
   вместо усреднённой оценки;
5. считается за десятки миллисекунд на лист до 5000 строк.

## 3. Не цели

- Серверное измерение текста и новые API.
- Пересчёт ширин на скролл/поиск/сортировку.
- Мультиспаны, вложенные таблицы, печатные листы (отдельные задачи, если понадобятся).
- Замена `table-fixed` обратно на auto-layout.

## 4. Формулировка

Для колонки `i`, строки `r` и доступной ширины `u_i = w_i − padding_i`:

```
lines(i, r, w_i) =
  wrap:     min(clamp_i, жадный перенос(text, u_i))
  truncate: 1,  ячейка обрезана, если naturalWidth > u_i
  pills:    1,  ячейка обрезана, если ширина пилюль > u_i
```

Высота строки и таблицы:

```
height(r) = max(MIN_ROW_HEIGHT, max_i lines(i, r, w_i) * LINE_HEIGHT + ROW_PADDING)
cost      = Σ_r height(r) + λ * (число обрезанных ячеек)
```

Ограничения:

```
Σ_i w_i ≤ W,   min_i ≤ w_i ≤ max_i
```

- `λ` — цена скрытого текста в пикселях высоты (стартовое значение 20 px).
  При `λ → 0` оптимизатор всё обрежет, при `λ → ∞` — всё перенесёт.
- `clamp_i` — потолок строк (`line-clamp`): «Ошибки» 3, «Наименование» 2.
- `min_i` — шапка + контрол (Select качества, участок) + разумный минимум.
- `max_i` — доля ширины таблицы (`maxShare`); защита от колонки-монополиста.

Задача с текстом NP-трудная (Anderson & Sobti, 1999), поэтому в продакте —
эвристика, а точный перебор — только оракул на малых инстансах.

## 5. Вход и выход

**Вход:**

- все строки листа (до 5000, лист уже приходит целиком);
- описание колонок: тип (`text` / `mono` / `numeric` / `control` / `pills`),
  `minPx`, `maxShare`, политика переполнения (`wrap`/`clamp`/`truncate`);
- шрифт и `line-height` (синхронизированы с CSS);
- `W` — ширина контейнера за вычетом служебных колонок.

**Выход:**

- ширины (в пикселях под текущий `W`; для хранения — доли от `W`);
- предсказанная высота каждой строки;
- статистика: p50/p90/p99/max натуральной ширины, доля переносов и обрезки.

## 6. Колонки (текущая продуктовая раскладка)

| Колонка | Тип | Политика | min, px | Доля сейчас |
|---|---|---|---:|---:|
| `#` | numeric | одна строка | 32 | 3% |
| `Код 1С` | mono | обрезка | 60 | 5.5% |
| `Артикул` | mono | обрезка | 70 | 7% |
| `Наименование` | text | wrap, clamp 2 | 90 | 15% |
| `Кол-во, шт` | numeric | одна строка | 55 | 5.5% |
| `Метры` | numeric | одна строка | 55 | 5.5% |
| `Длина` | numeric | одна строка | 45 | 5% |
| `Операции` | pills | nowrap, обрезка | 90 | 21% |
| `Качество` | control | const | 90 | 7% |
| `Участок` | control | const | 100 | 9.5% |
| `Ошибки` | text | wrap, clamp 3 | 90 | 11% |

Служебные колонки — 68 px (28 шеврон + 40 сброс), из бюджета `W` вычитаются.

Контролы и числовые колонки в оптимизации **не участвуют**: их высота входит
в `max` по строке константой. Гибкие колонки сейчас: `Наименование`,
`Операции`, `Ошибки`; в исследовании допускаются дополнительные generic-колонки.

## 7. Алгоритмы-кандидаты

| Алгоритм | Идея | Зачем в сравнении |
|---|---|---|
| `baseline` | текущие доли | точка отсчёта |
| `auto` | min/max-content, эмуляция браузерного auto | что даёт «родная» раскладка |
| `p90` | пропорционально p90 натуральной ширины | простая быстрая эвристика |
| `narrowing` | от широкой раскладки сужаем колонку с минимальным приростом высоты (Marriott et al., TWEB 2013) | академический ориентир |
| `breakpoints` | рост от минимумов по порогам, где падает число строк | объяснимо и не зависит от шага сетки |
| `oracle` | полный перебор порогов | эталон на малых инстансах |

Важно: жадность **от минимумов** с фиксированным шагом может застревать —
число строк падает ступенями, и 10 px не дают эффекта, пока порог не достигнут.
Поэтому либо narrowing от широкой раскладки, либо движение по breakpoints.

## 8. Измерение текста

- **`@chenglou/pretext`** — основной кандидат: `prepare()` один раз на текст,
  `layout()`/`measureLineStats()` на каждую ширину; в браузере использует
  canvas-движок как эталон.
- В Node pretext работает через подменённый `OffscreenCanvas`; в бенче это
  табличные метрики 11px + жадный перенос (реализовано в
  `research/column-widths/lib/measurers.mjs`).
- Baseline `ceil(naturalWidth / usable)` оставляет как грубую модель: она
  занижает число строк на длинных словах и артикулах без пробелов.
- Обязательные условия: `font`, `line-height`, `letter-spacing` и
  `overflow-wrap` совпадают с CSS; шрифт именованный (не `system-ui`);
  веб-шрифт загружен до `prepare()`.

## 9. Метрики

1. Суммарная высота и `cost` относительно `baseline` и оракула.
2. Средняя/`p95`/максимальная высота строки.
3. Доля строк с ≥2 и ≥3 строками текста.
4. Доля обрезанных ячеек.
5. Время расчёта на 5000 строк (цель — десятки мс).
6. Устойчивость: ширины на подвыборке 500 строк против полного листа.
7. Устойчивость к `W` в диапазоне 1180–1920 px (доли колонок).
8. Расхождение предсказанных и реальных строк в браузере.

## 10. Гипотезы

- **H1.** Лучшая эвристика отстаёт от оракула не более чем на 5% по `cost`.
- **H2.** Подвыборка 500 строк даёт ≤2% потерь относительно полного листа.
- **H3.** Раскладка устойчива к `W` 1180–1920 px (доли не гуляют больше 5 п.п.).
- **H4.** `pretext` расходится с реальным DOM менее чем на 1% строк.

## 11. Матрица экспериментов

- **Профили:** `realistic`, `long-tail`, `outlier`, `all-short`, `mono`,
  `mixed`, `empty`.
- **Размеры:** 100 / 1000 / 5000 строк.
- **Колонки:** 6 / 12 / 20 (11 — продуктовый срез, проверяется отдельно).
- **Ширины:** 1180 / 1500 / 1920 px.
- **Seed'ы:** 1, 2 (детерминированный PRNG).
- **Оптимизаторы:** `baseline`, `auto`, `p90`, `narrowing`, `breakpoints`;
  `oracle` — на 40–60 строках.
- Оптимизатор подбирает ширины на подвыборке ≤500 строк, метрики считаются
  на полном листе.

### Прогон после #480 (378 конфигураций, 2 seed, `greedy`)

| Оптимизатор | Высота / baseline | cost / baseline | Обрезка, % | Время, мс | Побед |
|---|---:|---:|---:|---:|---:|
| baseline | 1.000 | 1.000 | 7.32 | 0.03 | 43* |
| auto | 0.960 | 0.968 | 7.29 | 2.14 | 104 |
| p90 | 0.971 | 0.959 | 6.89 | 2.00 | 31 |
| narrowing | 0.970 | 0.947 | 6.55 | 4.07 | 69 |
| breakpoints | 0.959 | 0.933 | 6.33 | 3.07 | 110 |
| **search** | 0.960 | **0.933** | **6.31** | 5.84 | 21 |

\* ничьи достаются первому в списке.

- **H1 подтверждена.** `search` (кэш порогов по колонке + обмен бюджета)
  отстаёт от оракула не более чем на 0.49% на oracle-прогонах и 1.33% на
  худшей из 126 конфигураций; следующие — `breakpoints` 5.52%, `narrowing`
  13.99%, `p90` 14.02%, `auto` 28.13%.
- **Время.** `search` на 5000 строк × 11 колонок — медиана 11.8 мс (max 22.2),
  цель 50 мс закрыта; 20 колонок — стресс до 60 мс.
- **H2 не подтверждена** в общем виде: у `search` расхождение высоты 0.14%
  (внутренняя подвыборка 500/5000 — Δcost 0.73%), у `narrowing` на `outlier`
  3.95% при пороге 2%.
- **H3 не подтверждена**: доли при W 1180–1920 расходятся до 10.07 п.п.
  (`breakpoints`/`search`, `long-tail`) — цена более сильного поиска; нужна
  политика стабильности, а не «на глаз». Разбор — #482.
- Первый прогон каркаса (до кэша кривых) давал обратное: H1 **нет**, худший
  gap 17.56%, `narrowing` 1264 мс. Он сохранён в истории, чтобы видно было,
  что усиление поиска — не подгонка отчёта.
- H4 проверен в реальном браузере (#479, `research/column-widths/browser/`):
  расхождение **0.19%** по числу строк и по высоте (9 из 4656 ячеек, порог
  <1% пройден). Все расхождения — ширина меньше `maxWordWidth` строки:
  `pretext` рвёт слово по графемам, а CSS `overflow-wrap: normal` оставляет
  его в одной переполненной строке. При `width >= maxWordWidth` расхождений
  **ноль** (4647 ячеек, включая дефисные артикулы).
  Следствие для оптимизатора: минимум текстовой колонки —
  `max(minPx, max(maxWordWidth))` по листу, а не только статический `minPx`.
  Стенд проверяет контракт «wrap + `line-height: 20px` + Inter 400»; текущий
  продуктовый CSS (`truncate` у наименования, `leading-snug`/`font-medium` у
  ошибок) этому контракту ещё не соответствует — это вопрос интеграции (#483).

Финальные числа, выбор констант (`λ`, `line-clamp`, размер подвыборки) и
отчёт — #481; разбор H2/H3 и политика стабильности — #482. Абсолютные пиксели
в Node остаются табличными, но модель провалидирована в браузере (H4), поэтому
сравнение раскладок между собой корректно.

## 12. Ось «перенести пару строк»

`λ` превращает выбор в продуктовый:

- `Ошибки` — wrap: причина отказа важна, полный текст виден без наведения;
- `Наименование` — clamp 2 + `title`: две строки максимум, дальше — обрезка;
- `Операции` — nowrap: пилюли сжимаются, подпись в `title`.

Оптимизатор сам решает, где выгоднее отдать 20 px: сэкономить строку в
«Ошибках» или показать ещё одно наименование. Открытый вопрос — допустимая
доля строк выше 40 px (кандидат: ≤5%).

## 13. Открытые вопросы

1. `line-clamp` для «Ошибок»: 2, 3 или без потолка? Влияет на целевую функцию.
2. `λ`: 20 px, другая константа или настройка по профилю?
3. Хранить доли в процентах или пикселях? Пиксели честнее для `table-fixed`,
   проценты устойчивее к ресайзу; пересчёт по `ResizeObserver` — компромисс.
4. Пересчёт при смене шрифта/зума: считать ли `W` в CSS px после зума.
5. Влияние порядка колонок и горизонтального скролла на «воспринимаемую» высоту.
6. Нужен ли `oracle` в продакте как fallback при малом числе строк (<100).

## 14. Интеграция (после исследования)

- Хук `useOptimalColumnWidths(sheetIndex, columns)`:
  - кэш по `sheet_index` из **первого нефильтрованного** ответа;
  - пересчёт только при изменении `W` (ResizeObserver, дебаунс) и шрифта;
  - никогда — на скролл/поиск/сортировку.
- Ширины в `<colgroup>`, таблица остаётся `table-fixed`.
- Предсказанная высота строки — в `VirtualizedTableBody` вместо усреднённой.
- Всё за флагом (env или query-параметр), с возможностью отката на текущие доли.
