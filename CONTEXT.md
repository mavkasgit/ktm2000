# CONTEXT — глоссарий домена KTM-2000

Единый словарь терминов. Используем эти слова в коде, тикетах, тестах и UI.
Решения с обоснованием — в `docs/adr/`.

## Конфигурация завода

- **Канон (PlantConfig)** — типизированный единый источник правды по заводским
  справочникам и политикам: участки, правила маршрутов, карта брака, лейблы,
  тексты ошибок. Правила доступа сервисов к канону — ADR-0004 §5 и ADR-0008.
- **Справочник (справочные данные)** — заводские данные, наполняющие канон:
  участки, типы брака, профили правил, шаблоны импорта, флаги обработки,
  измерения. Исходный код справочника — типизированные authoring-данные
  (PlantConfig), а не сырые dict-дефолты в седерах (ADR-0010).
- **Шаблон импорта** — пользовательский шаблон сопоставления колонок Excel
  с полями системы; строка в таблице `import_templates`, показывается в UI
  (страница планов, «Шаблоны импорта»). Сейчас шаблоны — только для
  **импорта плана** («Упаковочная карта РП»).
- **Маппинг остатков** — системный дефолт сопоставления колонок для
  **импорта остатков** (Артикул/Кол-во/Операции/Участок/Длина и т.д.).
  Не шаблон: живёт в JSON-файле `backend/app/stock/remainders_columns.json`,
  в таблицу шаблонов и в UI не попадает (ADR-0003 «Обновление»).

## Учёт и склад

- **Размеры (dimensions)** — универсальный JSONB-атрибут единицы учёта:
  `{"length_mm": 2700}`, `{"width_mm": 1200, "height_mm": 2400}`, `null`.
  `null` = «безразмерные штуки» (крепёж и т.п.). Один SKU может лежать на складе
  в нескольких размерах одновременно — это **один продукт, разные состояния**,
  не разные SKU. Пишем «размеры» (как колонка каталога), не «габариты».
  Не говорим «партия» — партий в модели нет (ADR-0001).
  Терминология: в **коде** — `dimensions` (поле/переменные/комментарии
  кода), в **UI и глоссарии** — «размеры». Код не переименовывается.
- **Остаток по размеру** — баланс группируется по
  `product + section + dimensions`. «200 шт × 2,7 м» и «50 шт × 3,0 м» — два
  разных остатка одного SKU на одной секции.
- **Справочник измерений (dimension_types)** — каталог допустимых ключей
  dimensions (`length_mm`, «Длина», «мм»). Новый тип размера = строка в
  справочнике, без миграции схемы.
- **Размерность артикула (dimension_state)** — ровно одна ось описания
  продукта: `length` («Длина, мм»), `area` («Длина × Ширина × Толщина»),
  `volume` («Длина × Ширина × Высота»). `length` — по умолчанию и
  единственная, участвующая в подвесе: кол-во на подвесе настраивается
  только для `length` (ADR-0012).
- **Уникальный код артикула (code)** — короткий машиночитаемый
  идентификатор продукта для импорта/интеграций, опционален, уникален.
  Не то же, что `sku` (человекочитаемый артикул, который пользователь
  может менять) (ADR-0012).
- **Привязка измерений (product_dimensions)** — какие измерения обязательны
  для продукта и их значение по умолчанию (**типовой размер**). Если при
  импорте остатков длина не указана — подставляется типовой размер.
- **Излишки (избыток)** — годный материал, физически оставшийся сверх
  плановой логики. Не расширяют план и не идут дальше по плану; движутся
  **собственным потоком**: выдача избытка → завершение избытка → передача
  избытка на следующий склад/ГХП. Хранятся как обычный остаток со своим
  dimensions, вне плана; на следующем ГХП остаются избытком. Избыток —
  **ручные исправления**, в плане и его колонках (в т.ч. «Осталось
  выдать») не показывается — только в остатках/модалке.
- **Нетто по причине (net by reason)** — фактически учтённое количество
  по причине движения с учётом компенсаций: сумма активных транзакций
  причины минус сумма компенсирующих
  (`case(compensates_tx_id IS NULL → quantity, else_ -quantity)`).
  Один примитив для передачи, приёмки и выпуска; «уже отдано» по
  `(задача, размер)` всегда берётся как нетто по соответствующей причине,
  а не по отдельной локальной формуле. Для причины без компенсаций
  net ≡ gross.
- **Активная транзакция** — запись ledger без `compensates_tx_id`; входит
  в net своим quantity со знаком «+». Компенсированная транзакция вычитается
  из net независимо от причины.
- **Компенсация (компенсирующая проводка)** — встречная StockTransaction,
  связанная через `compensates_tx_id` с исходной проводкой и обнуляющая
  её эффект при расчёте нетто и баланса. Компенсация — **общая способность
  ledger** (применима к любой причине), а не семантика только
  `TRANSFER_SEND/RECEIVE`; бизнес-операции могут ограничивать, какие причины
  компенсируемы (сегодня — только передачи через `cancel_transfer`).
- **Уже выпущено (released)** — нетто `FINAL_RELEASE` по `(задача, размер)`:
  единое определение для обычных и трансформирующих задач.
- **К выпуску (releasable)** — произведено по размеру минус уже выпущено
  по размеру; выпуск нельзя сделать больше releasable.
- **Право компенсации (policy)** — правило доменной операции, определяющее,
  какая операция может создавать компенсирующую проводку для конкретной
  причины движения. Способность ledger вычислять нетто для причины сама по
  себе не означает, что любая операция вправе её компенсировать.
- **Gross-чтение** — чтение количества по причине без вычитания
  компенсирующих проводок. Применяется для причин, для которых доменный
  контракт не предусматривает net-семантику; в текущем срезе COMPLETE и
  SCRAP остаются gross.

## Трансформация габаритов

- **Трансформация** — операция участка, меняющая dimensions при неизменном SKU:
  вход (N шт × габарит A) → выходы (M шт × габарит B, K шт × габарит C, …).
  Способность **этапа маршрута**, не конкретного участка: пила сегодня,
  гильотина/фрезеровка завтра (ADR-0002).
- **Вход задания** — что списывается: количество заготовок + их dimensions.
- **Выход задания** — что появляется: количество + новые dimensions.
  Выходов может быть несколько (2,7 м → 1,8 м + 0,9 м).
- **Годный остаток резки** — недоиспользованная длина заготовки — всегда
  полноценная единица учёта (режем 0,9 из 2,7 → 1,8 обязательно остаётся
  на учёте). Пропил (≈5 мм) игнорируется. Понятия «обрезок/отход» в модели нет.

## План

- **Позиция плана** — группа строк Excel с общим входом (объединённые
  ячейки «кол-во шт. в 2,7» / «Длина, м») = одна PlanPosition =
  одна операция. Несёт один вход (`input_quantity` × `input_length`)
  и список выходов `[(output_quantity, output_length)]` — по строке
  на выход. Одиночная строка — группа из одного выхода (ADR-0003).
- **План — источник правды по размерам**: задание берёт вход/выход из
  позиции плана; оператор не назначает размеры сам.
- **Строка плана (размер)**: количества в плане разделяются по
  каноническим размерам — полное совпадение = `артикул + размеры`.
  Разные размеры одного SKU не суммируются друг с другом (один продукт,
  разные состояния). Длина — частный случай размеров (`{"length_mm": 2700}`).
- **План — только полные совпадения**: на страницах плана показываются
  только строки `артикул + размер` (по одному на каждое полное совпадение);
  **общее количество по артикулу не показывается** — оно видно только
  внутри модалки артикула. Строка «Итого» внизу таблицы суммирует только
  плановые строки; избыток в строки и итоги плана не входит.
- **Выдача и сдача по размерам**: «Выдача» строится по **входу**
  (`артикул + входной размер`, кол-во = `input_quantity`/`planned_quantity`),
  «Сдача» — по **выходам** (строка на каждый `outputs[i]`, кол-во =
  `outputs[i].quantity`). Прогресс строки «Сдачи» — из `outputs_progress`.
  На **доске** (и в bulk-панели) задачи группируются по **входу** — резка
  остаётся одной карточкой; разбивка по выходам — только в «Сдаче» плана.
  Подпись группы на доске дополняется размером входа
  (`артикул · 2,7 м`); строки разных размеров одного артикула — **разные
  строки**, они не группируются вместе.
  Bulk-панель после разделения по размеру распределяет количество по
  задачам внутри группы без изменения механики.
  Учётные колонки строки «Сдачи»: **План** = `outputs[i].quantity`,
  **Сделано** = `outputs_progress[i].produced_quantity`,
  **Передано** = сумма передач `(задача, размер выхода)` из ledger,
  **Остаток** = `outputs[i].quantity − produced`.
  Разбивка по выходам в «Сдаче» — **встроенная** трансформация таблицы
  (не критерий профиля группировки): группа разбивается на выходы со
  своими размерами и количествами, одинаково в модалке и печати.
- **Размер — принудительный критерий группировки**: «артикул + размер»
  всегда разделяет строки плана/доски независимо от выбранного профиля
  группировки (профиль управляет остальными критериями — операцией,
  историей, заказом). Размер не отключается в настройках профиля.
- **Колонка «Размер»** — во **всех** таблицах, где видны позиции/задания
  и группировка по размеру (план выдачи/сдачи, страница «Планирование»
  `PlanPage`, доска участка, передачи, печать), показывается колонка с
  подписью размера (`formatDimensionsLabel`: «2,7 м», «—» для безразмерных),
  чтобы строки одного артикула разных размеров различались. Включается в
  настройках печати (`ALL_PRINT_COLUMNS`), по умолчанию — включена.
  Колонка «Размер» — обычная колонка: поддерживает сортировку и фильтр.
- **Сортировка строк по размеру** — строки сортируются **по количеству
  от большего к меньшему**; если применяется сортировка по размеру —
  **от большего размера к меньшему** (3 м → 1 м).
- **Сортировка/фильтр по размеру (бэкенд)** — колонка «Размер»
  сортируется и фильтруется серверно по каноническому значению
  (`length_mm` → число, убыв.; безразмерные `null` — в конец).
  Фильтр — точное совпадение размера. На доске, передачах (`ready`),
  `PlanPage`.
- **Размер задания (WorkTask.dimensions)** — габарит материала на
  нетрансформирующем этапе; доска отдаёт его фронту для группировки
  «выдачи» (у резки вход несёт `input_dimensions`, выходы — `outputs`).
- **Безразмерные штуки (dimensions = null)** — отдельное состояние
  в группировке: образуют свою строку «артикул + без размеров» и не
  смешиваются с размерными строками того же артикула (как в ledger —
  баланс тоже разделяет `null` от размерных).
- **Пара (артикул A+B)** — правило «артикул + размер» применяется к
  паре целиком как к одному артикулу: ключ = `source_sku (+ форма) + размер`.
  Размер пары = пересечение размеров A и B. Передачи и отправка — тоже
  по паре с одним размером (пара идёт вместе, N×A + N×B).
- **Сводка артикула (модалка)** — суммарна по SKU, но с **разбивкой по
  размерам**: количества разных размеров не сводятся «в один котёл».
  Остатки и задачи в работе показывают размер каждой строки.

## Задание (WorkTask)

- Каждая позиция плана (группа строк с общим входом) → своё задание →
  одна карточка на доске трансформирующего участка:
  «150 × 2,7 → 150 × 0,9 + 150 × 1,8». Вход списывается один раз.
- **Частичное выполнение** — оператор вводит факт порциями (50 сегодня,
  50 завтра); каждая порция двигает ledger атомарно: списание входа +
  приход всех выходов.

## Передача между участками

- **Передача по размеру** — единицей передачи является пара
  `(задание, размер)`: с одного задания можно отправить несколько
  передач по одному выходному размеру (каждая — отдельный факт отправки,
  свой `transfer_no`). Резка «2,7 → 0,9 + 1,8» сдаётся дальше двумя
  передачами (0,9 и 1,8); один выходной размер — передача (их может быть
  несколько в заходы). Инвариант: сумма переданного по `(задача, размер)`
  не превышает `transferable` выхода.
  Страница «Готово к передаче» показывает строку на `(задача, размер)`;
  `transferable` выхода = `min(outputs[i].quantity, доступное по задаче)`
  с учётом уже переданного по этому размеру.
  Авто-передача после завершения (`auto_transfer_next`) создаёт **по
  передаче на каждый выход** (с его размером и количеством), а не одну.
  Коррекция (`correct_transfer`) и отмена (`cancel_transfer`) работают
  **по одной передаче** (id + размер) и не затрагивают другие передачи
  того же задания другого размера.
  Входящие передачи участка (`IncomingTransfer`) несут `dimensions` и
  показывают колонку «Размер» (как остальные таблицы).
  Инварианты (проверяются в тестах): у `TRANSFER_SEND`/`TRANSFER_RECEIVE`
  одного Transfer размеры совпадают; сумма переданного по
  `(задача, размер)` ≤ `outputs[i].quantity`; `FINAL_RELEASE` несёт размер
  выхода.
- **Отправка (final release)** — действие на **финальном участке**
  (последний этап маршрута, нет следующего шага): материал завершён,
  «уезжает» заказчику и у нас больше не хранится. На финальный участок
  материал попадает обычной передачей («Передать»); уезжает с него
  кнопкой «**Отправить**» → `FINAL_RELEASE` (участок → склад ГП).
  Передача и отправка — разные действия. Отправка выполняется **по
  строке размера** (как сдача): кнопка появляется для каждого выхода
  со своим `quantity`; `final_release` несёт `dimensions` выхода.
- **Авто-приём (auto-accept)** — политика передачи: оператор,
  отправляющий материал, одновременно принимает его на участке-
  получателе. Отдельного действия/кнопки «Принять» и «Выдать в работу»
  в модели нет: `transfer_send` сразу помечает передачу `accepted`,
  задача-получатель переходит `waiting_previous → ready`, а после
  синхронизации статуса — `in_progress` с `received == issued` (материал
  сразу в работе). Хранение/складские этапы оператор не завершает с
  доски — сырьё передаётся на следующий production-этап напрямую
  строкой «Готово к передаче» (transferable со склада считается по
  физическому остатку размера).

## Аутентификация и сессии

- **Auth-shell (общий модуль входа)** — байт-идентичные в KTM-2000 и HRMS
  файлы страницы входа и OIDC-клиента (`features/auth/*`, `shared/api/client.ts`).
  Правки для двух сервисов делаются в едином стиле: синхронно в обоих
  репозиториях, с поднятием `*_VERSION` и проверкой `verify-sync` (ADR-0007).
- **Server-side сессия (UserSession)** — строка `user_sessions`. Активный
  доступ проверяется по ней, а не по самому JWT: JWT — лишь указатель.
- **Claim `sid`** — всегда `UserSession.id`, только session semantics.
  Сильный инвариант без оговорок: *если JWT содержит `sid`, то `sid` — это
  ссылка на соответствующую активную сессию пользователя из `sub`.*
  Проверка в гейте сверяет активность сессии **и** `session.user_id`
  с владельцем `sub`. Токен без `sid` — не сессия.
- **Break glass** — аварийный вход в обход `users` (когда Authentik
  недоступен). Токен break glass **не содержит `sid`**: сессии не создаёт
  и на неё не ссылается. Правомочность определяется флагом `is_break_glass`.
- **`corr_id`** — непрозрачный UUID, связывающий audit-события входа/выхода
  break glass между собой (у настоящих сессий эту роль выполняет `sid`).
  Единственный эмиттер токена break glass — `create_break_glass_token`,
  который структурно не может добавить `sid`.
- **DEV bypass** — dev/test escape hatch (`DEV_BYPASS_AUTH`): отдельная,
  явно классифицированная ветка доступа, где `sid` опционален и допускается
  magic `admin` / `system@local`. Не имеет отношения к боевому контракту.

## Профиль и его кэш

- **Профиль** — display-поля пользователя: full_name, email, avatar_seed,
  locale, theme. Источник правды — Authentik (IdP); локальная БД — только кэш.
- **Кэш профиля** — локальные копии display-полей в `users`. Пулл при `/me`
  пропускается, пока кэш свеж (`profile_synced_at` в окне TTL).
- **`profile_synced_at`** — метка последнего авторитетного ответа IdP: профиль
  получен **или** «такого пользователя нет». При упавшем пулле не обновляется.
- **`profile_sync_failed_at`** — метка последней упавшей попытки пулла.
  Инвариант: не чаще одной попытки синхронизации профиля в окно TTL,
  успешной или нет.
- **Провал пулла (failed)** — IdP недоступен/ошибка (`AuthentikAdminError`
  502/503). Отличается от «нет такого пользователя»: провал не продлевает
  свежесть кэша.

## Уведомления

- **Уведомление (Notification)** — сообщение, предназначенное для отображения
  пользователю: что произошло и что показать. Чистый контент: type, title,
  payload, ссылка на объект. Не знает про прочтение.
- **Общее уведомление (Global notification)** — уведомление, адресованное
  всем пользователям. В БД: `user_id IS NULL` — деталь хранения адресации,
  а не тип уведомления.
- **Персональное уведомление (Personal notification)** — уведомление,
  адресованное конкретному пользователю (`user_id` заполнен).
- **Состояние уведомления (Notification state / UserNotificationState)** —
  состояние конкретного уведомления относительно конкретного пользователя:
  прочитано/непрочитано, прочитано в `read_at`, закрыто в `closed_at`.
  Единственное место хранения состояния и для общих, и для персональных
  уведомлений. «Broadcast» — не доменный термин (технический жаргон тикетов).
  **Ленивое создание**: state-запись создаётся при первом пользовательском
  действии (read/close). Отсутствие state означает «пользователь ещё не
  взаимодействовал» — для адресата такое уведомление считается непрочитанным
  и активным. Правило одинаково для персональных и общих уведомлений.
- **Прочитано (Read)** — пользователь просмотрел уведомление (колокольчик
  открыт): `read_at` в состоянии уведомления.
- **Закрыто (Closed)** — пользователь убрал уведомление из списка активных
  (кнопка ✕): `closed_at` в состоянии уведомления.

## Подвес (анодирование)

- **Подвес** — несущая конструкция, проходящая через ванну анодирования;
  лимит поверхности **13 м² — общий на весь подвес** (делится между всеми
  висящими на нём штуками), лимит по размеру — **две клюшки по 1450 мм**
  (суммарно 2900 мм занятой ширины, каждая штука занимает `габарит + 20 мм`).
- **Количество на подвес (N)** — сколько штук артикула висит на подвесе;
  авторасчёт: `floor(13/(периметр×длина/10⁶))` по площади,
  `floor(1450/(габарит+20))×2` по размеру, итог = min; округление вниз.
- **Основная длина** — длина артикула, явно выбранная пользователем как
  главная (флаг `is_primary`, ровно одна на артикул). Значение кол-ва на
  подвес и разбивка расчёта показываются именно для неё (приоритет
  авто > ручное), остальные длины — компактные чипы. Выбирается радио-
  кнопкой в форме; в списке сырья и таблице подвесов помечается подписью.
  Если у основной длины значения нет — она не показывается, рендерятся
  только длины со значениями.
- **Парная техкарта (пара)** — техкарта для двух артикулов A и B, которые
  висят на одном подвесе **одновременно и в равных количествах** (`N×A + N×B`).
  Равенство N для A и B — жёсткий инвариант пары; авторасчёт пары **совместный**:
  `by_area = floor(13/((perimeter_A+perimeter_B)×длина/10⁶))`,
  `by_size = floor(2900/(габарит_A+габарит_B+40))`, итог = min; N — единое поле.
- **Режим пары** — наследует режим артикулов: авто только когда оба артикула
  авто; если хоть один ручной — пара ручная (N из ручного значения).
- **Длина пары** — пересечение списков длин артикулов A и B; пустое
  пересечение → «расчёт невозможен».

## Тестовая инфраструктура

- **Test launcher** — `scripts/test-run.ps1`, единственная точка входа в
  backend-тесты; владеет жизненным циклом run-DB.
- **Test Run** — один запуск тестов через launcher; идентифицируется
  `RUN_ID` (12 hex). Каждый run получает собственную БД.
- **Run Database (run-DB)** — эфемерная БД `ktm2000_test_<runid>`, создаётся
  и удаляется launcher'ом на каждый прогон. Разные прогоны не видят и не
  удаляют чужие БД.
- **Orphan database** — run-БД, осиротевшая из-за убитого прогона; убирается
  отдельной командой `test:db:cleanup` по TTL.
- **Module schema** — схема `t_<uuid8>` на тестовый модуль внутри run-DB;
  изолирует модули друг от друга в одном прогоне. В launcher-режиме не
  дропается per-module (run-DB падает целиком launcher'ом); в ручном режиме
  на статичной `ktm2000_test` дропается в teardown.
