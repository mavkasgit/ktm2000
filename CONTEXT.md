# CONTEXT — глоссарий домена KTM-2000

Единый словарь терминов. Используем эти слова в коде, тикетах, тестах и UI.
Решения с обоснованием — в `docs/adr/`.

## Учёт и склад

- **Габариты (dimensions)** — универсальный JSONB-атрибут единицы учёта:
  `{"length_mm": 2700}`, `{"width_mm": 1200, "height_mm": 2400}`, `null`.
  `null` = «безразмерные штуки» (крепёж и т.п.). Один SKU может лежать на складе
  в нескольких габаритах одновременно — это **один продукт, разные состояния**,
  не разные SKU. Не говорим «партия» — партий в модели нет (ADR-0001).
- **Остаток по габариту** — баланс группируется по
  `product + section + dimensions`. «200 шт × 2,7 м» и «50 шт × 3,0 м» — два
  разных остатка одного SKU на одной секции.
- **Справочник измерений (dimension_types)** — каталог допустимых ключей
  dimensions (`length_mm`, «Длина», «мм»). Новый тип размера = строка в
  справочнике, без миграции схемы.
- **Привязка измерений (product_dimensions)** — какие измерения обязательны
  для продукта и их значение по умолчанию (**типовой размер**). Если при
  импорте остатков длина не указана — подставляется типовой размер.
- **Излишки** — годный материал, физически оставшийся сверх плановой логики.
  Хранятся на секции как обычный остаток со своим dimensions, вне плана.

## Трансформация габаритов

- **Трансформация** — операция участка, меняющая dimensions при неизменном SKU:
  вход (N шт × габарит A) → выходы (M шт × габарит B, K шт × габарит C, …).
  Способность **этапа маршрута**, не конкретного участка: пила сегодня,
  гильотина/фрезеровка завтра (ADR-0002).
- **Вход задания** — что списывается: количество заготовок + их dimensions.
- **Выход задания** — что появляется: количество + новые dimensions.
  Выходов может быть несколько (2,7 м → 1,8 м + 0,9 м).
- **Годный остаток резки** — недоиспользованная длина заготовки — всегда
  полноценная единица учёта (режем 0,9 из 2,7 → 1,8 обязательно остаётся
  на учёте). Пропил (≈5 мм) игнорируется. Понятия «обрезок/отход» в модели нет.

## План

- **Позиция плана** — группа строк Excel с общим входом (объединённые
  ячейки «кол-во шт. в 2,7» / «Длина, м») = одна PlanPosition =
  одна операция. Несёт один вход (`input_quantity` × `input_length`)
  и список выходов `[(output_quantity, output_length)]` — по строке
  на выход. Одиночная строка — группа из одного выхода (ADR-0003).
- **План — источник правды по габаритам**: задание берёт вход/выход из
  позиции плана; оператор не назначает размеры сам.

## Задание (WorkTask)

- Каждая позиция плана (группа строк с общим входом) → своё задание →
  одна карточка на доске трансформирующего участка:
  «150 × 2,7 → 150 × 0,9 + 150 × 1,8». Вход списывается один раз.
- **Частичное выполнение** — оператор вводит факт порциями (50 сегодня,
  50 завтра); каждая порция двигает ledger атомарно: списание входа +
  приход всех выходов.

## Аутентификация и сессии

- **Server-side сессия (UserSession)** — строка `user_sessions`. Активный
  доступ проверяется по ней, а не по самому JWT: JWT — лишь указатель.
- **Claim `sid`** — всегда `UserSession.id`, только session semantics.
  Сильный инвариант без оговорок: *если JWT содержит `sid`, то `sid` — это
  ссылка на соответствующую активную сессию пользователя из `sub`.*
  Проверка в гейте сверяет активность сессии **и** `session.user_id`
  с владельцем `sub`. Токен без `sid` — не сессия.
- **Break glass** — аварийный вход в обход `users` (когда Authentik
  недоступен). Токен break glass **не содержит `sid`**: сессии не создаёт
  и на неё не ссылается. Правомочность определяется флагом `is_break_glass`.
- **`corr_id`** — непрозрачный UUID, связывающий audit-события входа/выхода
  break glass между собой (у настоящих сессий эту роль выполняет `sid`).
  Единственный эмиттер токена break glass — `create_break_glass_token`,
  который структурно не может добавить `sid`.
- **DEV bypass** — dev/test escape hatch (`DEV_BYPASS_AUTH`): отдельная,
  явно классифицированная ветка доступа, где `sid` опционален и допускается
  magic `admin` / `system@local`. Не имеет отношения к боевому контракту.
