## Пропущено / не получилось

- **`section-totals` и парные позиции.** Сводка пропускает `product_id IS NULL`;
  это же условие отсекает парные артикулы, у которых продукт резолвится из
  пары. Уверенность средняя: в тесте `_seed_plan` такая позиция названа
  «без продукта пропускается сразу», то есть текущее поведение может быть
  осознанным. Правка требует решения, что считать «неразрешённой» позицией
  (см. предложение 3).
- **Статус задания после `reverse(task_complete)`.** Количества теперь нетто,
  но задача остаётся в `partially_completed`: `resolve_work_task_status` не
  выходит назад из нетерминального `partially_completed` при нулевом факте.
  Операционно завершить её снова можно, но подпись «частично выполнено» при
  нуле — неверна. Это отдельная политика статусов (предложение 4).
- **Гонки запросов предпросмотра остатков и подсказок SKU.** Реальные, но
  исправление требует `AbortController`/id запроса в двух компонентах;
  на фоне уже сделанного это средний риск без теста. В предложениях.
- **`last-completed-operation`** не исключает отменённые завершения: после
  `reverse(task_complete)` он всё ещё указывает на откатанную операцию.
  Отдельная семантика «последняя действительная операция» (предложение 5).
- **`upload_product_photo`** принимает любое расширение и отдаёт файл через
  `/static` (потенциальный stored XSS через `.html`/`.svg`). Отладочный
  `print` уже убран (`a2c24ba9`); остаётся решение по whitelist расширений,
  проверке сигнатуры и лимиту размера (предложение 2).
- **`_validate_admin` в `/api/backups` — заглушка**, всегда `"admin"`. Все
  ручки бэкапов фактически без авторизации. Это не ночная правка: нужно
  решение владельца, кто и как получает доступ (предложение 1).

### 1. Закрыть `/api/backups` настоящей авторизацией (P1, блокер деплоя)

Проблема: `backups.py:975` — `def _validate_admin(current_user: str = "admin")`,
проверка всегда проходит. Любой, кто дотянется до API, может создать/удалить
бэкап, восстановить БД и прочитать произвольный файл (после фикса traversal —
только внутри каталога бэкапов).

Варианты:
- **A. Роль `admin` через `require_role`.** Плюс: единый механизм, как у
  справочников. Минус: сломает dev/e2e-скрипты, которые ходят без токена.
- **B. Оставить заглушку, но закрыть сетью/nginx.** Плюс: нулевой риск кода.
  Минус: защита не в приложении, ошибка конфигурации снова всё открывает.
- **C. A + явный dev-флаг** (как `DEV_BYPASS_AUTH`). Плюс: совместимость со
  стендами. Минус: ещё один флаг, который можно забыть выключить.

Рекомендация: **C**, с тестом «viewer/аноним получает 403/401» по образцу
`test_reference_endpoints_auth.py`. Риск: средний (нужно проверить все
вызовы бэкапов в e2e/скриптах).

### 2. Whitelist расширений фото товара (средний риск)

Проблема: `products.py:1416` берёт `Path(file.filename).suffix` без проверки;
`upload_product_photo` пишет файл в `PRODUCT_PHOTO_DIR`, который смонтирован
как `/static`. Загрузка `.html`/`.svg` даёт stored XSS на том же origin
(нужна роль с правом справочников, но всё равно). Отладочный `print` уже
убран (`a2c24ba9`).

Варианты:
- **A. Whitelist `jpg/jpeg/png/webp/gif` + проверка сигнатуры.** Плюс:
  закрывает вектор и мусорные файлы. Минус: нужно решить, нужны ли SVG.
- **B. Только whitelist расширений.** Плюс: минимальная правка. Минус:
  содержимое не проверяется.
- **C. Раздавать фото с `Content-Disposition: attachment`/отдельного
  поддомена.** Плюс: сильнее. Минус: ломает `<img src>`.

Рекомендация: **A** (без SVG), плюс проверка сигнатуры и лимит размера.
Риск: низкий-средний.

### 3. `section-totals` для парных позиций (средний риск)

Проблема: `production_plans.py:1175-1180` требует `position.product_id is not
None`; парная позиция хранит продукт в `source_payload`, поэтому выпадает из
сводки. Сейчас это выглядит осознанным для «неразрешённых» позиций.

Варианты:
- **A. Заменить проверку на резолвер эффективных продуктов
  (`_resolve_effective_product_ids`).** Плюс: парные попадают в сводку.
  Минус: нужно определить поведение для действительно неразрешённых.
- **B. Оставить как есть и задокументировать** «парные позиции не входят в
  section-totals». Плюс: нулевой риск. Минус: отчётность неполная.

Рекомендация: **A** после подтверждения владельцем, что парные должны
считаться; риск средний.

### 4. Статус задания после отката завершения (средний риск)

Проблема: после `reverse(task_complete)` количества нетто-нулевые, но
`WorkTask.status` остаётся `partially_completed`/`completed`:
`resolve_work_task_status` для `completed` сразу возвращает `None`, а
`partially_completed` при нулевом факте не меняет.

Варианты:
- **A. В reversal явно пересчитывать статус с разрешённым понижением**
  (отдельная функция, не общий резолвер). Плюс: точное восстановление.
  Минус: два правила статуса.
- **B. Расширить `resolve_work_task_status`: `produced == 0` и
  `partially_completed` → `in_progress`/`ready`.** Плюс: одно правило.
  Минус: может задеть другие сценарии, нужен полный прогон.
- **C. Оставить статус и показать в UI «откатано».** Плюс: без риска.
  Минус: противоречивая карточка.

Рекомендация: **A** (локально в reversal), риск средний. Делать вместе с
предложением 5: это один сценарий «состояние после отката».

### 5. `last-completed-operation` и отменённые завершения (низкий риск)

Проблема: эндпоинт берёт последнюю `COMPLETE` без учёта `reverses_id`;
после отката показывает откатанное действие.

Варианты:
- **A. Исключать компенсации и исходные, у которых есть компенсация.**
  Плюс: «последняя действительная». Минус: запрос с `NOT EXISTS`.
- **B. Оставить как исторический факт.** Плюс: ничего не меняем. Минус:
  подпись вводит в заблуждение.

Рекомендация: **A**, риск низкий.

### 6. Гонки предпросмотра остатков и подсказок SKU (низкий-средний риск)

`ImportRemaindersDialog.loadPreview` и `ProductSkuSearchInput.doSearch` не
отменяют предыдущий запрос: поздний ответ затирает свежий. Варианты:
- **A. `AbortController` + id запроса.** Плюс: корректно; минус: две правки
  и тесты с таймингами.
- **B. Проверка «ответ для текущего ввода» по ключу.** Плюс: проще; минус:
  дублирование логики в двух местах.

Рекомендация: **A** отдельным тикетом; риск низкий.

### 7. Мелкое, но не ночное

- `scripts/test-run.ps1` читает `TEST_DB_USER`/`TEST_DB_PASSWORD`, а
  `scripts/test-db.py` — `TEST_DB_ADMIN_USER`/`TEST_DB_ADMIN_PASSWORD`.
  При переопределении одного имени создание БД и DSN разъедутся. Свести к
  одному имени с обратной совместимостью.
- `_transfer_no()` — `TR-<timestamp до микросекунд>`; unique-индекс
  `uq_transfers_transfer_no` есть, поэтому коллизия даст ошибку, а не дубль.
  Теоретический 500 при двух передачах в одну микросекунду; суффикс —
  отдельным тикетом, если владелец решит менять формат номера.

## Допущения

- Дата ветки — локальная дата машины (`2026-11-08`), хотя работа перешла в
  ночь на 09.11.
- База ветки — `ed0b0597` (`perf/307` и `origin/main`); локальный `main`
  устарел и для сверки не используется.
- Аудит persisted-кэшей не запускался на рабочей БД: доступа к ней нет.
  Скрипт сначала идёт dry-run; `--apply` — только после подтверждения
  владельцем и на копии.
- B1: сужение прав операций участка до `REFERENCES_WRITER_ROLES` совпадает
  с UI (`canEditReferences`), но подтверждение владельца, что
  viewer/transporter не использовали API намеренно, всё ещё требуется.
- Одновременный запуск backend- и frontend-тестов на этой машине создаёт
  конкуренцию за CPU; для честного baseline frontend перепроверялся
  изолированно. В отчёте это отмечено, а не выдано за дефект.
- В `_backup_file_path` выбран ответ 404 (а не 400/403) для имени с
  разделителями — как на «файл не найден», чтобы не подтверждать
  существование файла вне каталога.
- Для `reverse(task_complete)` принято, что нетто-ноль по COMPLETE/SCRAP —
  правильная семантика (ADR-0019: все чтения `reverses_id` переходят на
  нетто). ADR-0018 («COMPLETE/SCRAP остаются gross») писался до появления
  компенсатора `task_complete` и теперь помечен как заменённый.
- Ручная браузерная проверка Escape не выполнялась: поведение закрыто
  RTL-тестом на `document`/`window` и e2e-смоуком; capture-фаза убирает
  гонку с Radix, но визуальный прогон остаётся за владельцем.

## Как откатить всё разом

Ветка начата от `ed0b0597` (== `perf/307` == `origin/main`).

```bash
git checkout perf/307-auto-transfer-long-chain
git branch -D night/2026-11-08
```

Если ветка уже нужна в истории — откатывать диапазоном в обратном порядке:

```bash
git revert --no-commit ed0b0597..night/2026-11-08
```

Зависимости, которые нельзя игнорировать при точечном откате:

- `50f97e0e` (лента строк плана) — продолжение `ca3fddcd` (нетто-чтения);
  откатывать `50f97e0e` раньше `ca3fddcd` нельзя.
- `62d977b0` содержит и частичную авто-передачу, и уточнение после
  трансформации (бывшие `012963f9` + `92059a90`) — откатывается одним
  коммитом.
- `4e62bd65` (аудит persisted-кэшей) опирается на `ca3fddcd`: без него
  скрипт сверяет уже неверную формулу.
- `7861b766` (Escape/AlertDialog) включает расширение `isAnyDialogOpen`
  и capture-фазу; откат возвращает снятие массового режима при Escape
  внутри подтверждения.

Новые коммиты по ревью (после доклада) откатываются тем же диапазоном:
`git revert --no-commit 2d3c7276..HEAD` (или в обратном порядке по одному).
