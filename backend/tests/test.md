# Документация по тестированию в KTM-2000 (test.md)

В проекте настроена и оптимизирована система тестирования на базе **pytest**, **pytest-xdist** и **pytest-testmon**. Запуск тестов ускорен более чем в 7 раз за счет инкрементальных проверок, распараллеливания и транзакционной изоляции базы данных в оперативной памяти.

---

## 🏗️ Архитектура и изоляция базы данных

Для обеспечения высокой скорости и независимости тестов используется следующая схема:

1. **Создание схем на уровне модулей (`scope="module"`)**:
   - Вместо создания и удаления схемы базы данных для каждого теста, схема создается **один раз на тестовый модуль**.
   - Имя схемы генерируется динамически с префиксом `t_` (например, `t_a1b2c3d4`). Это позволяет запускать тестовые модули параллельно без взаимных блокировок и пересечения данных.
2. **Транзакционная изоляция тестов (`function scope`)**:
   - Каждый отдельный тест выполняется внутри изолированной транзакции (`SAVEPOINT`).
   - По завершении теста транзакция полностью откатывается (`rollback`). База данных возвращается в исходное состояние, которое было на момент начала модуля.
3. **Сброс последовательностей автоинкремента**:
   - В связи с тем, что последовательности (`SEQUENCE`) в PostgreSQL не откатываются при роллбэке транзакции, ID создаваемых сущностей инкрементируются от теста к тесту.
   - Для стабильности тестов, завязанных на системного пользователя, перед каждым тестом в фикстуре `session` принудительно сбрасывается генератор ID таблицы пользователей:
     ```sql
     ALTER TABLE users ALTER COLUMN id RESTART WITH 1;
     ```
   - Это гарантирует, что создаваемый фикстурой `system_user` всегда имеет `id = 1`, предотвращая ошибки нарушения внешних ключей (`ForeignKeyViolationError`) в аудит-логах.

## 📝 Правила написания новых тестов

При добавлении новых тестов обязательно следуйте этим правилам:

* **Используйте динамические ID**: Не завязывайтесь на то, что созданные в тесте сущности (продукты, задачи, разделы) будут иметь фиксированные `id = 1`, `id = 2` и т.д. Из-за инкремента последовательностей Postgres в рамках модуля их ID будут расти. Всегда считывайте ID из сохраненного объекта: `product.id`, `task.id`.
* **Изоляция транзакций**: Помните, что вызов `session.commit()` внутри теста в SQLAlchemy при включенном `join_transaction_mode="create_savepoint"` фиксирует изменения только во внутреннем сейвпоинте, а не в основной транзакции соединения. Реальный коммит в базу произойдет только после завершения всего теста.
* **Не изменяйте глобальное состояние модуля**: Если вам нужны общие данные для всех тестов модуля, создавайте их в фикстурах с `scope="module"`. Однако помните, что тесты не должны мутировать эти данные, иначе нарушится независимость тестов.
* **Используйте хелперы целостности**: После проведения операций перемещения запасов (`Transfer`, `StockTransaction`) обязательно вызывайте валидатор инвариантов:
  ```python
  from tests.test_integrity_invariants import assert_no_invariants_violations
  await assert_no_invariants_violations(session, context="your-context")
  ```

## 🚀 Команды для запуска тестов

Все команды запускаются из корня проекта:

* **Параллельный быстрый запуск (Рекомендуется)**:
  ```bash
  npm run test:pytest:fast
  ```
  Запускает тесты на всех доступных ядрах процессора с помощью `pytest-xdist`. Время прохождения полного набора — **~3 минуты**.

* **Умный инкрементальный запуск (для разработки/TDD)**:
  ```bash
  npm run test:pytest:mon
  ```
  Использует `pytest-testmon`. Запускает **только те тесты**, код которых или зависимости которых изменились с момента последнего прогона. Позволяет мгновенно получать фидбек при редактировании функций.

* **Запуск только упавших тестов**:
  ```bash
  npm run test:pytest:lf
  ```
  Запускает только те тесты, которые завершились ошибкой во время предыдущего прогона.

* **Обычный последовательный запуск**:
  ```bash
  npm run test:pytest
  ```

* **Профилирование медленных тестов**:
  В `backend/pytest.ini` настроен вывод 10 самых медленных тестов (`--durations=10`). Следите за выводом в конце прогона, чтобы не допускать появления медленных тестов.
